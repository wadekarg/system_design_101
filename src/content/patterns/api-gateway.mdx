<Callout type="analogy">
Think of a big hotel. Guests don't wander into the kitchen, housekeeping, or
accounting to get what they need — they walk up to the **front desk**. One
counter checks your ID, tells you which room is yours, calls the right
department, and hands you a single answer.

An **API Gateway** is that front desk for your microservices. Clients talk to
one place; the gateway checks who you are, routes you to the right service, and
returns one clean response. The dozens of services behind it stay hidden.
</Callout>

## What an API Gateway is

As a system grows from a monolith into many **microservices**, clients hit a
wall: instead of one endpoint, they now face dozens — each with its own
hostname, auth scheme, and API contract. A mobile app building a single screen
might need five separate calls to five services and then stitch the results
together itself.

An **API Gateway** fixes this by being a **single entry point** for all client
requests. Clients send everything to the gateway, which:

- **routes** each request to the right downstream service,
- **aggregates** responses when a screen needs several services,
- **applies shared logic** like authentication and rate limiting.

From the client's side, the whole system looks like *one API*. The internal
topology stays hidden. Because every request passes through it, the gateway sits
in a uniquely powerful spot — it can inspect, transform, reject, or route any
request without the downstream services knowing anything happened.

## What the gateway handles for you

The power of the pattern is the **breadth of cross-cutting concerns** it handles
in one place. Instead of every service reimplementing these, you implement them
once at the gateway and every service benefits.

- **Authentication & authorization** — the gateway validates the JWT, OAuth
  token, or API key, then forwards the caller's identity as trusted headers.
  Downstream services skip re-checking auth.
- **Rate limiting & throttling** — it sees all traffic, so it rejects abusive
  callers *before* they reach any backend.
- **Request routing** — `/api/users/*` goes to the User Service, `/api/orders/*`
  to the Order Service, based on path, headers, or body.
- **Protocol translation** — clients speak HTTP/REST while services may speak
  gRPC or WebSockets; the gateway bridges them.
- **SSL/TLS termination** — HTTPS ends at the gateway, centralizing certificate
  management.
- **Load balancing** — it spreads requests across healthy instances of each
  service, usually via service discovery.
- **Response caching** — idempotent GETs can be served without touching the
  backend.
- **Logging & observability** — one choke point means uniform logs, metrics, and
  trace spans across every service.

<Callout type="tip">
Auth at the gateway is fast because JWT validation is **local** — the gateway
checks the token signature with the identity provider's public key, no network
call needed. It then injects claims as headers like `X-User-Id: 12345` or
`X-User-Roles: admin,read`, and services trust them without re-validating.
</Callout>

## Coarse vs fine-grained authorization

Split the decisions by who has the context to make them well:

- **Coarse-grained** ("is this caller authenticated?", "does this API key have
  the paid tier?") → the **gateway** decides.
- **Fine-grained** ("can *this* user edit *this specific* document?") → the
  **downstream service** decides, because it owns the domain data.

For **API-key** auth (common in machine-to-machine calls), the gateway looks up
the key to find its identity and permissions. Cache that lookup aggressively —
key metadata rarely changes, so a DB round-trip per request is wasteful.

## Gateway vs load balancer vs reverse proxy

These three overlap and get confused. The difference is *how much they
understand about your application*.

| Capability | Reverse Proxy | Load Balancer | API Gateway |
|---|---|---|---|
| Forwards requests to backends | ✅ | ✅ | ✅ |
| Spreads load across instances | sometimes | ✅ (its whole job) | ✅ |
| TLS termination | ✅ | ✅ | ✅ |
| Auth / rate limiting | ✗ | ✗ | ✅ |
| Path/content-based routing | basic | ✗ | ✅ (rich) |
| Protocol translation, aggregation | ✗ | ✗ | ✅ |
| Knows about application/API semantics | no | no | yes |

An API Gateway is essentially a **smart, application-aware reverse proxy** that
adds cross-cutting logic. A load balancer just distributes connections; a plain
reverse proxy just forwards them.

## Routing in a dynamic cluster

Hardcoded service addresses break the moment services scale up and down. The
gateway integrates with **service discovery** — Consul, Kubernetes DNS, AWS
Service Discovery — to keep a live registry of healthy instances. On each
request it asks discovery for the current healthy set, then load-balances across
them.

<Callout type="tip">
In **Kubernetes**, the `Ingress` resource formalizes this idea. Ingress
controllers (nginx, Traefik, or cloud-native ones) route external traffic to
Services by host and path — and full gateway features are layered on top.
</Callout>

## The BFF pattern

The **Backend for Frontend (BFF)** pattern is the single gateway, evolved.
Different clients have different needs: a mobile app on 4G wants compact,
aggregated responses; a desktop web app prefers granular endpoints it can call
in parallel; third-party developers want stable, versioned endpoints.

In BFF, you run a **separate gateway per client type**. The iOS BFF shapes
responses for the iOS data model; the Web BFF serves richer, granular data. Each
client team evolves its own contract without negotiating with the others or
settling for a lowest-common-denominator shape.

The cost: more gateway configs to operate. The payoff: client-specific
optimizations (compression, field selection, aggregation) live in one place
instead of being reimplemented in every client.

## Where this shows up

- **Public API products (Stripe, Twilio)** → a gateway enforces per-key rate
  limits, versioning, and usage metering at the edge, so billing and abuse
  control live in one spot.
- **Mobile-heavy apps (Netflix, Uber)** → BFF-style gateways aggregate many
  backend calls into one compact response, saving battery and round-trips on
  slow networks.
- **Kubernetes microservice platforms** → an Ingress/gateway is the single
  documented front door; internal services stay private and unexposed.
- **Enterprises modernizing a monolith** → a gateway sits in front, routing new
  paths to microservices and legacy paths to the monolith during a gradual
  strangler-fig migration.

## Pressure points

<Callout type="warning">
The gateway sits on the critical path of **every** request, so its weaknesses
hit the whole system:

- **Single point of failure** — if the gateway dies, all services go dark. Never
  run one instance. Deploy several behind a load balancer with health checks and
  automatic failover.
- **Bottleneck / latency** — you added a network hop (client → gateway →
  service), typically 1–5 ms. Keep auth local, cache hot responses, and measure
  it on latency-sensitive paths.
- **Config sprawl** — routes, auth policies, and rate limits pile up into a giant
  shared config owned by one platform team, creating coordination friction and
  risky deploys.
</Callout>

## Handling the pressure points

- **Avoid the SPOF** → run multiple stateless gateway instances behind a load
  balancer; health-check and auto-heal them. Keep the gateway *stateless* so any
  instance can serve any request.
- **Tame the latency** → validate JWTs locally, cache API-key and response data,
  and keep gateway logic thin — push heavy business logic to services.
- **Curb config sprawl** → treat gateway config as code (versioned, reviewed,
  CI-deployed), and split into per-team or per-client (BFF) configs so ownership
  is clear.

## Alternatives & related ideas

<Callout type="alternative">
The gateway handles **north-south** traffic (client → service). For
**east-west** traffic (service → service inside the cluster), reach for a
**service mesh** like Istio or Linkerd — it gives you mutual TLS, retries,
circuit breaking, and tracing on internal calls without funneling everything
through one center.

For per-client response shaping, use the **BFF pattern** above. And for very
simple setups, a plain **reverse proxy or Ingress controller** may be all you
need — don't reach for a full gateway until the cross-cutting concerns justify
it. Popular gateways: **Kong**, **AWS API Gateway**, **nginx**, and **Envoy**.
</Callout>

## Summary

An **API Gateway** is the single front door to your microservices: it routes,
aggregates, and applies shared concerns like **auth, rate limiting, TLS
termination, and observability**, so each service can focus on business logic and
clients see one clean API. It's more than a load balancer or reverse proxy
because it understands your application's semantics. The catch is that it lives
on every request's critical path — so run **multiple highly available
instances**, keep it thin to control latency, and manage its config as code.
Reach for a **service mesh** for service-to-service traffic and the **BFF
pattern** when different clients need different response shapes.
