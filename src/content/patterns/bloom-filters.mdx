<Callout type="analogy">
Imagine a nightclub bouncer with no guest list — just a rubber stamp and a
book of smudged ink marks. When someone enters, he stamps a few random pages.
Later, to check if you've been in before, he looks at *your* pages: if any is
blank, you've **definitely** never been here. If all are stamped, you've
**probably** been here — though the marks might just be leftovers from other guests.

That's a Bloom filter. It's astonishingly cheap to keep, it's never wrong when
it says "no," and it's occasionally wrong when it says "yes." For huge sets,
that lopsided trade is a bargain.
</Callout>

## The problem: "have I seen this before?" at scale

Tons of systems need to answer one cheap question very fast: **has this URL been
crawled? Is this username taken? Is this IP on the blocklist?**

The obvious fix is a **hash set** holding every element. Fine for thousands of
items. But for **billions** — billions of crawled URLs, seen events, registered
emails — that set balloons to tens or hundreds of gigabytes of RAM. Too expensive.

The key insight: you often don't need a *guaranteed* answer. You need to **cheaply
rule out the clear negatives** and save the expensive lookup (a database query, a
disk read) for the rare item that *might* be present.

## How a Bloom filter works

It's just two pieces:

- A **bit array** of `m` bits, all starting at 0.
- **k independent hash functions**, each mapping any input to one of the `m` positions.

**To add an element:** hash it k ways to get k positions, and set all k bits to 1.
The element itself is *never stored* — only the pattern of set bits remains.

**To query an element:** hash it the same k ways and look at those k bits.

- If **any** bit is 0 → the element is **definitely not** in the set.
- If **all** bits are 1 → the element is **probably** in the set.

The "definitely not" answer is airtight: if the element had ever been added, all
k of its bits would be 1. So a single 0 proves it was never added — **no false
negatives, ever**.

The "probably yes" answer is where uncertainty lives. Those k bits might all be 1
because *other* elements happened to set them. That's a **false positive**: the
filter says "maybe" for something that was never added.

<Callout type="tip">
Think of the two answers as asymmetric: **"no" is a fact, "yes" is a hint.**
Design your system so the fact (skip the work) is the common path and the hint
(do a verifying lookup) is the rare exception.
</Callout>

## Tuning false positives

The false positive rate isn't an accident — it's a **dial you set**. Given `n`
elements to insert and a target false positive rate `p`, you compute the ideal
bit array size `m` and hash count `k`:

```
m = -(n * ln(p)) / (ln(2))^2
k = (m / n) * ln(2)
```

More bits or more hash functions → fewer false positives, more memory. Fewer →
the opposite. For most systems, a rate between **0.1% and 5%** is the sweet spot:
nearly every negative is answered instantly and cheaply, and the rare false
positive just pays for one fallback lookup.

<Callout type="tip">
Concrete numbers: 1 billion elements at a **1% false positive rate** needs about
**9.6 bits per element — ~1.2 GB total**. A hash set of the same billion 64-bit
integers needs **at least 8 GB** just for the values, plus table overhead. That's
roughly a **10x memory win**, and the optimal hash count lands around **k = 7**.
</Callout>

## Bloom filter vs hash set

| Property | Bloom filter | Hash set |
|---|---|---|
| Memory (1B items) | ~1.2 GB | 8+ GB |
| "Is it present?" | Probably / Definitely not | Exact yes/no |
| False positives | Yes (tunable) | Never |
| False negatives | Never | Never |
| Delete an element | No (standard) / Yes (counting) | Yes |
| Iterate / list members | No | Yes |
| Insert & lookup cost | O(k), effectively constant | O(1) average |

The table captures the whole deal: you **give up exact answers and the ability to
list or delete members**, and in exchange you get **an order of magnitude less
memory** and constant-time operations that don't grow with the data.

## Where this shows up

- **Web crawlers & URL shorteners** → skip re-crawling seen URLs. Google's crawler
  famously used a Bloom filter in front of the URL frontier: "definitely not seen"
  means enqueue; "probably seen" triggers a rare check against the real store.
- **Database engines (Cassandra, RocksDB, HBase)** → each SSTable carries a Bloom
  filter. On a read, if the filter says the key is definitely not in that file,
  the engine **skips the disk read entirely** — huge for LSM-tree read amplification.
- **Cache layers** → guard against **cache penetration**. Check the filter first;
  a "definitely not" lets you skip the cache and avoid stampedes from attackers
  hammering keys that exist nowhere.
- **Spam & network security** → test senders, IPs, and domains against enormous
  blocklists too big to hold in full. A false positive just delays a legit sender;
  a false negative (letting a known bad actor through) is exactly what can't happen.
- **Bitcoin SPV clients** → a lightweight client sends a Bloom filter to full nodes
  so they forward only the transactions it might care about.

## When they break

<Callout type="warning">
Bloom filters have three classic failure modes:

- **False positives are unavoidable.** If your system truly cannot tolerate
  *any* false positive, a Bloom filter alone is wrong — you must verify every
  "probably yes" against the source of truth, or use an exact structure.
- **You can't delete.** Clearing an element's bits may zero a bit another element
  shares, producing **false negatives** and breaking the core guarantee. Standard
  filters are append-only.
- **They fill up.** Insert far more than the `n` you sized for and the bit array
  saturates — the false positive rate climbs toward 100% and the filter becomes
  useless. Sizing is a commitment made at construction time.
</Callout>

## Handling the pressure points

- **Can't tolerate false positives?** → keep the filter as a fast pre-check, then
  verify each "probably yes" against the authoritative store. The filter still
  eliminates the vast majority of negatives cheaply.
- **Need deletes?** → use a **counting Bloom filter** (increment/decrement small
  counters instead of flipping single bits), at the cost of extra memory per cell.
- **Set keeps growing?** → size for the real `n` up front, monitor the fill ratio,
  and **rebuild into a larger filter** (or use a **scalable Bloom filter** that
  chains sub-filters) when you outgrow it.

## Alternatives & related ideas

<Callout type="alternative">
Reach for a variant when the plain filter's limits bite:

- **Counting Bloom filter** — replaces each bit with a small counter so you can
  **delete** elements; costs several bits per slot instead of one.
- **Cuckoo filter** — supports deletes *and* often uses less space at low false
  positive rates, with better cache locality; it stores compact fingerprints in a
  cuckoo hash table.
- **Quotient filter** — another delete-capable, more cache-friendly alternative
  that plays nicely with resizing and merging.
- **Scalable Bloom filter** — chains multiple filters so capacity grows on demand
  without a full rebuild.

If you need exactness and can afford the RAM, a plain **hash set** is still the
right answer — the whole point of these filters is trading certainty for space.
</Callout>

## Summary

A Bloom filter is a **bit array plus k hash functions** that answers set
membership with a lopsided promise: **"definitely not" is always true, "probably
yes" is occasionally wrong.** That one-sided error buys roughly a **10x memory
reduction** over a hash set and constant-time operations that don't grow with the
data — ideal for crawlers, cache guards, and LSM databases skipping disk reads.
The price is a **tunable false positive rate**, **no deletes** in the standard
form, and a fixed capacity you must size up front. When those limits pinch, verify
"maybe" hits against the source of truth, or reach for a **counting or cuckoo
filter**.
