<Callout type="analogy">
Picture a **round clock face**, but instead of 12 hours it has billions of tiny
positions around the rim. You drop your **servers** onto the clock at scattered
spots, then drop each **key** somewhere on the rim too. To find a key's home, you
start at the key and walk **clockwise** until you bump into the first server —
that server owns the key.

Now add a new server: it slots in at one spot on the clock, and only the keys in
the little arc just before it change hands. Everyone else keeps the same home.
That's the whole idea — moving one server disturbs one slice of the clock, not
the entire keyspace.
</Callout>

## The problem: modulo hashing breaks on resize

Say you build a distributed cache from three servers. The obvious way to spread
keys is **modulo hashing**: send a key to server `hash(key) % n`, where `n` is
the server count. If `"user:123"` hashes to 47, then `47 % 3 = 2`, so it lives on
server 2. Clean and simple — **as long as `n` never changes**.

The trouble starts the instant you scale. Add a fourth server and `n` jumps from
3 to 4. Now `"user:123"` maps to `47 % 4 = 3` — a *different* server. And this
isn't a one-off: changing `n` by one reshuffles **nearly every key** in the whole
cache.

On the next request, that key misses on the new server and falls through to the
database. Multiply by millions of keys hitting at once and you've effectively
**flushed your entire cache** — a **thundering herd** that can drown your
database. Removing a server does the same damage in reverse.

<Callout type="tip">
The math is brutal: with modulo hashing, growing from n to n+1 servers remaps
roughly **(n / (n+1)) of all keys**. Going from 9 to 10 servers moves ~90% of
them. What you actually want is to move only about **K/n** keys — the fair share
that belongs on the one server you added.
</Callout>

## The fix: put servers and keys on one ring

Consistent hashing maps **both servers and keys into the same circular address
space** — the **hash ring**. Think of a circle numbered `0` to `2^32 - 1`. You
hash each server's identifier (its IP or hostname) to a spot on the ring, using
the *same* hash function you use for keys.

To find a key's owner:

- Hash the **key** to its position on the ring.
- Walk **clockwise** until you hit the first server.
- That server owns the key.

Because both live in the same space, the mapping is **deterministic** — the same
key always lands on the same server, as long as the servers don't change.

Now the payoff. **Adding a server** drops it between two existing servers; only
the keys in the arc between the newcomer and its clockwise-previous neighbor move
to it. Everything else is untouched. **Removing a server** hands only its keys to
the next server clockwise. Either way, roughly **K/n keys move** instead of all
of them.

That's the fundamental insight: arranging servers and keys on a ring means any
one node change disturbs only its **immediate ring neighbors**, never the whole
keyspace.

### Modulo hashing vs consistent hashing

| Aspect | Modulo hashing (`hash % n`) | Consistent hashing (ring) |
|---|---|---|
| Add/remove a node | ~**all** keys remap | ~**K/n** keys remap |
| Cache impact of resize | Near-total flush → thundering herd | A small slice repopulates |
| Load balance | Even (when `n` is fixed) | Uneven with few nodes → **virtual nodes** |
| Weighting big servers | Hard | Easy (more virtual nodes) |
| Best when | Node count never changes | Cluster grows, shrinks, or fails often |

## Virtual nodes: fixing lumpy distribution

Basic consistent hashing has a real weakness: **uneven distribution**. With only
a few servers, the ring splits into arcs of very different sizes depending on
where each server's hash happened to land. One server might own **40% of the
ring** while another owns **5%** — badly lopsided load.

**Virtual nodes** (vnodes) fix this. Instead of placing each physical server at
one spot, you place it at **many** — often 100 to 300 positions. Each virtual
node hashes as something like `server-A:0`, `server-A:1`, ... `server-A:150`, and
the physical server owns the union of all those arcs.

<Callout type="tip">
With a few hundred vnodes per server, the **law of large numbers** kicks in and
positions spread nearly uniformly around the ring. Add a server and its vnodes
grab small slices from *many* servers at once — not one unlucky neighbor. Remove
one and its load flows back out proportionally.
</Callout>

Virtual nodes also make **weighting** trivial: a server with twice the RAM gets
twice the vnodes, and naturally receives about twice the keys — with zero change
to the routing logic.

## Where this shows up

- **Amazon DynamoDB** → partitions items across storage nodes by a hash of the
  partition key. Virtual nodes keep partitions even and make post-scaling
  rebalancing minimal.
- **Apache Cassandra** → the whole architecture is a token ring. Each node owns a
  token range, data replicates to the next few nodes clockwise for fault
  tolerance, and only affected ranges move when nodes join or leave.
- **Redis Cluster** → uses a pragmatic variant: **16,384 fixed hash slots** split
  across nodes. Adding/removing a node migrates whole slots — simpler to reason
  about than a raw ring, same core benefit.
- **CDNs** → route each URL to a consistent edge cache node, so cached copies
  accumulate on one server instead of scattering across all of them.

The common thread: they all spread a huge keyspace across a **changing** cluster
and can't afford a global reshuffle every time membership changes.

<Callout type="warning">
The trap is assuming the ring balances itself. With **few physical nodes and no
virtual nodes**, load is genuinely lopsided — one server can carry many times its
share. A second failure mode is a **hot key**: consistent hashing spreads *keys*
evenly, but if one key (a celebrity's profile, a viral URL) gets 90% of the
traffic, the ring can't help — that whole load still lands on one server.
</Callout>

## Handling the pressure points

- **Uneven arcs / lopsided load?** → use **virtual nodes** (100–300 per server).
  This is the default in every serious implementation, not an optional extra.
- **Heterogeneous hardware?** → assign **more vnodes to bigger machines** so load
  tracks capacity, with no routing changes.
- **Hot single key?** → the ring won't save you. **Replicate** that key across
  several nodes and load-balance reads, or cache it at the edge / in the client.
- **Cascading failure when a node dies?** → keep **replicas** on the next nodes
  clockwise so a crash is an instant failover, not a mass of cache misses.

## Alternatives & related ideas

<Callout type="alternative">
Consistent hashing isn't the only way to place data:

- **Rendezvous (HRW) hashing** — for each key, compute `hash(key, server)` for
  every server and pick the highest. Same minimal-movement property, often
  simpler, and no ring to maintain.
- **Fixed hash slots** (Redis Cluster's 16,384 slots) — a discretized ring that's
  easier to operate and migrate.
- **Range partitioning / directory-based sharding** — a lookup table maps key
  ranges to nodes. Maximum flexibility, but you must keep the directory highly
  available.

Reach for plain **modulo hashing** only when the node count is truly fixed — it's
the simplest thing that works, right up until you resize.
</Callout>

## Summary

Modulo hashing (`hash % n`) is simple but catastrophic on resize: change `n` by
one and nearly every key remaps, flushing your cache and stampeding your database.
**Consistent hashing** puts servers and keys on a shared **ring** and walks
clockwise to find each key's owner, so adding or removing a node moves only about
**K/n keys** instead of all of them. Because a handful of servers carve the ring
into uneven arcs, real systems use **virtual nodes** — hundreds of positions per
server — to balance load and to weight bigger machines. This is exactly why
**DynamoDB, Cassandra, Redis Cluster, and CDNs** lean on it: they scale, shrink,
and survive failures without ever reshuffling the whole keyspace.
