## Event-Driven vs Request-Driven

In a request-driven (or request-response) architecture, when Service A needs data from Service B, it calls Service B directly and waits for a response. The call is synchronous: A is blocked until B responds. This is the natural model for reads (fetching data) and is familiar from traditional REST APIs. Its weakness is coupling: A must know B's address, B must be available when A needs it, and if B is slow or down, A is stuck.

In an event-driven architecture, services communicate by producing and consuming events through a message broker (like Apache Kafka, RabbitMQ, or AWS SNS/SQS). When something noteworthy happens in Service A — a user placed an order, a payment was processed, a file was uploaded — A publishes an event to the broker. Any number of other services can subscribe to that event type and react accordingly. A never knows who is consuming its events and does not wait for a response.

This shift from synchronous calls to asynchronous events has profound implications. Services become loosely coupled: Service A does not need to know that Services B, C, and D exist. You can add a new consumer of the `OrderPlaced` event without modifying Service A at all. If Service C is temporarily down, its events queue in the broker and it processes them when it recovers — no data is lost, and Service A is unaffected. The system becomes more resilient, more extensible, and more independently deployable.

## Events, Commands, and Queries

Not all messages in an event-driven system are the same kind of thing. Distinguishing between events, commands, and queries helps clarify the intent of each message and design more coherent systems.

An **event** is a record of something that has already happened: `OrderPlaced`, `PaymentProcessed`, `UserRegistered`. Events are facts — they describe completed actions in the past tense. The producer publishes them without expecting any particular response. Any consumer can react to an event. Events are the natural currency of event-driven systems.

A **command** is a directive to perform an action: `PlaceOrder`, `SendEmail`, `GenerateInvoice`. Commands have intent and a specific target recipient. They may be sent via a queue to a single consumer (point-to-point). Unlike events, commands imply that the sender cares about whether the action succeeds.

A **query** retrieves data and is typically synchronous — it does not fit naturally into asynchronous messaging. The CQRS pattern (discussed below) formalizes the separation between commands/events (write side) and queries (read side).

In practice, many systems blend these patterns. The important discipline is to design your events as immutable facts about the world, rather than as instructions for what should happen next.

## Event Sourcing

Traditional applications store the current state of entities in a database. When a user updates their address, the old address is overwritten. When an order is cancelled, the order record is updated with status `cancelled`. The history of how state was reached is lost.

Event sourcing inverts this model. Instead of storing the current state, you store the sequence of events that produced it. An order's history might be: `OrderCreated`, `ItemAdded`, `ItemAdded`, `ShippingAddressUpdated`, `PaymentCaptured`, `OrderShipped`. The current state of the order is not stored directly — it is derived by replaying these events in sequence.

This has several powerful consequences. First, you have a complete, immutable audit log of everything that ever happened. For financial systems, compliance requirements, and customer support ("what happened to this order?"), this is invaluable. Second, you can replay events to reconstruct past states: what did this order look like before the payment was captured? Third, you can replay the event log through a different projection function to produce a new view of your data — enabling powerful retroactive analysis and new read models without migrating existing data.

Event sourcing pairs naturally with event-driven architecture: the stored events are also the messages that flow between services. An order service that uses event sourcing naturally produces `OrderPlaced` and `PaymentCaptured` events that downstream services can consume.

The challenges of event sourcing are real. Querying current state requires either replaying all events (slow for large histories) or maintaining a separate "snapshot" of the current state alongside the event log. Schema evolution — changing the structure of events over time — requires careful versioning. Debugging and mental model maintenance become harder because state is implicit rather than explicit. Event sourcing is a powerful pattern for domains with complex, auditable workflows, but it adds significant complexity and should not be adopted as a default for simple CRUD systems.

## CQRS

Command Query Responsibility Segregation (CQRS) is the pattern of using separate models for reading data (queries) and writing data (commands). In a traditional system, the same data model serves both reads and writes — the same `Order` object is used for placing an order and for rendering the order history screen. These two operations often have different shapes, different performance requirements, and different consistency requirements.

CQRS separates them explicitly. The write side handles commands (`PlaceOrder`, `CancelOrder`) and maintains data in a normalized, write-optimized form — often with full ACID guarantees. The read side maintains denormalized, read-optimized projections that are derived from the events produced by the write side. The read model for "my order history" might be a denormalized table that joins order, payment, and shipping data, optimized for the specific query pattern of the order history screen.

The read model is eventually consistent: it is updated when events from the write side arrive, which may be milliseconds or seconds after the write. For most read operations — browsing a catalog, viewing order history, searching for products — this delay is imperceptible and acceptable. For operations where you need immediate read-your-writes consistency, you must read from the write model or add explicit coordination.

CQRS enables independent scaling of reads and writes. If your application reads 100x more than it writes, you can deploy many read replicas fed by the event stream without adding write infrastructure. Read models can be stored in whatever technology is best for their access pattern: a relational DB for complex filtered queries, Elasticsearch for full-text search, Redis for low-latency key lookups — all fed from the same event stream.

## Choreography vs Orchestration

When multiple services must collaborate to complete a complex workflow — like processing an order: validate payment, update inventory, generate invoice, send confirmation email — there are two fundamental approaches to coordinating them.

**Choreography** has no central coordinator. Each service knows what to do when it receives a particular event, and it publishes its own events upon completion. The Order Service publishes `OrderPlaced`. The Payment Service consumes `OrderPlaced`, processes payment, and publishes `PaymentProcessed`. The Inventory Service consumes `PaymentProcessed`, updates stock, and publishes `InventoryUpdated`. The workflow emerges from the interaction of independent services reacting to events. There is no single place that has a complete view of the workflow's state.

Choreography is simple to add to: a new service that wants to react to `OrderPlaced` just subscribes to it, with no changes to existing services. It scales well and is resilient — if one service is down, the others continue processing. Its weakness is visibility: when something goes wrong, understanding what happened requires correlating events across multiple services. Complex workflows become hard to reason about; the implicit flow of control is distributed across many service codebases.

**Orchestration** uses a central coordinator (the orchestrator or saga orchestrator) that explicitly directs each step. The orchestrator sends a `ProcessPayment` command to the Payment Service, waits for the response, then sends `UpdateInventory` to the Inventory Service, and so on. The workflow is defined in one place, making it easy to visualize, debug, and modify. When compensation is needed (rolling back a failed workflow), the orchestrator is responsible for issuing compensating commands in reverse order.

The orchestrator becomes a dependency of the entire workflow, which introduces a single point of failure. It also creates coupling: the orchestrator must know about every participating service. AWS Step Functions and Apache Airflow are examples of orchestration platforms.

**The Saga pattern** is the application of choreography or orchestration to long-running distributed transactions. Each step in the saga is a local transaction in one service. If a step fails, compensating transactions undo the effects of previous steps. Sagas are discussed in depth in the Distributed Transactions topic.

## Benefits and Trade-offs

Event-driven architecture's benefits are compelling: loose coupling between services, independent scalability of producers and consumers, natural resilience to partial failures, temporal decoupling (producer and consumer need not be up simultaneously), and built-in audit logging when event sourcing is used.

The trade-offs are equally real. **Eventual consistency** is the default: a write in Service A may not be visible to Service B's consumers for seconds or longer. Applications must be designed to handle this gracefully, and users must understand that "your changes may take a moment to reflect everywhere." **Debugging complexity** increases: tracing a request across a chain of asynchronous events requires distributed tracing tooling and careful correlation ID management. **Event schema evolution** is a constant challenge: changing an event's shape can break consumers, requiring versioning strategies. **Exactly-once delivery** is hard: message brokers typically guarantee at-least-once delivery, meaning your consumers must be idempotent — handling the same event multiple times without causing duplicate effects.

Event-driven architecture is not the right default for every system. It excels when services are maintained by independent teams that need to evolve at different speeds, when workflows are long-running and involve multiple services, and when an audit trail or temporal decoupling is valuable. For simple systems where a direct call is clearer and the coupling is acceptable, the additional complexity of event-driven architecture may not pay off.
