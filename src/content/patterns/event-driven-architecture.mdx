<Callout type="analogy">
Think of a **newspaper**. The reporters who write stories have no idea who
reads them — subscribers, a library, someone lining a birdcage. The paper just
gets **published**, and anyone who cares can pick it up.

That's event-driven architecture. A service **publishes** an event ("an order
was placed") like a headline, and never worries about who reads it. Want a new
subscriber? They just start reading — the newsroom doesn't change a thing.
Compare that to a **phone call** (request/response): you dial a specific person,
wait on the line, and you're stuck if they don't pick up.
</Callout>

## Event-driven vs request-driven

In a **request-driven** (request/response) system, when Service A needs
something from Service B, it **calls B directly and waits**. The call is
synchronous — A is blocked until B answers. This is the natural model for reads
and it's how ordinary REST APIs work. Its weakness is **coupling**: A must know
B's address, B must be up right now, and if B is slow or down, A is stuck.

In an **event-driven** system, services talk through a **message broker**
(Kafka, RabbitMQ, AWS SNS/SQS). When something noteworthy happens — a user
placed an order, a payment cleared, a file was uploaded — the service
**publishes an event** and moves on. Any number of other services can
**subscribe** and react. The publisher never knows who's listening and never
waits for a reply.

That one shift — synchronous calls to asynchronous events — buys a lot:

- **Loose coupling** — A doesn't need to know B, C, and D exist.
- **Extensibility** — add a new consumer of `OrderPlaced` without touching A.
- **Resilience** — if a consumer is down, its events wait in the broker and get
  processed on recovery. Nothing is lost, and the publisher is unaffected.
- **Temporal decoupling** — producer and consumer don't have to be up at the
  same moment.

<Callout type="tip">
The mental test: **would the producer break if a consumer disappeared?** In a
good event-driven design, the answer is no — the Order service publishes
`OrderPlaced` whether or not anyone is listening. The moment a producer starts
caring about a specific consumer's response, you've quietly rebuilt a phone call.
</Callout>

## Events, commands, and queries

Not every message is the same kind of thing. Keeping three straight makes your
system far more coherent.

- **Event** — a record of something that *already happened*: `OrderPlaced`,
  `PaymentProcessed`, `UserRegistered`. Events are **facts**, phrased in the past
  tense. The producer fires them without expecting a reply, and *any* consumer
  may react. Events are the native currency of event-driven systems.
- **Command** — a directive to *do something*: `PlaceOrder`, `SendEmail`,
  `GenerateInvoice`. A command has intent and a **specific target**, usually one
  consumer (point-to-point), and the sender *does* care whether it succeeds.
- **Query** — a request to *read data*. Queries are naturally synchronous and
  don't fit async messaging well; **CQRS** (below) formalizes splitting them out.

The discipline that pays off: **model your events as immutable facts about the
world, not as instructions for what should happen next.** `OrderPlaced` (a fact)
ages well; `TellInventoryToDecrement` (a hidden command) locks you into today's
workflow.

## Event sourcing

Most apps store the **current state**: update your address and the old one is
overwritten; cancel an order and its status flips to `cancelled`. The *history*
of how you got there is gone.

**Event sourcing** flips this. Instead of storing current state, you store the
**sequence of events** that produced it. An order's log might be `OrderCreated`
→ `ItemAdded` → `ItemAdded` → `ShippingAddressUpdated` → `PaymentCaptured` →
`OrderShipped`. Current state isn't stored — it's **derived by replaying** the
events.

That unlocks three things:

- A complete, **immutable audit log** of everything that ever happened —
  priceless for finance, compliance, and "what on earth happened to this order?"
- **Time travel** — replay up to any point to reconstruct a past state.
- **New views for free** — replay the same log through a different projection to
  build a brand-new read model, no data migration required.

<Callout type="tip">
Event sourcing pairs naturally with event-driven architecture: the events you
*store* are the same ones you *publish*. An order service that's event-sourced
emits `OrderPlaced` and `PaymentCaptured` as a byproduct — downstream consumers
just read the log.
</Callout>

The costs are real, though. Reading current state means either replaying the
whole log (slow for long histories) or keeping periodic **snapshots**. Changing
an event's shape over time forces **schema versioning**. And because state is
implicit, debugging is harder. Event sourcing shines for complex, auditable
domains — but it's overkill for simple CRUD, so don't reach for it by default.

## CQRS

**Command Query Responsibility Segregation** means using **separate models for
writing and reading**. In a traditional app, one `Order` object serves both
placing an order and rendering the order-history screen — two jobs with
different shapes, performance needs, and consistency needs jammed together.

CQRS splits them:

- The **write side** handles commands (`PlaceOrder`, `CancelOrder`) in a
  normalized, write-optimized form, often with full ACID guarantees.
- The **read side** keeps denormalized, read-optimized **projections** built
  from the events the write side emits — e.g. an "order history" table that
  pre-joins order, payment, and shipping data for exactly that screen.

The read model is **eventually consistent**: it updates when write-side events
arrive, milliseconds to seconds later. For browsing, history, and search that
lag is invisible and fine. When you need **read-your-writes** consistency, read
from the write model or add explicit coordination.

The payoff is **independent scaling**. If you read 100× more than you write, add
many read replicas fed by the event stream without touching write infrastructure.
Each read model can live in whatever store fits its access pattern — a relational
DB for filtered queries, Elasticsearch for full-text, Redis for hot lookups — all
fed from the same stream.

## Choreography vs orchestration

When several services must cooperate on a workflow — process an order: validate
payment, update inventory, generate invoice, send confirmation — there are two
ways to coordinate them.

**Choreography** has **no central boss**. Each service knows what to do when it
sees an event and publishes its own when done. Order publishes `OrderPlaced`;
Payment consumes it, charges the card, publishes `PaymentProcessed`; Inventory
consumes *that*, decrements stock, publishes `InventoryUpdated`. The workflow
**emerges** from independent services reacting to each other.

- **Strengths** — dead simple to extend (a new service just subscribes), scales
  well, resilient (one service down, the rest keep going).
- **Weakness** — **visibility**. When something breaks, you're correlating
  events across many codebases. There's no single place that knows the whole
  workflow's state.

**Orchestration** uses a **central coordinator** that explicitly drives each
step: send `ProcessPayment`, wait, send `UpdateInventory`, wait, and so on. The
workflow lives in **one place** — easy to visualize, debug, and modify — and the
orchestrator can issue **compensating commands in reverse** to roll back a
failure.

- **Weakness** — the orchestrator is a **single point of failure** and must
  **know about every** participating service (coupling). AWS Step Functions and
  Apache Airflow are orchestration platforms.

The **Saga pattern** applies either style to long-running distributed
transactions: each step is a local transaction, and on failure, **compensating
transactions** undo prior steps. Sagas are covered in depth in Distributed
Transactions.

| | Event notification | Event-carried state transfer | Event sourcing |
|---|---|---|---|
| **What the event contains** | Just "it happened" + an ID | A full copy of the relevant data | Every state change, stored forever |
| **Consumer must call back?** | Yes, to fetch details | No, data is in the event | No, replays the log |
| **Coupling** | Low, but chatty | Lower, but fatter events | Lowest; log is the source of truth |
| **Best for** | Lightweight signals | Avoiding sync calls on the read path | Audit, replay, temporal queries |

## Where this shows up

- **E-commerce order pipelines** → `OrderPlaced` fans out to payment, inventory,
  shipping, email, and analytics — all reacting independently so teams ship on
  their own schedules.
- **Banking & finance** → **event sourcing** gives the immutable ledger
  regulators demand; every balance is derived from an append-only history.
- **Uber / ride-hailing & IoT** → floods of location and sensor events stream
  through brokers to many consumers (matching, pricing, maps, analytics) at once.
- **Notification systems** → one `UserMentioned` event drives push, email, and
  in-app alerts via separate subscribers — the classic **choreography** shape.
- **Read-heavy dashboards & search** → **CQRS** read models (Elasticsearch, Redis)
  are rebuilt from the event stream, scaled apart from the write path.

<Callout type="warning">
The pressure points, and how they bite:

- **Eventual consistency** — a write in A may not show in B's read model for
  seconds. Users see stale data; design the UX around it or read from the write
  model when you truly need read-your-writes.
- **Debugging across async flows** — a request scattered across a chain of events
  has no single stack trace. Without distributed tracing and **correlation IDs**,
  "why didn't this order ship?" becomes a nightmare.
- **Event ordering** — events can arrive out of order across partitions. If
  `PaymentCaptured` lands before `OrderCreated`, consumers misbehave. Partition
  by a key (e.g. order ID) or make consumers order-tolerant.
- **Duplicate events** — brokers give **at-least-once** delivery, so the same
  event *will* arrive twice. Non-idempotent consumers double-charge. "Exactly-once"
  is mostly a myth you engineer around.
</Callout>

## Handling the pressure points

- **Eventual consistency** → set user expectations ("changes may take a moment"),
  and read from the write model for the rare read-your-writes case.
- **Tracing** → propagate a **correlation ID** on every event and adopt
  distributed tracing (OpenTelemetry, Jaeger) so one request is one trace.
- **Ordering** → partition by entity key so all of one order's events stay in
  order; version events so consumers can detect and reorder if needed.
- **Duplicates** → make consumers **idempotent** — dedupe on a unique event ID,
  or use upserts so replaying an event changes nothing.

## Alternatives & related ideas

<Callout type="alternative">
Event-driven isn't the default for everything. When a call is simpler and the
coupling is acceptable, plain **request/response** is clearer — don't add a
broker to avoid one function call.

Within event-driven, the axes to pick along: **choreography vs orchestration**
(emergent-and-resilient vs central-and-visible), **sagas** for long-running
distributed transactions with compensation, and **CQRS** when reads and writes
have genuinely different shapes and scale. **Event sourcing** is a heavier commitment
— take it only when audit and replay earn their keep. Most real systems **blend**
these rather than adopting one wholesale.
</Callout>

## Summary

Event-driven architecture replaces direct calls with **published events** so
producers never know their consumers — buying loose coupling, independent
scaling, and resilience to partial failure. Model events as **immutable past-tense
facts**; layer on **event sourcing** for a replayable audit log and **CQRS** to
scale reads apart from writes. Coordinate multi-service workflows with
**choreography** (simple, resilient, low-visibility) or **orchestration**
(central, debuggable, a single point of failure), and use **sagas** with
compensating transactions for rollbacks. The tax you pay is **eventual
consistency, harder debugging, event ordering, and duplicate delivery** — so
propagate correlation IDs and make every consumer **idempotent**, and skip the
whole thing when a plain request/response would be clearer.
