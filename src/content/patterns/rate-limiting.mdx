<Callout type="analogy">
Think of a nightclub with a bouncer. The club holds a fixed number of people,
and the bouncer's job is to make sure **no single rowdy group takes over the
whole floor**. Some clubs let a group in all at once if there's room (bursty);
others let people in one at a time on a strict cadence (smooth).

**Rate limiting** is that bouncer for your API. Each client gets a quota, and
once they've used it up they wait outside — you send back an **HTTP 429 (Too
Many Requests)** instead of letting them crash the party for everyone else.
</Callout>

## Why rate limiting

Every public endpoint is a target. Without a cap on how often clients can call
you, one misbehaving client — a bug in someone's integration, an aggressive
scraper, or a deliberate **denial-of-service attack** — can eat your whole
server capacity and degrade service for everyone.

Rate limiting puts a ceiling on how many requests a client makes in a time
window. Exceed it and the server rejects further requests (usually **429 Too
Many Requests**) until the window resets. The goal isn't to punish good users —
it's to stop any one client from monopolizing shared infrastructure.

Beyond protection, it also enables:

- **Fair usage** — no single caller starves the rest.
- **Tiered pricing** — free tier gets 100 req/min, paid gets 10,000.
- **Capacity planning** — if every key is capped, you can size infra and offer SLAs.

<Callout type="tip">
Standard limits in the wild: the Twitter/X API historically allowed ~900
requests per 15-minute window per endpoint; GitHub's REST API gives
authenticated clients 5,000 requests/hour. These are per-**client** ceilings,
which is why they key on the API token, not the IP.
</Callout>

## The algorithms

Several algorithms implement rate limiting. They differ mainly in **how they
handle bursts** and **how much memory they cost**.

**Token bucket** is the most widely used. Picture a bucket holding up to
`capacity` tokens. Tokens refill at a fixed rate (say 10/second). Each request
spends one token; if the bucket is empty, the request is rejected. The key
trait: while idle, tokens **accumulate**, so a client can send a burst up to the
bucket's capacity all at once. That's usually *desirable* — real traffic is
bursty, and legitimate clients shouldn't be punished for it. AWS API Gateway and
Stripe use token bucket internally.

**Leaky bucket** takes the opposite tack. Picture a bucket with a hole in the
bottom: requests fill it, and it drains at a fixed constant rate. Overflow gets
dropped. This enforces a **strict, smooth output rate** — no matter how fast
requests arrive, they leave at a steady pace. Great when the backend can't
tolerate bursts, but it smooths out legitimate spikes, which can feel slow.

**Fixed window** is the simplest. Chop time into windows (each minute :00–:59),
keep a counter per client per window, increment on each request, reject over the
limit, reset when the next window starts. Easy to build and reason about — but
it has a nasty **boundary edge case**: a client can send the full quota at the
end of one window and again at the start of the next, briefly **doubling** the
rate (100 req at 12:00:59 + 100 req at 12:01:00 = 200 in two seconds).

**Sliding window log** fixes that by recording the exact **timestamp** of every
request. To check a new one, drop all timestamps older than one window and count
what's left; allow if under the limit. It's **exact** — no boundary bursts — but
**memory-hungry**: one entry per request means the log explodes at high volume.

**Sliding window counter** is the pragmatic middle ground. It blends the current
and previous window's counts, weighted by how far into the current window you
are:

```
current_count + previous_count * (1 - elapsed_fraction_of_current_window)
```

If 40% of the current minute has elapsed, the estimate is the current count plus
60% of the previous window's count. The error is only ~5–10%, and it needs just
**two counters per client** — nearly as cheap as fixed window, without the
boundary bug.

| Algorithm | Bursts | Memory | Output rate | Boundary bug? |
|---|---|---|---|---|
| **Token bucket** | Allows (up to capacity) | Tiny (2 values) | Bursty then throttled | No |
| **Leaky bucket** | Smooths them out | Small (queue) | Strictly constant | No |
| **Fixed window** | Allows 2x at seams | Tiny (1 counter) | Uneven | **Yes** |
| **Sliding window log** | Blocks precisely | Large (per-request) | Even | No |
| **Sliding window counter** | Blocks (approx) | Tiny (2 counters) | Even | No (approx) |

<Callout type="tip">
Rule of thumb: reach for **token bucket** when you want to permit bursts (most
public APIs), **leaky bucket** when a fragile backend needs a steady drip, and
**sliding window counter** when you want fixed-window cheapness without the 2x
boundary leak.
</Callout>

## Where this shows up

- **API gateways (AWS, Kong, Stripe)** → token bucket at the edge, so a rejected
  request never touches a microservice and one config governs all downstream routes.
- **Message/video pipelines feeding a fragile backend** → leaky bucket, because
  the downstream system needs a smooth, predictable rate more than it needs speed.
- **Login / OTP / password-reset endpoints** → tight sliding-window limits per
  account and per IP to blunt brute-force and credential-stuffing attacks.
- **Free vs. paid API tiers** → same algorithm, different quotas keyed on the API
  token, so pricing tiers map directly to rate-limit policies.

## Where to enforce it

The right place for most systems is the **edge** — the **API gateway** or load
balancer that all inbound traffic passes through. Enforcing there means:

- Excess traffic is dropped **before** it consumes any app-layer resources.
- You get **one place** to configure and update policies.
- You don't reimplement limiting logic in every microservice.

Push it into individual services and two problems bite. First, each service only
sees the requests that reach *it*, not the client's total rate — hammer five
endpoints and no single service sees the full picture. Second, you now build,
test, and operate limiter logic everywhere. The advice: **limit once, at the
gateway**, with policies per route or client tier.

<Callout type="tip">
When a client is throttled, hand it the info to back off gracefully. The
conventional headers are `X-RateLimit-Limit`, `X-RateLimit-Remaining`,
`X-RateLimit-Reset` (Unix timestamp of reset), and `Retry-After` (seconds to
wait, sent on 429s). Well-behaved clients read these and back off instead of
hammering you with wasted retries.
</Callout>

## Pressure points

<Callout type="warning">
Rate limiting quietly breaks in distributed setups. Three traps:

- **Per-server counters lie.** Run a fleet with local in-memory counters and a
  client just spreads requests across servers, blowing past the intended limit
  by the server count. You need a **shared store**.
- **Bursty traffic vs. strict smoothing.** Pick leaky bucket and legitimate
  bursts get throttled and feel slow; pick fixed window and bursts leak through
  at window boundaries. Match the algorithm to the traffic shape.
- **Thundering herd at window reset.** With fixed windows, every throttled client
  is told to retry at the *same* reset instant — so they all stampede back at
  once, spiking load the moment the window flips. Randomized **jitter** on
  `Retry-After` spreads them out.
</Callout>

## Handling the pressure points

- **Shared, atomic counters.** Use **Redis** as the shared store. `INCR` +
  `EXPIRE` on a key like `ratelimit:{client}:{window}` gives all servers one
  consistent view. For token bucket, wrap check-and-decrement in a **Lua script**
  so two servers can't both pass the same last token — the update must be *atomic*.
- **Two-tier counters for latency.** Every request now costs a Redis round-trip
  (usually sub-millisecond co-located, but not free). On hot paths, keep a local
  in-memory counter as a first-pass filter and only consult Redis as the client
  nears the limit — far fewer Redis calls, still globally correct where it matters.
- **Jitter the retries.** Add randomness to `Retry-After` so throttled clients
  don't all return at the same tick and re-create the overload.
- **Pick the algorithm for the traffic.** Bursty clients → token bucket; fragile
  backend → leaky bucket; cheap-and-accurate → sliding window counter.

## Alternatives & related ideas

<Callout type="alternative">
Rate limiting isn't the only lever for protecting a system:

- **Load shedding** drops low-priority requests once the server is already
  saturated — a reactive last resort, versus rate limiting's proactive quota.
- **Backpressure** pushes the "slow down" signal upstream through queues so
  producers naturally throttle themselves.
- **Circuit breakers** stop calling a failing downstream entirely, protecting it
  from a retry storm rather than capping per-client rate.
- **Quotas / throttling tiers** cap usage over long horizons (per day/month) for
  billing, layered on top of the short-window rate limits above.

Use rate limiting to enforce *fairness and per-client caps*; reach for these when
the goal is *surviving overload* or *protecting a specific dependency*.
</Callout>

## Summary

Rate limiting caps how fast each client can call you, rejecting the excess with a
**429** so no single caller can starve the rest. **Token bucket** permits bursts
then throttles to a refill rate; **leaky bucket** enforces a strictly smooth
output; **fixed window** is cheap but leaks a 2x burst at boundaries, which
**sliding window** (log or counter) fixes. Enforce it once at the **edge**, and
in a fleet back it with a **shared, atomic store like Redis** — local counters
multiply the real limit by the number of servers. Watch for the thundering herd
at window reset, and add jitter so throttled clients don't all stampede back at
the same instant.
