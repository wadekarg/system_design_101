<Callout type="analogy">
Think of HTTP as ordering at a restaurant counter. You (the **client**) walk up
and place a specific order — "I'll have the #42, no onions" (the **request**).
The kitchen (the **server**) makes it and hands it back with a receipt (the
**response**), and the receipt has a code on it: "Ready," "Out of stock," or
"You didn't pay."

The key twist: the counter has **amnesia**. The moment they hand you your food,
they forget you exist. Come back for a refill and you have to re-introduce
yourself every single time. That forgetfulness feels annoying, but it's exactly
why the restaurant can throw any free cashier at any customer — nobody has to
remember anybody.
</Callout>

## What HTTP is (and why "stateless" matters)

**HTTP** (HyperText Transfer Protocol) is the application-layer language of the
web. Load a page, hit an API, have one microservice call another — HTTP is almost
always in the middle. The shape is simple: the **client sends a request, the
server sends a response.**

The defining trait is that HTTP is **stateless**. Each request stands alone — the
server remembers *nothing* about your previous requests.

- Log in, then load a new page: the server has no built-in idea those two
  requests came from the same person.
- This isn't a flaw — it's the reason HTTP scales. **Any server in a cluster can
  handle any request**, because none of them hold your history.
- State lives in the *application* layer instead: cookies, session tokens, or
  auth headers that the client re-sends on every request.

<Callout type="tip">
This is why load balancers can spray requests across dozens of identical servers
with zero coordination. The "memory" (your session) rides along in a cookie or a
JWT, so it doesn't matter which box answers. Statelessness is the quiet
superpower behind horizontal scaling.
</Callout>

## Request and response structure

An HTTP **request** has three parts:

- **Request line** — the method (`GET`), the path (`/api/users/42`), and the HTTP version.
- **Headers** — key-value metadata: `Host` (which server), `Content-Type` (body
  format), `Authorization` (credentials), and many more.
- **Body** — the actual payload. Common on `POST` and `PUT`, absent on most `GET`s.

An HTTP **response** mirrors it:

- **Status line** — version plus a status code, e.g. `HTTP/1.1 200 OK`.
- **Headers** — content type, cache rules, cookies to set.
- **Body** — the data (HTML, JSON, an image, whatever).

The three-digit **status code** is the headline: it tells the client what
happened before it reads a single byte of the body.

## HTTP methods

Methods (or **verbs**) declare the *intent* of a request. Two properties matter
more than the names:

- **Safe** — read-only, changes nothing on the server.
- **Idempotent** — doing it once or ten times leaves the same end state.

| Method | Purpose | Safe? | Idempotent? | Safe to auto-retry? |
|---|---|---|---|---|
| GET | Read a resource | Yes | Yes | Yes |
| POST | Create / trigger an action | No | No | No (risks duplicates) |
| PUT | Replace a resource fully | No | Yes | Yes |
| PATCH | Partially update fields | No | No* | Usually no |
| DELETE | Remove a resource | No | Yes | Yes |

<Callout type="tip">
These aren't academic. A caching proxy will happily cache a `GET` but must never
cache a `POST`. When a client's connection drops mid-request, it can safely retry
a `GET` or `PUT` — but retrying a `POST` might create **two orders or two
charges**. That's why payment APIs hand out **idempotency keys**: a repeated POST
with the same key is deduped instead of double-charging.
</Callout>

## Status codes

The status code carries structured meaning by its first digit:

- **2xx — Success.** `200 OK` (generic), `201 Created` (new resource, often after
  POST), `204 No Content` (worked, nothing to return).
- **3xx — Redirect.** `301 Moved Permanently` (update your links), `302 Found`
  (temporary).
- **4xx — You (the client) messed up.** `400 Bad Request`, `401 Unauthorized`
  (log in), `403 Forbidden` (logged in, still not allowed), `404 Not Found`.
- **5xx — The server messed up.** `500 Internal Server Error` (catch-all),
  `503 Service Unavailable` (temporarily overloaded or down).

Getting these right is craftsmanship. Return `200` with an error buried in the
body and you force every client to parse the body just to learn it failed. Return
`404` when you meant `403` and you leak whether a resource exists. **Precise
status codes make APIs predictable, cacheable, and debuggable.**

## HTTP/1.1 vs HTTP/2 vs HTTP/3

Each version chips away at the same enemy: **latency and head-of-line blocking.**

| | HTTP/1.1 (1997) | HTTP/2 (2015) | HTTP/3 (2022) |
|---|---|---|---|
| Format | Text | Binary | Binary |
| Transport | TCP | TCP | **QUIC over UDP** |
| Concurrency | One request at a time per connection | **Multiplexed** streams on one connection | Multiplexed streams |
| Head-of-line blocking | Yes (per connection) | Fixed at app level, **still at TCP level** | Fixed per-stream |
| Header compression | No | Yes (HPACK) | Yes (QPACK) |
| Encryption | Optional | Optional (effectively required) | **Mandatory (TLS 1.3)** |

- **HTTP/1.1** makes each request finish before the next one starts on a
  connection — **head-of-line blocking**. Browsers hack around it by opening ~6
  parallel connections per host, but each needs its own TCP handshake. This is why
  the old web leaned on domain sharding and image sprites.
- **HTTP/2** adds **multiplexing**: many requests and responses fly over a
  *single* connection, interleaved. It compresses repeated headers and is binary
  (faster to parse, less human-readable).
- **HTTP/3** swaps TCP for **QUIC** (built on UDP). QUIC merges the connection and
  TLS handshakes into one round trip and handles packet loss *per stream*, so one
  lost packet no longer stalls every other download.

<Callout type="tip">
The HTTP/2-over-TCP flaw is real on flaky networks: because everything shares one
TCP connection, a single dropped packet freezes *all* streams until it's resent.
On a lossy mobile connection, HTTP/3's per-stream loss handling can noticeably cut
stalls — a big reason it took off for video and mobile traffic.
</Callout>

## HTTPS and TLS

**HTTPS** is just HTTP with encryption. The "S" is for Secure, provided by **TLS**
(Transport Layer Security, SSL's modern successor).

- Before any HTTP flows, client and server run a **TLS handshake**.
- The server presents a **certificate** signed by a trusted **Certificate
  Authority (CA)**, proving it's really who it claims to be.
- They negotiate keys and open an **encrypted channel**.

Everything after that — paths, headers, body, response — is encrypted and
unreadable to anyone sniffing the wire. This is no longer optional:

- Browsers flag plain HTTP as **"Not Secure."**
- Search engines rank HTTPS higher.
- Modern browser APIs (geolocation, service workers) **refuse to run** without it.

Inside data centers, service-to-service traffic increasingly uses **mTLS** (mutual
TLS), where *both* sides present certificates so no rogue service can impersonate
another.

## Where this shows up

- **Every web browser** → speaks HTTP/2 or HTTP/3 to load pages with dozens of
  assets over one multiplexed connection instead of six choked HTTP/1.1 pipes.
- **REST APIs** → lean hard on methods and status codes so clients, caches, and
  gateways can reason about requests without reading bodies.
- **Payment systems (Stripe, PayPal)** → use idempotency keys on POST so a
  retried charge never double-bills.
- **CDNs (Cloudflare, Fastly)** → cache `GET`s aggressively using `Cache-Control`
  headers and status codes; they were early HTTP/3 adopters for mobile speed.
- **Service meshes (Istio, Linkerd)** → wrap internal calls in mTLS so every hop
  is encrypted and authenticated.

<Callout type="warning">
The classic outages here are usually **certificates and semantics**, not code:

- **Expired TLS cert** → every client rejects the connection and the whole site
  goes dark. Automate renewal (Let's Encrypt issues 90-day certs on purpose) and
  alert *before* expiry.
- **Retrying a non-idempotent POST** → duplicate orders and double charges. Use
  idempotency keys or make the operation idempotent.
- **Lying with status codes** (200-on-error, 403-vs-404 confusion) → broken
  clients and leaked information. Treat status codes as a contract, not decoration.
</Callout>

## Alternatives & related ideas

<Callout type="alternative">
HTTP's request/response shape isn't the only option. When you need the server to
*push* data or keep a live connection, reach for **WebSockets** (full-duplex,
persistent) or **Server-Sent Events** (one-way streaming over plain HTTP). For
high-throughput internal service calls, **gRPC** rides on HTTP/2 with binary
Protobuf for speed. And **GraphQL** typically runs over HTTP too — it changes the
*shape* of the payload, not the transport underneath.
</Callout>

## Summary

HTTP is the stateless request/response protocol behind the web: the client asks,
the server answers and immediately forgets, which is precisely what lets you throw
any server at any request. **Methods** encode intent (and their safe/idempotent
properties drive caching and retries), while **status codes** form a contract
where 4xx blames the client and 5xx blames the server. The protocol has evolved to
kill latency — HTTP/2 multiplexes over one connection and HTTP/3 (QUIC) fixes the
last TCP-level head-of-line blocking. Wrap it all in **HTTPS/TLS** for encryption
and identity, and never forget that an expired certificate takes the whole site
down.
