## What is HTTP

HTTP, the HyperText Transfer Protocol, is the application-layer protocol that powers the web. Every time a browser loads a page, an app fetches data from an API, or a microservice calls another microservice, HTTP is almost certainly involved. It defines how clients and servers communicate: the client sends a request, the server sends a response. Simple in principle, and rich with detail in practice.

The most important characteristic of HTTP is that it is stateless. Each request is completely independent — the server does not remember anything about previous requests from the same client. If you log into a website and then load a new page, the server has no built-in way to know that these two requests came from the same person. This is not a design flaw; it is a deliberate choice that makes HTTP servers easy to scale horizontally, since any server in a cluster can handle any request. State is managed at the application layer, typically using cookies, session tokens, or other mechanisms that the client sends with every request.

## Request and Response Structure

An HTTP request has three parts: a request line, headers, and an optional body. The request line specifies the method (like GET or POST), the path of the resource (like /api/users/42), and the HTTP version. Headers are key-value pairs that provide metadata: the Host header identifies which server to talk to, Content-Type describes the format of the body, Authorization carries authentication credentials, and dozens of others serve various purposes. The body carries the actual data being sent, and is most common with POST and PUT requests.

An HTTP response mirrors this structure. It starts with a status line containing the HTTP version and a status code (like "HTTP/1.1 200 OK"), followed by response headers, and then the response body. The status code is a three-digit number that immediately tells the client what happened. The response headers describe things like the content type, how long the response should be cached, and any cookies the server wants the client to store.

## HTTP Methods

HTTP defines a set of methods (sometimes called verbs) that indicate the intended action for a request. GET retrieves a resource and should have no side effects — calling it multiple times should return the same result without changing anything. POST creates a new resource or triggers an action; it is not idempotent, meaning calling it multiple times may create multiple resources. PUT replaces a resource entirely; calling it multiple times with the same data is safe because the result is the same each time. PATCH applies a partial update to a resource, changing only the specified fields. DELETE removes a resource.

These semantics matter for caching, proxies, and distributed systems. A caching proxy can safely cache GET responses but must not cache POST responses. A client that loses its connection mid-request can safely retry a GET or PUT, but retrying a POST might cause duplicate orders or double charges. The idempotency guarantees of HTTP methods inform retry logic throughout the stack.

## Status Codes

The three-digit status code in an HTTP response carries a structured meaning. Codes in the 200s indicate success: 200 OK is the generic success, 201 Created indicates that a new resource was created (common with POST requests), and 204 No Content indicates success with nothing to return. Codes in the 300s indicate redirects: 301 Moved Permanently tells the client to update its bookmarks, while 302 Found is a temporary redirect. Codes in the 400s indicate client errors — the request was wrong in some way. 400 Bad Request is a generic client error, 401 Unauthorized means the client needs to authenticate, 403 Forbidden means authentication succeeded but access is denied, and 404 Not Found means the resource does not exist. Codes in the 500s indicate server errors: 500 Internal Server Error is the catch-all for server-side failures, while 503 Service Unavailable indicates the server is temporarily unable to handle requests.

Using status codes correctly is an act of craftsmanship. An API that returns 200 with an error message in the body forces clients to parse every response before knowing if it succeeded. An API that returns 404 when you mean 403 leaks information about resource existence. Getting status codes right makes your APIs predictable and easier to debug.

## HTTP/1.1 vs HTTP/2 vs HTTP/3

HTTP/1.1, standardized in 1997, is a text-based protocol where each request must complete before the next one begins on a given connection — a behavior known as head-of-line blocking. Browsers work around this by opening multiple parallel connections to each server (typically six), but this is wasteful and still limits parallelism. Each new connection requires a TCP handshake, adding latency. Developers spent years using techniques like domain sharding and image sprites to work around these limitations.

HTTP/2, released in 2015, addressed these problems with multiplexing: multiple requests and responses can be in flight simultaneously over a single connection, interleaved at the protocol level. There is no head-of-line blocking between different resources. HTTP/2 also introduced header compression (since headers repeat on every request) and server push, which allows servers to proactively send resources the client will need before the client asks for them. HTTP/2 is binary rather than text-based, making it more efficient to parse but less human-readable.

HTTP/3 takes a more radical approach: it replaces TCP as the transport layer with QUIC, a protocol built on top of UDP. QUIC bakes in encryption (TLS 1.3 is mandatory) and moves connection establishment and TLS handshake to happen simultaneously, reducing the latency of new connections. QUIC also solves a remaining head-of-line blocking issue in HTTP/2: since HTTP/2 runs over a single TCP connection, a lost TCP packet blocks all multiplexed streams. QUIC handles packet loss per-stream, so a lost packet for one resource does not block others.

## HTTPS and TLS

HTTPS is HTTP with encryption. The "S" stands for "Secure," and the encryption is provided by TLS (Transport Layer Security), the modern successor to SSL. When a browser connects to an HTTPS server, they perform a TLS handshake before any HTTP data is exchanged. During this handshake, the server presents a certificate signed by a trusted Certificate Authority (CA), proving that it is actually the entity it claims to be. The client and server then negotiate cryptographic parameters and exchange keys, establishing an encrypted channel.

Everything sent over HTTPS — request paths, headers, body, response data — is encrypted and cannot be read by anyone intercepting the traffic. This is not optional for modern applications: browsers flag HTTP sites as "Not Secure," search engines rank HTTPS pages higher, and many browser APIs (like geolocation and service workers) require HTTPS to function at all. Beyond user-facing applications, service-to-service communication within a data center increasingly uses mutual TLS (mTLS), where both parties present certificates, preventing any unauthorized party from impersonating a service.

The certificate trust model has real implications for system design. Certificates expire (typically every one to two years, though Let's Encrypt issues 90-day certificates) and must be renewed before they do, or every client will reject the connection. Automating certificate renewal is a basic operational requirement for any production system.
