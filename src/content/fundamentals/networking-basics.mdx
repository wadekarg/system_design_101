<Callout type="analogy">
Sending data across the internet is like mailing a letter. The **IP address**
is the street address that tells the postal system where to deliver it. **DNS**
is the phone book that turns "grandma's house" into that street address.

**Ports** are like apartment numbers — one building (IP) holds many tenants
(services), and the port says which door to knock on. And the choice between
**TCP and UDP** is like registered mail versus a postcard: one guarantees
delivery with a signature, the other just drops it in the box and hopes.
</Callout>

## IP Addresses: every device needs one

Every device on a network needs a unique identifier so data can find it. That
identifier is the **IP address**.

The version you'll see most is **IPv4** — four numbers from 0 to 255 separated
by dots, like `192.168.1.1`. IPv4 can address about **4.3 billion** devices, a
number that felt infinite in the 1980s but ran dry once smartphones, IoT
gadgets, and cloud servers exploded.

**IPv6** fixes that exhaustion. It uses 128-bit addresses written in hex — like
`2001:0db8:85a3::8a2e:0370:7334` — with an essentially unlimited supply. Adoption
has been slow, so much of the internet still runs IPv4, often using **NAT**
(Network Address Translation) to let many devices share one public IP.

IP addresses come in two flavors:

- **Public** — globally routable; reachable from anywhere on the internet.
- **Private** — only valid inside a local network (`192.168.x.x` at home,
  `10.x.x.x` in offices). Not routable on the public internet.

When your laptop makes a request, your router rewrites your private IP to its
public IP before the request leaves your home — that's NAT in action.

<Callout type="tip">
As of the mid-2020s, roughly **40–45%** of Google's traffic arrives over IPv6,
yet IPv4 refuses to die. That's why a single public IPv4 address now sells for
**$30–60** on address markets — genuine scarcity for a 40-year-old design.
</Callout>

## DNS — the internet's phone book

IP addresses are great for machines and terrible for humans. Would you rather
type `142.250.80.46` or `google.com`? **DNS** (Domain Name System) maps
human-readable names to IP addresses. It's a globally distributed, hierarchical
database handling **trillions** of lookups a day.

When you type a URL, a **resolution chain** kicks off:

1. **Local cache** — your device checks if it looked this up recently. If so,
   done.
2. **Recursive resolver** — otherwise it asks a resolver (your ISP's, or Google
   `8.8.8.8`, or Cloudflare `1.1.1.1`), which does the legwork.
3. **Root nameserver** — tells the resolver who handles `.com`.
4. **TLD nameserver** — tells it the authoritative server for the domain.
5. **Authoritative nameserver** — returns the actual IP address.

This whole chain usually finishes in **tens of milliseconds**.

Each DNS record carries a **TTL** (Time to Live) — how long resolvers may cache
it before rechecking. It's a trade-off:

- **Low TTL** → you can change IPs fast, but query volume rises.
- **High TTL** → less query load, but changes propagate slowly.

<Callout type="tip">
Before a planned server migration, engineers drop the TTL to **60 seconds** a
day ahead of time. Then when they flip the IP, the old address falls out of
caches within a minute instead of lingering for hours.
</Callout>

## TCP vs UDP: reliable or fast

Once you have an IP, you need a **transport protocol** to actually move data.
The two dominant choices — **TCP** and **UDP** — sit at opposite ends of a
fundamental trade-off.

**TCP** (Transmission Control Protocol) is **connection-oriented** and
guarantees reliable, ordered delivery. It opens with a **three-way handshake**:

- Client sends **SYN**
- Server replies **SYN-ACK**
- Client confirms **ACK**

From there, TCP tracks every packet, waits for acknowledgments, retransmits
anything lost, and reorders packets that arrive out of sequence. That reliability
makes it perfect for web browsing, email, and file transfers.

**UDP** (User Datagram Protocol) throws all that overhead out. No handshake, no
tracking, no reordering — it fires packets and moves on. That sounds reckless,
but for real-time media a **lost packet beats a late one**: if a video frame is
late, you want the *next* frame, not a pause to re-fetch the old one.

| | TCP | UDP |
|---|---|---|
| Connection | Handshake first | None — just send |
| Delivery | Guaranteed | Best-effort |
| Ordering | Reordered for you | Arrives however |
| Speed | Slower (overhead) | Faster (lean) |
| Best for | Web, email, files | Video, gaming, voice, DNS |

<Callout type="tip">
DNS queries ride on **UDP** because a TCP handshake for one tiny question-answer
would be pure overhead. Modern **HTTP/3** even runs web traffic over UDP (via
QUIC) — rebuilding just the reliability it needs, without TCP's rigid ordering
that stalls on a single lost packet.
</Callout>

## Ports: many services, one machine

An IP address finds a **machine**, but one machine runs many services at once.
**Ports** let the OS route traffic to the right one. A port is a 16-bit number
(**0–65535**) tacked onto an IP address. Connecting to a web server means
connecting to port **80** (HTTP) or **443** (HTTPS) at its IP.

Some ports are standardized by convention:

- **80** — HTTP · **443** — HTTPS
- **22** — SSH · **25** — SMTP (email)
- **3306** — MySQL · **5432** — PostgreSQL

Ports below **1024** are reserved for system services and need elevated
privileges to bind. App developers use ports above that — like `3000` or `8080`
for a local dev server.

## Where this shows up in real systems

- **CDNs (Cloudflare, Akamai)** → lean on **DNS** to steer you to the nearest
  edge server. The same domain resolves to different IPs depending on where you
  are, cutting latency.
- **Video calls & streaming (Zoom, Netflix live, Twitch)** → **UDP**-based
  transports, because smooth playback beats perfect delivery.
- **Databases & internal APIs** → fixed, well-known **ports** so services find
  each other reliably in microservice networks.
- **Cloud VPCs (AWS, GCP)** → carve out **private IP** ranges (`10.x.x.x`) so
  instances talk internally without exposing themselves to the public internet.
- **Load balancers** → route by **port and IP**, sending port 443 traffic to
  your web tier and port 5432 to your database tier.

<Callout type="warning">
The classic trap is a **port or firewall mismatch**. A service listens on port A
while clients connect to port B, or a firewall silently blocks the port — and
you get mysterious timeouts that "work on my machine." Always confirm both sides
agree on the port, and remember that a blocked port fails *silently*, unlike a
wrong IP which usually errors fast.

DNS has its own trap: **stale caches**. You change an IP, but users keep hitting
the old server for hours because a high TTL froze the record in caches. Lower the
TTL *before* the change, not after.
</Callout>

## How a request travels the internet

Type `https://github.com` and hit Enter, and a chain of systems springs to life:

1. **DNS lookup** — your browser checks its cache, then walks the DNS hierarchy,
   returning an IP like `140.82.114.4`.
2. **TCP connection** — your browser opens a connection to port **443**,
   traveling through your router, your ISP, and a dozen backbone routers to
   GitHub's servers.
3. **TLS handshake** — because it's HTTPS, an encrypted channel is negotiated on
   top of the TCP connection.
4. **HTTP request** — *only now* does your browser send the actual **GET**
   request. The response travels back the same path, reassembled in order by TCP.

For servers in the same country this usually finishes in **100–500 ms**; across
continents it can top a second. Every layer — DNS, TCP, TLS, HTTP — adds to the
total, which is why engineers optimize each one separately.

## Alternatives & related ideas

<Callout type="alternative">
When the raw network layer isn't enough, you build on top of it:
**HTTP/2 and HTTP/3** multiplex many requests over one connection to dodge
handshake and head-of-line costs; **WebSockets** keep a single TCP connection
open for two-way real-time messaging instead of re-opening one per request; and
**anycast** advertises the same IP from many locations so packets flow to the
nearest datacenter automatically. Each one hides networking pain rather than
changing the physics underneath.
</Callout>

## Summary

Networking starts with **IP addresses** (the destination), which **DNS**
resolves from human-friendly names, and **ports** that pick the right service on
a machine. Data then moves over **TCP** (reliable and ordered, for web and files)
or **UDP** (fast and lossy, for real-time media). A single request quietly chains
DNS → TCP → TLS → HTTP, and every hop adds latency. Master these four pieces and
most "why can't it connect?" mysteries — stale DNS, blocked ports, wrong protocol
— stop being mysteries.
