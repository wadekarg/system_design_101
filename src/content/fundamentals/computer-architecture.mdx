<Callout type="analogy">
Think of a chef working at a kitchen counter. The **CPU** is the chef —
fast hands, but only two of them. What's *within arm's reach* on the counter
(**cache**) they grab instantly. Ingredients in the **fridge** across the
kitchen (**RAM**) take a walk to fetch. And anything in the **basement
storage** (**disk**) means trudging down the stairs.

The chef's hands aren't the problem — the *walking* is. A world-class chef who
spends all day running to the basement cooks slowly. Great system design, like
a well-run kitchen, is mostly about keeping what you need close by.
</Callout>

## What computer architecture actually is

Computer architecture is how a computer's core parts — the **processor**,
**memory**, and **storage** — are organized and how they talk to each other.

For most engineers it feels like a college course you happily forgot. But once
you're serving millions of requests a day, the physical limits of hardware
become the ceiling on everything you can do.

Here's the key idea: every caching strategy, every database index, every
in-memory-vs-disk decision traces back to one question — *why is this operation
fast and that one slow?* Answer it, and system design stops being guesswork.

## The CPU: fast hands, always waiting

The **CPU** (Central Processing Unit) is the brain. It fetches an instruction,
decodes it, executes it, and writes the result back — billions of times per
second. A 3 GHz chip runs three billion cycles per second.

That sounds impossibly fast, and in isolation it is. The catch: **the CPU spends
most of its time waiting for data to arrive from memory.**

- **Cores** — each core executes instructions independently. A quad-core CPU
  runs four threads at once.
- **Hyperthreading** — lets one physical core look like two logical cores to
  the OS. The payoff depends heavily on the workload.
- **What matters for design** — CPU-bound work scales by adding cores.
  Memory-bound and I/O-bound work hit *different* walls entirely.

## The memory hierarchy: a stack of speed vs. size trade-offs

The gap between how fast the CPU thinks and how fast memory delivers is huge.
To bridge it, computers stack several memory types — each one bigger but slower
than the one above it.

- **L1 cache** — on the CPU die, ~1 ns, tiny (32–64 KB per core).
- **L2 cache** — a few MB, ~4 ns.
- **L3 cache** — shared across cores, tens of MB, ~10–40 ns.
- **RAM (main memory)** — 32 GB to terabytes, ~100 ns, **volatile** (gone when
  power drops).

The three cache levels use **SRAM** — blazing fast but expensive and
power-hungry. RAM uses **DRAM** — cheaper and larger, but ~100x slower than L1.

| Layer | Typical size | Access time | Volatile? | Cost per GB |
|---|---|---|---|---|
| L1 cache | 32–64 KB/core | ~1 ns | Yes | Very high |
| L2 cache | a few MB | ~4 ns | Yes | High |
| L3 cache | tens of MB | ~10–40 ns | Yes | High |
| RAM (DRAM) | 32 GB–TBs | ~100 ns | Yes | Medium |
| SSD | TBs | ~100 µs | No | Low |
| HDD | TBs | ~10 ms | No | Very low |

<Callout type="tip">
When engineers say "in-memory" databases like **Redis**, they mean the RAM
layer: fast (~100 ns), but not durable on its own. Pull the power and it's gone
— which is why Redis also writes snapshots and logs to disk in the background.
</Callout>

Caches work because programs show **locality of reference** — they reuse the
same data and touch nearby addresses. The cache hardware exploits this for free.

Access memory in **sequential** order and you ride the cache efficiently. Scatter
your accesses **randomly** and you cause **cache misses** — the CPU stalls,
waiting ~100 ns for RAM, over and over.

## Storage: durable but slow

Below RAM sits **persistent storage** — data that survives a power loss, at the
cost of much slower access.

- **SSDs** (solid-state, no moving parts) — ~100 µs random access, roughly
  **1,000x slower than RAM**.
- **HDDs** (spinning platters, mechanical heads) — ~10 ms random access, another
  **100x slower than SSDs**, and ~100,000x slower than RAM.

Modern SSDs sustain **several GB/s sequential** throughput, so they're great for
streaming big datasets. But **random** access — small reads from unpredictable
spots — exposes their real latency.

<Callout type="tip">
The design rule of thumb: need it **fast**? Keep it in memory. Need it
**durable**? Write it to disk. Need **both**? Use a **write-ahead log** on disk
paired with an **in-memory cache** — this is exactly how Postgres, Kafka, and
most databases get speed and safety at once.
</Callout>

## Where this shows up in real systems

- **Redis / Memcached** → keep hot data in RAM to dodge the ~1,000x SSD penalty.
  The whole product *is* the memory hierarchy turned into a service.
- **Kafka** → writes sequentially to disk on purpose. Sequential SSD/HDD writes
  are fast; it turns the slow layer into a fast one by never seeking randomly.
- **Column-oriented analytics DBs (ClickHouse, BigQuery)** → lay data out for
  sequential scans and cache locality, so the CPU rarely stalls on a miss.
- **Video streaming / CDNs** → large sequential reads play to SSD strengths;
  they cache popular files close to users to avoid the slow disk *and* network.
- **High-frequency trading** → obsess over cache locality and avoid a single
  RAM stall, because ~100 ns actually decides who wins the trade.

## When it breaks: the pressure points

<Callout type="warning">
The classic trap is **micro-optimizing CPU code when the real cost is I/O**. A
"slow" algorithm is almost always dwarfed by one unnecessary disk read or
network hop — the CPU is idle, waiting.

Diagnose the resource that's actually saturated: **CPU** (compute pegged),
**memory** (cache misses / RAM bandwidth), or **I/O** (disk or network). Fixing
the wrong one wastes effort — and worse, adding threads to an I/O-bound service
can make it *slower* by piling on contention.
</Callout>

## Handling the pressure points

- **CPU-bound?** → scale horizontally (more servers), parallelize across cores,
  or use a better algorithm to cut raw work.
- **Memory-bound?** → improve **cache locality** (sequential access, compact
  data layouts) and keep hot data close to the processor.
- **I/O-bound?** → add **caching**, **batch** writes, or move to a faster storage
  tier (HDD → SSD → RAM). Eliminating I/O beats speeding it up.

## Alternatives & related ideas

<Callout type="alternative">
When one machine can't keep up, you choose how to grow. **Vertical scaling**
(a bigger CPU, more RAM, faster disks) is simple but capped by the best hardware
money can buy. **Horizontal scaling** (spread work across many servers) can grow
almost forever, but adds coordination, consistency, and failure-handling
complexity.

Related hardware escapes hatches: **GPUs / TPUs** for massively parallel math,
**NVMe / persistent memory** to shrink the RAM-to-disk gap, and **NUMA-aware**
scheduling so cores read from the memory bank physically nearest them.
</Callout>

## Summary

Computer architecture is a hierarchy of trade-offs: each layer from L1 cache to
RAM to SSD to HDD is larger and cheaper but dramatically slower than the one
above it. The CPU is rarely the real limit — it spends most of its time waiting,
so keeping the data it needs *close* (cache locality, in-memory storage) is where
the wins live. When a system is slow, find whether it's **CPU-, memory-, or
I/O-bound** and fix that specific resource. Internalize the numbers — RAM is
~1,000x faster than an SSD — and caching stops feeling like magic and starts
feeling inevitable.
