<Callout type="analogy">
Picture a highway. **Latency** is how long *your* car takes to drive from
one end to the other. **Throughput** is how many cars get through per minute.

Adding lanes (throughput) doesn't make any single car faster. And a 200 mph
sports car (low latency) is useless if only one lane is open and traffic is
bumper-to-bumper. They're different problems with different fixes — confusing
them is the #1 reason performance work goes sideways.
</Callout>

## Latency: the time for one thing

Latency is how long a single operation takes, measured from the moment you ask
to the moment you get an answer. Click a button and wait for the page — that
wait is latency. An API that responds in 50 ms has 50 ms of latency. It's
always a *per-operation* measurement.

It has two parts:

- **Propagation delay** — time for the signal to physically travel. This is
  capped by the speed of light and you cannot beat it. A round trip from New
  York to London is ~70 ms *from physics alone*, no matter how fast your servers are.
- **Processing delay** — time spent actually computing the answer. This you
  *can* shrink: faster code, better algorithms, caching.

<Callout type="tip">
That physics floor is why global apps put servers close to users (edge / CDNs).
You can't make London→Sydney faster — so you move the data to Sydney instead.
</Callout>

## Throughput: how much you can handle

Throughput is how many operations you finish per unit of time — usually
requests per second (RPS). If latency is one car's journey, throughput is the
*capacity of the whole highway*. A server doing 10,000 RPS has far more
throughput than one doing 100, regardless of how fast any single request is.

Throughput is capped by your **slowest resource — the bottleneck**. If your
database maxes out at 5,000 queries/second, no amount of tuning elsewhere pushes
the system past that. And bottlenecks move: fix the CPU and the database becomes
the limit; add read replicas and the network becomes the limit. Performance work
is a game of whack-a-mole — always chase the *current* bottleneck.

## Why they fight each other

Here's the part that trips people up: **improving one often hurts the other.**

The classic example is **batching**. Bundle ten database writes into one
transaction and throughput jumps — you're doing 10× the work per round trip.
But each write now waits for the batch to fill, so its latency goes up. You
traded snappy responses for bulk efficiency.

The same shape shows up everywhere:

| Technique | Throughput | Latency |
|---|---|---|
| Batching writes | ⬆ higher | ⬇ worse |
| Queue in front of a service | ⬆ higher (absorbs spikes) | ⬇ worse (requests wait) |
| Connection pooling | ⬆ higher (no exhaustion) | ⬇ worse when pool is full |
| Caching | — | ⬆ better |

<Callout type="warning">
The trap: optimizing the wrong metric. A system that's **slow under light load**
has a *latency* problem — batching and queuing will make it *worse*. A system
that **falls over under heavy load** has a *throughput* problem — shaving
milliseconds off one request won't save it. **Diagnose which one you have before
you touch anything.**
</Callout>

## Where this shows up in real systems

- **Payment / checkout** → latency-critical. Users abandon carts when it's slow;
  you optimize the single-request path even if it costs some throughput.
- **Analytics / log ingestion / ETL** → throughput-critical. Nobody watches a
  single event; you batch aggressively and happily add latency for volume.
- **Live chat, gaming, video calls** → latency-critical *and* tail-sensitive; a
  laggy p99 ruins the experience even if the average is fine.
- **Bulk email / report generation / backups** → throughput-critical; run them
  async and let each item take as long as it needs.

## Numbers worth memorizing

Internalizing orders of magnitude changes how you reason. Roughly:

- L1 cache: ~1 ns · Main memory (RAM): ~100 ns
- SSD random read: ~100 µs (1,000× slower than RAM)
- Datacenter round trip: ~0.5 ms · Cross-US: ~40–70 ms · Cross-continent: ~100–200 ms

<Callout type="tip">
The message: **your code probably isn't the problem.** A slightly slow algorithm
is dwarfed by a single unnecessary disk read or network hop. The biggest wins
come from *eliminating I/O*, not micro-optimizing CPU cycles.
</Callout>

## Measuring it right: percentiles, not averages

An average hides the distribution. If 99% of requests finish in 10 ms but 1%
take 10 seconds, the average still looks okay — while thousands of real users
are staring at a spinner. Use percentiles:

- **p50** (median) — half of requests are faster than this.
- **p99** — only 1% are slower. *This* is what user-facing systems live by.
- **p999** — the 99.9th percentile, for systems where even rare slowness is costly.

And tail latency **compounds** with fan-out. One service with a p99 of 100 ms is
slow 1% of the time. Build a response from 10 such services and the odds that at
least one is slow climb to ~10%. That's why reducing the number of calls on the
critical path is one of the highest-leverage things you can do.

## Handling the pressure points

- **Slow p99 but fine average?** → attack the tail: add caching, timeouts +
  retries with backoff, and hedge requests (send to two replicas, take the first).
- **Throughput ceiling?** → scale horizontally, process async, batch, and pool
  connections. Then find the *next* bottleneck.
- **Fan-out amplifying the tail?** → cut the number of downstream calls, fetch in
  parallel instead of serially, and set aggressive per-call timeouts.

## Alternatives & related ideas

<Callout type="alternative">
When you can't lower true latency, you often change what the user *perceives*:
**async processing** (accept now, do the work in the background),
**optimistic UI** (show the result before the server confirms), and
**streaming / pagination** (deliver the first bytes fast instead of the whole
payload at once). None reduce the actual number — they hide it well.
</Callout>

## Summary

Latency is the time for **one** request; throughput is **how many** per second.
They pull in opposite directions — batching, queuing, and pooling buy throughput
at the cost of latency, while caching buys latency back. Figure out which metric
your system is actually failing on, measure it with **p99 (not averages)**, and
remember that tail latency compounds every time you add a hop. Optimize the
bottleneck you have, not the one that's easy to see.
