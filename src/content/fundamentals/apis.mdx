<Callout type="analogy">
Think of an API as a **restaurant menu**. You don't walk into the kitchen and
cook — you point at an item, the kitchen does the work, and a finished plate
comes back. The menu is a **contract**: it lists what you can order, what you
must specify ("no onions"), and what arrives.

Your weather app doesn't predict the weather — it "orders" a forecast from the
National Weather Service API. Your checkout form doesn't move money — it orders
a charge from Stripe. Every boundary between services is bridged by a menu like this.
</Callout>

## What an API really is

An **API** (Application Programming Interface) is a contract between a **client**
(the one asking) and a **server** (the one doing the work). It defines three things:

- What operations are available
- What you must send
- What you'll get back

The word **contract** matters. A good API is **stable and predictable**. Clients
build on top of it, so a breaking change forces every consumer to scramble.

That makes API design an *organizational* decision, not just a technical one.
The URL shapes, data formats, and error codes you pick today will constrain how
your system evolves for years.

<Callout type="tip">
Treat breaking changes with the same gravity as a database migration. The usual
escape hatch is **versioning** — put `/v1/` and `/v2/` in the path (or a version
header) so old clients keep working while new ones move forward.
</Callout>

## REST — the default

**REST** (Representational State Transfer) is the dominant style on the web. It
maps operations onto HTTP methods and organizes everything around **resources**
identified by URLs.

For a blog:

- `GET /articles` — list articles
- `GET /articles/42` — fetch one article
- `POST /articles` — create one
- `DELETE /articles/42` — remove one

Because HTTP is **stateless** — each request carries everything the server needs —
REST scales horizontally with ease. Responses are usually **JSON**: readable and
supported everywhere.

A couple of properties worth knowing:

- **Idempotency** — calling it repeatedly has the same effect as calling once.
  `GET` and `DELETE` are naturally idempotent; design `PUT` to be too.
- **Status codes** — `200` OK, `201` Created, `400` bad request, `404` not found,
  `500` server error. Used well, they make responses self-explanatory.

REST's main weakness is **overfetching and underfetching**. Each endpoint returns
a *fixed* shape. A mobile client that wants only a title and thumbnail still
downloads the full body, author bio, and comments (**overfetching**). And a page
needing three resources must make three round trips (**underfetching**).

## GraphQL — clients pick the fields

**GraphQL** came out of Facebook (built 2012, open-sourced 2015) as a direct
answer to REST's fetching problem. Instead of many endpoints with fixed shapes,
it exposes **one endpoint** where the client sends a query describing *exactly*
the fields it wants.

- Mobile asks for `title` and `thumbnail`.
- Desktop asks for the full article plus comments.
- Both hit the same endpoint; each gets precisely what it asked for.

This shines when **many clients have different needs** — mobile, web, and
third-party integrations — without you building a custom endpoint for each.

But GraphQL adds real complexity:

- **The N+1 problem** — query 100 articles, each with an `author`, and a naive
  server runs 1 query for the list plus 100 more for authors. **DataLoader**
  batches these, but you must wire it up deliberately.
- **Harder caching** — queries are `POST` bodies to one URL, so plain HTTP caches
  can't tell responses apart the way they can with distinct REST URLs.

## gRPC — calling a function on another machine

**gRPC** is a high-performance **RPC** (Remote Procedure Call) framework from
Google. Instead of "send an HTTP request, get JSON," it feels like *calling a
function* that happens to run on another server.

You define your service in a `.proto` file using **Protocol Buffers** (a compact
binary format), and the toolchain generates client and server code in your language.

Why it's fast:

- Binary encoding is smaller and quicker to serialize than JSON.
- It runs on **HTTP/2** with multiplexing and streaming.

It supports four call patterns: **unary** (one request, one response — like REST),
**server streaming**, **client streaming**, and **bidirectional streaming** — great
for live ingestion and long-running operations.

The catch: gRPC is awkward for *public* APIs. Browsers need a proxy layer
(**gRPC-Web**), the binary format is hard to poke at without tooling, and changing
the contract means regenerating and redeploying client stubs. Fine inside one org;
painful for external consumers.

## WebSockets — the server can talk first

Plain HTTP is **request-response**: the client asks, the server answers. The server
can't push data on its own. For **live chat, collaborative editing, sports scores,
or stock tickers**, that's a dealbreaker.

**WebSockets** fix it with a **persistent, bidirectional** connection. It starts as
a normal HTTP request carrying an `Upgrade` header; the server replies `101
Switching Protocols`, and the connection becomes a **full-duplex** channel. After
that, *either side* can send a message anytime.

- Great for **high-frequency, small messages** where per-request HTTP headers would
  dominate.
- No per-message connection setup cost.
- But it's **stateful** — the server holds the connection open, which complicates
  horizontal scaling (the same connection must reach the same server, or state
  lives in an external store like Redis).

<Callout type="tip">
Need only *server-to-client* updates (a notification feed, a progress bar)?
**Server-Sent Events (SSE)** run over plain HTTP, auto-reconnect, and are far
simpler than WebSockets. Reach for full WebSockets only when you truly need
*both* directions.
</Callout>

## Comparing the four styles

| Style | Transport | Payload | Best for | Weak spot |
|---|---|---|---|---|
| **REST** | HTTP/1.1 | JSON | Public APIs, most web apps | Over/underfetching |
| **GraphQL** | HTTP (usually POST) | JSON | Many clients, varied data needs | N+1, hard to HTTP-cache |
| **gRPC** | HTTP/2 | Protocol Buffers (binary) | Internal microservices, high throughput | No native browser support |
| **WebSockets** | TCP (after HTTP upgrade) | Any (text/binary) | Real-time, two-way messaging | Stateful, scaling complexity |

## Where this shows up

- **Stripe, Twilio, GitHub public APIs** → **REST**. Millions of unknown developers
  in every language; simplicity, cacheability, and easy exploration win.
- **Facebook / GitHub GraphQL API** → **GraphQL**. One News Feed powering many
  platforms, each needing a different slice of data from a single API layer.
- **Google, Netflix internal traffic** → **gRPC**. Tens of thousands of services
  talking to each other where throughput and low overhead matter and both sides
  ship code together.
- **Slack, Figma, trading dashboards** → **WebSockets**. Presence, live cursors,
  and price ticks need the server to push instantly, both directions.

<Callout type="warning">
The classic trap: **breaking the contract without anyone noticing.** Renaming a
field, tightening a validation rule, or removing an endpoint can crash live clients
you don't even know exist. Add fields, never remove or rename in place; version the
API (`/v1`, `/v2`); and for GraphQL, guard against the **N+1 explosion** with
DataLoader before it turns one request into thousands of database queries.
</Callout>

## Handling the pressure points

- **Evolving safely?** → additive changes only, explicit versioning, and a
  deprecation window before you retire anything.
- **GraphQL blowing up your database?** → batch with DataLoader, cap query depth
  and complexity, and add persisted queries.
- **WebSockets hard to scale?** → move connection state to an external store (Redis
  pub/sub) so any server can handle any client, and fall back to SSE when one-way is enough.

## Alternatives & related ideas

<Callout type="alternative">
The styles aren't mutually exclusive — big systems mix them. A company often exposes
a **public REST API** for outsiders, powers its own apps with **GraphQL**, wires
backend services together over **gRPC**, and pushes live updates via **WebSockets**.
Other options in the family: **webhooks** (the server calls *you* when an event
happens — great for async notifications), **SSE** for one-way streams, and
**long polling** as a WebSocket fallback where persistent connections aren't allowed.
</Callout>

## Summary

An API is a **contract** between a client and a server, and the style you choose
shapes how your system evolves. **REST** is the simple, cacheable default for public
APIs; **GraphQL** lets varied clients fetch exactly the fields they need; **gRPC**
delivers binary, HTTP/2 speed for internal microservices; and **WebSockets** enable
true real-time, two-way communication. Match the style to the problem — and once
clients depend on your contract, change it as carefully as a database migration.
