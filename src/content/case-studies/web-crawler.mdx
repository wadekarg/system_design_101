<Callout type="analogy">
Think of crawling the web like **exploring an endless maze with a huge team of scouts**. Every room (page) has doors (links) to more rooms, and you don't know how big the maze is — it might be infinite.

To do this well you need three things: a **to-do list of doors to try next** (the URL Frontier), a rule that says **"don't knock on the same house 100 times a second"** (politeness), and a **memory of rooms you've already visited** so you don't walk in circles forever (deduplication). Get those three right and the rest is plumbing.
</Callout>

## Requirements

Before designing any component, clarify what the crawler must do and what constraints it must respect.

**Functional requirements:**
- Accept a seed list of URLs and discover new links recursively.
- Download and store HTML content of crawled pages for downstream indexing.
- Respect the `robots.txt` exclusion standard for every domain.
- Avoid crawling the same URL twice within a crawl cycle.
- Detect near-duplicate content to avoid storing redundant pages.

**Non-functional requirements:**
- **Scale**: crawl 1 billion web pages. Average page size 10 MB (HTML + metadata).
- **Politeness**: no more than 1 request per second per domain to avoid overloading servers.
- **Freshness**: the crawler should re-visit pages periodically to detect updates.
- **Extensibility**: pluggable content parsers — HTML today, PDFs tomorrow.
- **Fault tolerance**: workers crash; the system must resume without losing progress or recrawling excessively.

The hardest design challenges are *not* the networking. They are the **URL Frontier** (what to crawl next and when) and the **deduplication pipeline** (avoiding redundant work at petabyte scale).

## Components

A production web crawler is a **pipeline of cooperating services**, not a single loop:

- **URL Frontier** — the central scheduler. A priority queue that decides which URL to crawl next, balancing **freshness priority** (high-PageRank pages crawled more often) against **politeness** (never flooding one domain).
- **Fetcher** — a pool of HTTP workers. Each pulls a URL, issues an HTTP GET, follows redirects (bounded, to prevent loops), and hands the raw HTML to the Parser.
- **Parser** — extracts two things from the HTML: (1) the page's **text content** and (2) all anchor `href` **links**. Content goes to the Content Store; links are normalized and sent to the Dedup Filter before entering the Frontier.
- **Dedup Filter** — two jobs: **URL dedup** (have we scheduled this URL before?) and **content dedup** (have we already stored effectively the same page?). Both run *before* writing to storage to avoid wasted I/O.
- **Content Store** — raw HTML goes to object storage (S3); metadata (URL, timestamp, status, hashes, links) goes to a distributed database (Cassandra) for the indexing pipeline.

<Callout type="tip">
**In practice:** the pipeline maps cleanly onto a stream: Frontier → Fetcher → Parser → Dedup → Storage. Each stage can be a Kafka consumer group reading one topic and producing to the next. That decoupling lets you scale stages independently and resume from the last offset when a stage crashes — no lost work.
</Callout>

## URL Frontier

The URL Frontier is the most architecturally interesting component. A naive FIFO queue crawls URLs in discovery order — so a single domain that links internally to thousands of its own pages can **flood the queue**, violating politeness and burning capacity on one site.

A production Frontier uses a **two-level queue design**:

**Front queues** are priority queues, one per priority level. Priority is assigned by:
- **PageRank estimate** — high-authority pages crawled more frequently.
- **Recency** — pages that change often (news, feeds) get higher re-crawl priority.
- **Depth** — seed URLs and early discoveries outrank deep internal links.

**Back queues** are **per-domain FIFO queues** — one for `en.wikipedia.org`, one for `github.com`, and so on. A URL leaves the front queue and enters its domain's back queue. Each back queue has a **timer**: a worker only pulls the next URL for that domain once the crawl delay has elapsed.

This split is the key insight: it **decouples priority from politeness**. You can rank URLs however you like in the front queues, while the back queues independently guarantee domain-level rate limiting.

<Callout type="tip">
**In practice:** Frontier state lives in **Redis** (active back queues + domain timers) for millions of scheduling lookups per second, backed by a durable store (Cassandra or Kafka) that survives worker crashes. In-memory speed for scheduling; durability for recovery.
</Callout>

<Callout type="warning">
**The pressure point — crawler traps.** Some sites generate infinite URLs on the fly: calendars with a "next month" link forever, faceted search with endless filter combinations, or session IDs baked into every link (`?sid=abc123`). A depth-first crawler can fall in and never climb out, endlessly fetching one domain.

Defend with **crawl-depth limits per domain**, **per-domain URL budgets** (cap how many pages you'll take from any single site), aggressive **URL normalization** (strip session IDs and volatile params), and pattern detection for exploding query-string spaces. The per-domain back queue helps too — it caps the *rate* even when the trap can't cap the *count*.
</Callout>

## Politeness & Crawl Delay

Politeness is **not optional** — it is what separates a responsible crawler from one that gets IP-banned and knocks sites over.

- **robots.txt compliance** — before crawling a domain for the first time, fetch `https://domain.com/robots.txt`. It declares which paths are off-limits. Cache it per domain (re-fetch daily) and check every URL against it before enqueuing; drop matches.
- **Crawl delay** — many `robots.txt` files set a `Crawl-delay` directive (minimum seconds between requests). If unspecified, default to **1 second**. The back-queue timer enforces it: `next_allowed = last_crawl_time + crawl_delay`.
- **Redirect depth limits** — cap redirect chains at ~5 hops to break loops (`A → B → A`).
- **DNS caching** — cache DNS lookups per domain with a short TTL (a few minutes); resolving per URL hammers DNS servers.
- **User-Agent header** — identify the crawler honestly (e.g. `MySearchBot/1.0 (+https://myengine.com/bot)`) so sites can allow or deny it in `robots.txt`.

<Callout type="tip">
**In practice:** at **1 request/second/domain**, a single domain yields at most ~86,400 pages/day from one crawler. That's why throughput comes from **breadth** — crawling thousands of domains in parallel — not from hitting any one site harder. Politeness and scale aren't in conflict; they're solved on different axes.
</Callout>

## Duplicate Detection

Deduplication has two dimensions — **URL-level** and **content-level** — and they solve different problems.

### URL deduplication: "have we seen this exact URL?"

Without it, a page linking to itself in a nav menu would cause infinite re-crawling. The challenge is scale. A naive hash set at 1 billion URLs needs:

```
1B URLs × 8 bytes/hash = 8 GB RAM
```

Borderline on one machine, painful when distributed. The standard fix is a **Bloom filter** — a space-efficient probabilistic structure that answers "**definitely not seen**" or "**probably seen**." It has **no false negatives** (if it says new, it's new) but can have false positives. At a 1% false-positive rate, 1 billion URLs fit in about **1.14 GB** — nearly 7× smaller than the hash set. Occasionally skipping a genuinely new URL is a fine price for that memory.

**URL normalization runs before the Bloom filter check**, converting equivalent URLs to one canonical form:

| Rule | Before | After |
|---|---|---|
| Lowercase scheme + host | `HTTP://Example.com` | `http://example.com` |
| Remove default port | `http://example.com:80/` | `http://example.com/` |
| Sort query params | `?b=2&a=1` | `?a=1&b=2` |
| Drop fragments | `page#section` | `page` |

### Content deduplication: "is this page basically one we already stored?"

Even if the URL is new, mirrors, scrapers, and syndicated articles create massive content redundancy. Storing exact copies wastes disk and pollutes the index.

- **Exact duplicates** — compute a fast hash (MD5/SHA-1) of the page body; skip pages whose hash already exists.
- **Near-duplicates** — use **SimHash**. It produces a 64-bit fingerprint such that two 90%-similar documents differ in only a **few bits**. Comparing **Hamming distances** flags pages that are essentially the same even when they differ by a few ads or nav links.

<Callout type="warning">
**The pressure point — dedup at scale.** A Bloom filter's false-positive rate **climbs as it fills**; sized for 1B URLs, it degrades once you blow past that, silently dropping real pages. And a single global filter becomes a coordination bottleneck across distributed workers.

Handle it by **partitioning the filter by domain-hash** (each worker owns its shard — see Scaling), **sizing generously** for expected growth, and using a **rotating/scalable Bloom filter** you can grow or reset per crawl cycle. For content SimHash, don't compare every fingerprint to every other (that's O(n²)) — **bucket by bit-blocks (LSH)** so you only compare candidates likely to be close.
</Callout>

## Storage

At 1 billion pages with 10 MB average size:

```
Raw storage = 1B × 10 MB = 10 PB
```

10 petabytes of raw HTML doesn't go in a relational database. The architecture **separates concerns**:

**Object storage (S3 or GCS)** holds raw HTML, keyed by URL hash (e.g. `s3://crawl-store/2024/01/15/{url_hash}.html.gz`). Pages are gzip-compressed (~10× for HTML), cutting effective storage to roughly **1 PB**. S3 is built for this: massively parallel writes, cheap, schemaless.

**Cassandra** holds per-URL metadata:

```sql
CREATE TABLE crawl_metadata (
  url_hash   TEXT PRIMARY KEY,
  url        TEXT,
  crawled_at TIMESTAMP,
  http_status INT,
  content_hash TEXT,
  sim_hash   BIGINT,
  s3_key     TEXT,
  links_out  LIST<TEXT>
);
```

Cassandra fits because it absorbs very high write throughput (millions of pages/hour) and supports **TTL** on rows — handy for expiring stale metadata when re-crawling.

**Redis** holds the live Frontier state: per-domain back queues, domain timers, and the Bloom filter — fast enough for millions of lookups per second.

## Scaling

At 1 billion pages per month, the throughput requirement is modest:

```
QPS = 1,000,000,000 / (30 × 86,400) ≈ 385 pages/sec
```

385 pages/sec needs only **~50–100 Fetcher workers**, since most fetches finish in under a second and **network latency, not CPU, is the bottleneck**. The Fetcher pool scales horizontally — add workers for more throughput.

**Domain affinity**: each worker owns a subset of domains, assigned via a **consistent hash ring on the domain name**. When a URL is picked, it routes to the worker responsible for its domain. That way the per-domain crawl delay is enforced *inside one worker* — no distributed coordination needed to stay polite.

<Callout type="tip">
**In practice:** domain affinity is what makes politeness *scalable*. Because one worker owns `example.com` end to end, the "1 request/second" timer is just a local check — no locks, no cross-node consensus. Consistent hashing also means adding or removing a worker only reshuffles a small slice of domains.
</Callout>

**JavaScript-heavy pages**: a plain HTTP GET can't run JavaScript, so single-page apps that render client-side look **empty** to the crawler. For those, run **headless browsers** (Chromium/Playwright) to execute the JS. It costs **10–50× more CPU** than a plain fetch, so reserve it for sites explicitly flagged as needing rendering.

**Freshness and re-crawl scheduling**: not every page deserves equal attention. News changes every few minutes; Wikipedia every few days; old blog posts stay static for years. A re-crawl scheduler tracks `last_modified` headers, content-hash drift over time, and observed update frequency, then assigns re-crawl intervals — often crawled pages get scheduled more, stable pages less.

## Summary

A web crawler is really three hard problems wearing a networking costume: **what to crawl next**, **how not to be rude**, and **how not to do the same work twice**. The **URL Frontier** answers the first with a two-level queue — priority front queues feeding per-domain back queues — which cleanly separates crawl priority from **politeness** (robots.txt, a ~1 req/sec crawl delay, DNS caching). **Deduplication** answers the third on two levels: a **Bloom filter** for URL membership at ~1.14 GB instead of 8 GB, and **SimHash** for near-duplicate content. Store the 10 PB of raw HTML compressed in **S3** (~1 PB), metadata in **Cassandra**, and live scheduling state in **Redis**, with **domain affinity** via consistent hashing so politeness scales without coordination. Watch for the classic traps — infinite crawler traps, Bloom filters that degrade as they fill, and JavaScript-rendered pages that need a costly headless browser.
