<Callout type="analogy">
Think of the notification system as a **post office**. A service somewhere just wants to tell a user "your order shipped" — it drops one letter at the counter and walks away. It does **not** care whether that message goes out as a **push**, an **email**, or an **SMS**.

The post office does the rest: it reads the address, checks whether the recipient has opted out of junk mail, then sorts the letter into the right pile — air mail (push), standard post (email), or courier (SMS) — each with its own truck and driver. If the courier company is having a bad day, the standard-post trucks keep rolling. That sorting-and-routing is the whole job: **one drop-off, fan out to the right channels, and make sure nothing gets lost.**
</Callout>

## Requirements

Scope the notification system before designing it. Real systems send dozens of types of notifications; the interview focuses on the **delivery infrastructure**.

**Functional requirements:**
- Support three notification channels: mobile push (iOS and Android), email, and SMS.
- Accept notification requests from internal services (**event sources**) — e.g., a payment service triggers a "payment confirmed" notification.
- Respect per-user **opt-out preferences**: users can disable individual channels.
- Deliver with low latency — push and SMS should arrive within seconds.
- Maintain an **audit log** of every notification sent.

**Non-functional requirements:**
- **Scale**: 10 million push/day, 1 million emails/day, 100,000 SMS/day.
- **Reliability**: a failed delivery must be retried — notifications must not be silently dropped.
- **Idempotency**: if a triggering event fires twice, users must not receive duplicates.
- **High availability**: the notification path stays up even if upstream services are degraded.

At these volumes (roughly **115 push/sec** sustained), a synchronous API call straight from the event source to a third-party SDK *would* technically work — but it welds delivery failures to the upstream service. The right approach decouples them with a **message queue**.

<Callout type="tip">
**In practice — do the back-of-envelope math.** 10M push/day averages ~115/sec, but traffic is spiky: a marketing blast or a 6 PM order wave can be 10× that. Design for the peak (~1,000+/sec), not the average. This is also why you never size the system on the daily total alone.
</Callout>

## Types of Notifications

Each channel uses a different third-party integration, with a different latency and cost profile.

**Push notifications** reach mobile apps even when the app is backgrounded. iOS uses **Apple Push Notification Service (APNs)** and Android uses **Firebase Cloud Messaging (FCM)**. Both require the backend to hold a **device token** (issued by the OS when the user installs the app and grants permission). The flow:

1. Mobile app registers with APNs/FCM → receives a device token.
2. Device token is stored server-side, tied to the user's account.
3. Backend sends a push request to APNs/FCM with the token and payload.
4. APNs/FCM delivers to the device.

Device tokens **expire and change** when users reinstall apps. Handle token-invalidation errors from APNs/FCM by removing stale tokens from your database.

**Email** is the highest-volume but lowest-urgency channel. Sending billions of emails reliably requires specialized infrastructure — **IP warm-up, DKIM/SPF signing, bounce handling** — that is infeasible to build in-house. Providers like **SendGrid** and **Amazon SES** handle it: you make an API call, they own deliverability, unsubscribe management, and bounce tracking.

**SMS** is the most reliable channel for urgent messages (two-factor auth, account alerts) because it needs only a cellular signal, not internet. **Twilio** is the dominant provider. SMS is also the **most expensive** channel, so its volume is naturally lowest.

| Channel | Provider | Typical latency | Relative cost | Best for |
|---|---|---|---|---|
| Push | APNs / FCM | Sub-second | ~Free | Engagement, real-time alerts |
| Email | SendGrid / SES | Seconds–minutes | Very cheap | Receipts, digests, marketing |
| SMS | Twilio | Seconds | Expensive (per segment) | 2FA, critical account alerts |

## High-Level Architecture

The key principle is **decoupling**: the event source should not care *how* a notification is delivered. It fires an event and moves on. The system handles everything downstream.

The flow:

1. An **event source** (payment, order, marketing) calls the Notification Service API with `user_id`, `event_type`, `template_key`, and `template_params`.
2. The **Notification Service** validates the request, looks up the user's **preferences** (which channels are enabled), resolves the **template**, and enriches the payload with user data.
3. It publishes **one message per channel** to the appropriate **message queue** (push queue, email queue, SMS queue).
4. **Channel workers** consume from each queue and call the relevant third-party API (APNs, FCM, SendGrid, SES, Twilio).
5. Workers write the delivery result (success or failure + error code) to the **notification log**.

By routing through queues, the system stays resilient to third-party slowness. If SendGrid is slow, emails pile up in *their* queue and drain when SendGrid recovers — without touching push delivery or blocking the event source.

## Message Queue Design

**Separate queues per channel are essential.** If push and email shared a queue and email workers stalled during a SendGrid outage, slow email would **starve push notifications** of workers. With dedicated queues:

- The push queue drains at the push worker's rate, independent of email.
- **Queue depth per channel** becomes an operational signal: a growing email queue means "SendGrid problem."

**Queue technology**: Kafka or SQS both work. Kafka gives strong durability, **replay** (great for debugging missed notifications), and very high throughput. SQS is simpler to operate. For most teams, **SQS with dead-letter queues (DLQ)** is the right starting point.

**Message schema:**

```json
{
  "notification_id": "uuid-v4",
  "user_id": 12345,
  "channel": "push",
  "device_token": "abc...xyz",
  "title": "Your order shipped!",
  "body": "Your order #4892 has shipped and will arrive tomorrow.",
  "created_at": "2024-01-15T10:30:00Z"
}
```

The `notification_id` is the **idempotency key**. If the same event fires twice and produces two messages with the same `notification_id`, the worker checks the notification log first — if an entry with status `sent` already exists, it skips delivery.

<Callout type="tip">
**In practice — one queue per channel, not per team.** Netflix, Uber, and similar shops route each channel through its own topic/queue precisely so a flaky email vendor can't back up 2FA texts. Watch **queue lag / age of oldest message** as your primary health metric — it spikes long before users start complaining.
</Callout>

## Third-Party Integrations

Workers call third-party APIs synchronously. The patterns:

**APNs (iOS push)** — Apple's HTTP/2 API, one notification per token per request. Responses are synchronous: **200** means delivered to APNs (not necessarily the device — APNs owns the last mile); **410** means the token is invalid → remove it from the DB immediately.

**FCM (Android push)** — similar to APNs, but Google's API supports **batch sends** (up to 500 tokens per request), useful for broadcasts. Handle `INVALID_REGISTRATION` by removing stale tokens.

**SendGrid / SES (email)** — REST calls with bulk sends and provider-side templates (HTML templating lives with the provider, not your code). Always configure **SPF, DKIM, and DMARC** for your sending domain — without them, email lands in spam.

**Twilio (SMS)** — simple REST API. Twilio charges **per message segment** (160 chars ASCII, 70 Unicode). Keep SMS payloads short; truncate if necessary.

Wrap every integration in a **provider abstraction layer**. To switch from SendGrid to SES, you replace one implementation — not every caller.

<Callout type="warning">
**The main bottleneck: you don't control your providers.** APNs, Twilio, and SendGrid *will* have outages, rate-limit you, throttle without warning, and return stale-token errors — and there is nothing you can do to make them faster in the moment.

Defend against it: (1) put a **queue in front of every provider** so an outage becomes backpressure, not lost data; (2) **retry with exponential backoff** so you don't hammer a struggling API; (3) respect the provider's own **rate limits** with a global cap; (4) hide them behind a **provider abstraction** so you can fail over to a backup vendor; and (5) alert on **queue depth and DLQ size**, which surface a provider problem faster than error logs do.
</Callout>

## Rate Limiting

Without rate limiting, a poorly written marketing campaign can send a user **50 notifications in one day**. That destroys trust and drives uninstalls.

Apply rate limiting at the **Notification Service layer**, *before* messages are enqueued:

- **Per-user, per-day**: no more than **10 notifications/user/day** across all channels.
- **Per-user, per-channel**: no more than **3 push/hour** (prevents rapid-fire alerts).
- **Global burst limit**: cap the total send rate to protect **third-party API quotas**.

Track rate-limit state in **Redis** with an atomic increment and TTL:

```
Key: rate_limit:{user_id}:{channel}:{date}
Value: current count
TTL: 86400 seconds (resets daily)
```

On each request, the Notification Service calls `INCR` on the key. If the value exceeds the limit, the notification is dropped (or deferred to next-day delivery, depending on priority).

<Callout type="tip">
**In practice — separate "transactional" from "promotional."** A 2FA code or fraud alert must *never* be rate-limited away, while a marketing blast should be the first thing throttled. Tag each notification with a priority/class and apply limits per class, so the daily cap trims the newsletter, not the security code.
</Callout>

## Reliability

A system that silently drops messages on provider errors is not production-ready. Reliability rests on three mechanisms:

**Retry with exponential backoff** — on a delivery failure (network timeout, provider 5xx), the worker does *not* retry instantly. It re-enqueues with an exponentially growing delay (**1s, 2s, 4s, 8s, … up to ~30 min**). This keeps a struggling API from being hammered by a retry storm. After a max retry count (e.g., **5 attempts**), the message moves to a **dead-letter queue**.

**Idempotency** — before calling the provider, the worker writes a `pending` record to the notification log keyed by `notification_id`. Before writing, it checks whether that ID already has a `sent` entry — if so, skip. This **two-phase write** means that even if a worker crashes *after* the API call but *before* logging success, the next attempt detects the duplicate and won't re-send.

**Dead-letter queues** — messages that exhaust all retries land in a DLQ. An alert pages on-call, who inspects the failures, spots systemic issues (e.g., a batch of dead tokens), and replays or discards them.

<Callout type="warning">
**Deduplication has a subtle gap.** The idempotency check works only if the log write and the provider call can't get permanently out of sync. If the worker sends the SMS and then dies before writing `sent`, a naive retry would send it **twice**. The `pending`-then-`sent` two-phase write shrinks — but doesn't fully close — this window, so treat delivery as **at-least-once** and make sure duplicate user-visible sends are *rare and tolerable*, not impossible. True exactly-once across a third-party boundary you don't control is a myth.
</Callout>

**Notification log schema:**

```sql
CREATE TABLE notification_log (
  notification_id  UUID PRIMARY KEY,
  user_id          BIGINT NOT NULL,
  channel          VARCHAR(10),
  status           VARCHAR(20),  -- pending, sent, failed, deduplicated
  provider_response TEXT,
  created_at       TIMESTAMP,
  updated_at       TIMESTAMP
);
```

The log serves double duty: **idempotency store** and **audit trail**. When a user reports "I didn't get my shipping notification," you query the log to see exactly what was sent, when, and what the provider returned.

**User preference table:**

```sql
CREATE TABLE user_notification_preferences (
  user_id       BIGINT NOT NULL,
  channel       VARCHAR(10) NOT NULL,
  event_type    VARCHAR(50) NOT NULL,
  is_enabled    BOOLEAN DEFAULT TRUE,
  PRIMARY KEY (user_id, channel, event_type)
);
```

Before enqueuing, the Notification Service checks this table. If the user opted out of push for "marketing" events, that notification is **discarded, not enqueued**. Respecting opt-outs is both a legal requirement (**CAN-SPAM, GDPR**) and essential for user trust.

## Summary

A notification system is a **post office**: one drop-off from an event source, fanned out to push, email, and SMS. The core move is **decoupling** — put a **message queue between trigger and delivery** so a slow provider becomes backpressure instead of a failure, and give **each channel its own queue and worker pool** so one bad vendor can't starve the others. Reliability comes from **retries with exponential backoff, dead-letter queues, and an idempotency key** (the `notification_id`) checked against a notification log, while **rate limiting and opt-out preferences** protect the user from spam and keep you legal. Because you don't control APNs, SendGrid, or Twilio, design for **at-least-once** delivery and treat provider outages as the expected case, not the exception.
