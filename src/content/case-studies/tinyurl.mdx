<Callout type="analogy">
A URL shortener is a **coat-check counter for links**. You hand over a big,
unwieldy coat (a 200-character URL), and you get back a tiny numbered ticket
(`tinyurl.com/abc1234`). The ticket is meaningless on its own — but bring it
back and the attendant instantly fetches your exact coat.

The whole system is really just two jobs: **file a coat and hand out a ticket**
(write), and **take a ticket and return the coat** (read). The catch is that
people redeem tickets far more often than they check in coats — so the counter
is built for lightning-fast lookups above all else.
</Callout>

## Requirements Clarification

Before diving into databases and algorithms, clarify exactly what you are building. For a URL shortener, the requirements split cleanly into two categories.

**Functional requirements** define what the system must do:
- Accept a long URL and return a short, unique code (e.g., `tinyurl.com/abc1234`).
- Redirect a short URL to its original long URL quickly and reliably.
- Short URLs should optionally **expire** after a user-specified time.
- Users may optionally specify a **custom alias** instead of a generated code.

**Non-functional requirements** define how the system must behave under load:
- **High availability**: a downed URL shortener breaks links across the internet. Target **99.99% uptime**.
- **Low read latency**: redirects should complete in **under 10ms** at the application layer.
- **Durability**: once a short URL is created, it must never be silently lost.
- **Scale**: **100 million** new URLs shortened per day.

One important scoping decision is whether **analytics** matter. If you track every click (user agent, location, timestamp), you cannot let browsers cache the redirect indefinitely — an important factor in the redirect strategy you'll pick later.

## Scale Estimation

Scale estimation anchors your design choices. With 100 million URLs created per day:

```
Write QPS = 100,000,000 / 86,400 seconds ≈ 1,160 writes/sec
```

URL shorteners are **read-heavy**. Assume every link is clicked roughly 10 times on average:

```
Read QPS = 1,160 × 10 ≈ 11,600 reads/sec
```

That is a **10:1 read-to-write ratio**. Your caching strategy should be designed around this asymmetry.

For storage, assume each URL record is about 500 bytes (long URL + metadata). Over a 5-year retention window:

```
Storage = 100M URLs/day × 365 days × 5 years × 500 bytes ≈ 91 TB
```

<Callout type="tip">
**In practice:** 1,160 writes/sec is tiny — a single well-tuned database can
absorb that without breaking a sweat. The real number to fixate on is the
**11,600 reads/sec**. That asymmetry is the whole story: your job isn't to
scale writes, it's to make reads absurdly cheap. Everything downstream (Redis,
the redirect path, the 301/302 call) flows from that one ratio.
</Callout>

91 TB is manageable with modern object stores and replicated SQL, but you should mention **sharding or archival** strategies for cold data. The storage math confirms it: read throughput, not write throughput, is your bottleneck — reinforcing the need for a caching layer.

## High-Level Design

The core data flow is simple:

1. A client sends `POST /shorten` with a long URL in the request body.
2. The **Shortening Service** generates a unique short code, stores the mapping in the database, and returns the short URL.
3. A user visits `GET /{short_code}` (e.g., `tinyurl.com/abc1234`).
4. The **Redirect Service** looks up the short code in the cache, falls back to the database, and returns an HTTP redirect to the long URL.

These two flows — **shortening** and **redirecting** — can be served by the same application tier but benefit from separation because they have very different load profiles. Write traffic is modest; read traffic is an order of magnitude higher, so you scale the redirect tier independently.

The API contracts are:

```
POST /shorten
Body: { "longUrl": "https://...", "expiresAt": "2025-01-01", "alias": "my-link" }
Response: { "shortUrl": "https://tinyurl.com/abc1234" }

GET /{code}
Response: HTTP 301 or 302 redirect to long URL
```

## Database Design

The central table is straightforward:

```sql
CREATE TABLE urls (
  id           BIGINT PRIMARY KEY AUTO_INCREMENT,
  short_code   VARCHAR(10) UNIQUE NOT NULL,
  long_url     TEXT NOT NULL,
  user_id      BIGINT,
  created_at   TIMESTAMP DEFAULT NOW(),
  expires_at   TIMESTAMP,
  click_count  BIGINT DEFAULT 0
);
```

A relational database (MySQL or PostgreSQL) works well at this scale. The table is **write-once, read-many**: once a short code is created, the row is never updated except for optional click-counter increments.

The `short_code` column carries a **unique index** — that's your read path. The `expires_at` column lets a background job soft-delete or archive expired mappings. If you expect hundreds of millions of rows, **hash-based sharding on `short_code`** distributes read load across database replicas.

<Callout type="warning">
**Pressure point — the hot-row counter.** If you `UPDATE click_count = click_count + 1`
on every single redirect, a viral link becomes a **write hotspot**: thousands of
requests per second all fighting for a lock on the same row, and your read-heavy
system suddenly has a write-contention problem it wasn't built for.

Don't count synchronously on the read path. **Fire an event** (or increment a
Redis counter) and **batch-flush** the totals to the database every few seconds.
Analytics can tolerate being a few seconds stale; your redirect latency cannot
tolerate a row lock.
</Callout>

## Encoding Algorithm

How do you generate a short code that is compact, unique, and human-readable? The most robust approach is **Base62 encoding of an auto-increment integer**.

Base62 uses the character set `[a-z A-Z 0-9]` — 62 characters total. A **7-character code** gives you:

```
62^7 = 3,521,614,606,208 ≈ 3.5 trillion unique URLs
```

At 100 million new URLs per day, that capacity lasts nearly **100,000 years**. The algorithm:

1. The database auto-increments the row `id` (e.g., `id = 12345678`).
2. Convert the integer to Base62: divide repeatedly by 62 and map each remainder to the character set.
3. The result is the short code (e.g., `"dnh9zR"`).

This approach is **collision-free by construction**: because the underlying integer is unique, its Base62 representation is unique. No random generation, no uniqueness checks, no retry loops. The only coordination required is that the auto-increment primary key is unique — which the database already guarantees.

<Callout type="tip">
**In practice:** why 7 characters and not fewer? Six Base62 characters
(`62^6 ≈ 56 billion`) would still last centuries, but 7 gives comfortable
headroom and keeps every code the same length, which is friendlier for indexing
and UI. The trade-off in the other direction: a single global auto-increment ID
is a coordination point. At extreme scale, teams hand each shortener node a
**pre-allocated block of IDs** (or use a Snowflake-style generator) so nodes
don't fight over the counter.
</Callout>

An alternative is to generate **random 7-character codes** and check for collisions before insertion. This adds complexity (retry logic, potential thundering herd on a popular shortener) for no real benefit over the deterministic approach.

## Caching Layer

With **11,600 reads per second** and a 10:1 read-to-write ratio, a caching layer is essential. The access pattern follows the **Pareto principle** — roughly **20% of short codes account for 80% of clicks**. You only need to cache the hot 20%.

**Redis** is the right tool: in-memory, **sub-millisecond** lookups, and native TTL support so cache expiry can mirror URL expiry. The cache key is `short_code`; the value is `long_url`.

Cache population strategy: **cache-aside on first read**. On a cache miss, the redirect service fetches from the database and writes the result into Redis with a TTL. Subsequent reads are served straight from cache.

<Callout type="tip">
**In practice — cache sizing:** if 100 million URLs are active and the hot 20%
is 20 million entries at ~512 bytes each, that's roughly **10 GB** of Redis
memory. That fits on a single beefy Redis instance, or spreads across a Redis
Cluster for headroom and failover. Notice how cheap the read path becomes: a
10 GB cache absorbs the vast majority of 11,600 reads/sec that would otherwise
pound your database.
</Callout>

**Bloom filter optimization**: a Bloom filter placed in front of the cache short-circuits lookups for short codes that **definitely do not exist** (e.g., a user manually types `tinyurl.com/zzzzzzz`). A Bloom filter never returns a false negative — if it says "does not exist," you can safely skip both cache and database. This stops malicious or accidental **enumeration** of non-existent codes from reaching the database.

## Redirects

When a user visits a short URL, the redirect service must decide between two HTTP status codes:

**301 Moved Permanently** tells the browser the redirect is permanent. The browser caches it locally and never sends future requests to your server for that short code. This slashes server load — but it **permanently blinds you to future clicks** from that browser, and makes it impossible to change the destination URL without fighting a response the client has already cached.

**302 Found** (temporary redirect) tells the browser *not* to cache the redirect. Every click comes back to your servers, so you can log every visit, track analytics, and change the destination at will. The cost is a round trip per click.

| | 301 Permanent | 302 Temporary |
|---|---|---|
| Browser caches redirect | Yes | No |
| Server load per repeat click | ~zero | one round trip |
| Click analytics | Lost | Fully captured |
| Change destination later | Hard (client cached) | Easy |
| Best for | Static, never-changing links | Almost everything else |

**The recommendation for most URL shorteners is 302.** Redirect QPS is your primary design challenge, but you solve that with **application-layer caching (Redis)**, not by handing caching over to the browser. Preserving click analytics — visits per code, geography, timing, referrers — is extremely valuable and is silently destroyed by 301.

A **hybrid** approach uses 302 by default and lets power users opt into 301 (e.g., links in printed marketing materials that will never change and where analytics don't matter).

## Summary

A URL shortener is a **read-heavy** system — about 11,600 reads/sec against just 1,160 writes/sec — so every design decision optimizes the redirect path. Generate codes by **Base62-encoding an auto-increment ID**, which is unique by construction and needs no collision checks, and store the mapping in a simple write-once SQL table. Serve reads from a **Redis cache-aside layer** sized to the hot ~20% of codes (~10 GB), and front it with a **Bloom filter** to swat away lookups for codes that never existed. Return **302 redirects** so every click flows back through you for analytics, and keep click counting **off the synchronous path** by batching increments to avoid hot-row contention. The result: sub-10ms redirects that stay fast and observable even when a single link goes viral.
