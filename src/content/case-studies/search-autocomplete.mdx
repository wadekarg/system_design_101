<Callout type="analogy">
Autocomplete is a **phone book that finishes your sentence**. You flip to the
"Sy" tab and instantly see the most-called "Sy…" numbers — you don't read every
name in the book.

A **Trie** is that tabbed phone book for search queries: each letter you type
narrows you to a page. And instead of scanning that page every time, we
**pre-write the top 5 answers right on the tab** ahead of time. Typing becomes:
walk to the tab, read the sticky note. That's the whole trick.
</Callout>

## Requirements

Search autocomplete is a **latency-sensitive** feature: users type fast, and suggestions must appear **within 100ms** of each keystroke — otherwise the experience feels broken.

**Functional requirements:**
- As a user types, return the **top 5 most popular completions** for the current prefix.
- Rank completions by **historical search frequency** (how many users searched for this query).
- Support queries up to 50 characters long.
- Support ASCII lowercase for the initial design (26-letter English alphabet).

**Non-functional requirements:**
- **Latency**: suggestions in under 100ms end-to-end, per keystroke.
- **Scale**: Google-scale — billions of past searches to learn from.
- **Freshness**: reflect recent trends — yesterday's event should surface quickly.
- **Read-heavy**: users *query* autocomplete far more often than they *submit* a full search.

The system splits naturally into two independent concerns: a **data gathering phase** that learns from past searches, and a **serving phase** that answers live keystrokes. Design them separately.

<Callout type="tip">
**In practice — the two-system split.** Notice the shapes are opposite. Data
gathering is **write-heavy, batch, latency-doesn't-matter** (runs nightly).
Serving is **read-heavy, real-time, latency-is-everything** (100ms budget).
Bolting them together is a classic mistake — the offline job would stall the hot
path. Keep them apart and each can be tuned for its own goal.
</Callout>

## Data Gathering Phase

The system learns what people search for by observing **completed** queries. Every time a user submits a full search, the query string and a frequency count are recorded.

**Search frequency table:**

```sql
CREATE TABLE search_frequency (
  query      VARCHAR(255) PRIMARY KEY,
  frequency  BIGINT NOT NULL,
  updated_at TIMESTAMP
);
```

This table grows to **billions of rows** at Google scale. Running a raw SQL query every time the Trie is rebuilt would be infeasibly slow. Instead, the pipeline works in two steps:

1. **Stream raw queries** — every submitted search is written to a Kafka topic (`search-events`) with the query string and timestamp. Kafka gives **durability** and lets multiple consumers read the same stream (the indexing pipeline and the autocomplete pipeline both tap it).

2. **Aggregate over a window** — a batch job (Spark or Flink) reads the stream, aggregates query frequencies over a **rolling 7-day window**, and writes the counts to the frequency table. A weekly window (rather than all-time counts) means **trending queries surface fast** and **stale queries decay naturally**.

The aggregation runs on a schedule (e.g., nightly) and emits a snapshot of the top-N queries and their counts. That snapshot is the input to the Trie builder.

<Callout type="warning">
**The freshness trap.** A weekly window means a query that trends *today* won't
appear for up to **7 days** — unacceptable for breaking news. The fix is a
**second, real-time tier**: a sliding-window counter in Redis tracks per-query
frequency over the **last hour**. Any query that spikes past a threshold is
**injected into the serving Trie with a boosted score**, bypassing the batch
cycle entirely. Batch for accuracy, stream for speed — you need both.
</Callout>

## Serving Phase

When a user types "sys", the system must return the top 5 completions for "sys" — ideally "system design", "system of a down", "syscall" — within 100ms *including* the network round-trip.

The serving flow is short:
1. User types a character → browser sends `GET /autocomplete?q=sys`.
2. Autocomplete Service checks the **Redis cache** for prefix "sys".
3. **Cache hit** → return the cached top-5 immediately.
4. **Cache miss** → query the in-memory **Trie service** for the top-5, write the result to Redis, return it.

The Trie service is an in-memory process that loads the Trie from a serialized snapshot at startup. It serves **pure in-memory lookups — no disk I/O on the hot path.**

<Callout type="tip">
**In practice — spend the 100ms wisely.** A cross-continent round trip alone can
eat 100–200ms, so most of your budget is *network*, not compute. That's why edge
proximity, a Redis hit (sub-millisecond), and a debounce on the client (fire only
after the user pauses ~50ms of typing) matter as much as the Trie itself.
</Callout>

**Browser-side caching:** results for a prefix don't change second-to-second, so the API response can carry `Cache-Control: max-age=60`. The browser caches for 60 seconds — if the user deletes and re-types the same prefix within a minute, **no request is sent at all**, cutting server load sharply during heavy typing.

## Trie Data Structure

A **Trie** (prefix tree) is the natural structure for prefix search. Each node is one character. The path from root to any node spells a **prefix**; the path from root to a leaf spells a **complete query**.

For the query "system design":
- The root has a child `s`.
- `s` → `y` → `s` → `t` → `e` → `m` → `(space)` → `d` → `e` → `s` → `i` → `g` → `n`.
- At the leaf you store that "system design" has frequency **9,400,000**.

A prefix query for "sys" traverses root → `s` → `y` → `s`. That node (depth 3) is the **prefix node**. To get the top 5 completions, you must explore all paths descending from it and pick the 5 highest-frequency queries.

The **naive approach** — DFS from the prefix node to gather every descendant leaf, then sort by frequency — collapses for a popular short prefix. Under "s" the subtree holds **millions of nodes**, and doing that DFS on every keystroke is hopeless within 100ms.

## Optimizing the Trie

The key optimization is **pre-computing top-K at every node at build time**. Instead of *searching* for completions on each query, each node **stores** the top-5 completions for its prefix with their frequencies:

```
Node "sys" → top5: [
  ("system design", 9400000),
  ("system of a down", 7200000),
  ("syscall", 3100000),
  ("system requirements", 2800000),
  ("system restore", 2100000)
]
```

With pre-computed top-K, a query for "sys" needs only:
1. Traverse root → prefix node: **O(p)**, where p is the prefix length.
2. Read the pre-stored top-5 list: **O(1)**.

Total: **O(p)** — proportional only to prefix length, independent of how many descendants exist. A 10-character prefix is just 10 node hops. Extremely fast.

**Building top-K bottom-up:** during construction, process nodes bottom-up. Leaves carry their own frequency. Each internal node's top-K is the **merge of its children's top-K lists**, keeping only the top K. This is O(n × K × log K) across the Trie — expensive, but it runs **offline** where latency doesn't matter.

<Callout type="tip">
**In practice — trade build cost for query speed.** This is the whole design
philosophy: you happily burn minutes of offline CPU merging top-K lists so that
each of billions of daily keystrokes costs ~10 pointer hops. Precomputation moves
work off the hot path — the same reason CDNs pre-warm content and search engines
pre-build inverted indexes.
</Callout>

**Storing the Trie:** a 26-ary Trie (one child slot per letter) grows to **millions of nodes** for the full vocabulary. To persist and load it:
- **Serving**: load the serialized Trie into process memory at startup.
- **Persistence**: keep the snapshot in **S3**; on restart, download and deserialize.
- Use **binary serialization** (protobuf or a custom format) — far more compact than JSON.

## Caching

The Trie query is already O(p) — sub-millisecond in memory. But under heavy traffic even fast lookups pile up, so a cache in front removes most of them.

**The Pareto principle applies to prefixes:** a small fraction of prefixes drive the vast majority of queries. Prefixes like "the", "how", "what", "new", "you" together carry enormous traffic. Caching the **top ~10,000 prefixes** absorbs most requests without touching the Trie.

**Redis cache layer:**

```
Key:   autocomplete:{prefix}
Value: JSON array of top-5 completions with frequencies
TTL:   3600 seconds (1 hour)
```

Population is **cache-aside (lazy)**: on a miss, query the Trie, write the result to Redis with a 1-hour TTL. When the TTL expires, the next query re-fetches — which naturally refreshes the cache after a weekly rebuild.

<Callout type="tip">
**In practice — a tiny cache goes a long way.** Because prefix popularity follows
a **Zipfian** distribution, a Redis cache of only a **few hundred megabytes** can
reach **80%+ hit rates** — meaning 80% of keystrokes never reach the Trie service
at all. Cheap memory, huge load reduction.
</Callout>

## Scale

**Partitioned Trie:** one server eventually can't hold the whole Trie or serve the whole query volume. **Shard by first character** of the prefix:

| Shard | Handles prefixes starting with |
|---|---|
| A | `a` |
| B | `b` |
| … | … |
| Z | `z` |

The API gateway routes each query to the correct shard by its first character — 26 independent shards, each ~1/26 of the Trie. For very popular first letters, shard further by the **second** character.

<Callout type="warning">
**Hot-shard skew.** Splitting by first letter does *not* split traffic evenly —
prefixes starting with `s` or `t` dwarf those starting with `x` or `z`. A naive
26-way split overloads the popular shards. Mitigate by **splitting hot letters
finer** (by second character) and **adding read replicas** for hot shards, so
load — not just the alphabet — drives the partitioning.
</Callout>

**Trie update strategy:** you can't safely mutate the Trie in place while it serves live traffic (it needs complex locking). Use an **atomic swap** instead:
1. The batch job builds a **completely new Trie** from the latest snapshot.
2. Serialize it and upload to S3.
3. Trie servers download the new snapshot, load it into memory, then **atomically flip the pointer** the serving code reads from.
4. The old Trie is garbage-collected.

This gives **zero-downtime updates**: from the request handler's view, the swap is instantaneous.

**Handling real-time trends:** the batch cycle misses same-day spikes, so a real-time pipeline runs alongside it:
- A **Flink** job reads `search-events` and keeps sliding-window counts for the last hour.
- Queries whose hourly count exceeds a threshold (e.g., **10,000 searches/hour**) are injected into the Trie with a boosted score, surfacing immediately.
- This **two-tier** design — weekly batch for historical accuracy, real-time stream for trend sensitivity — is how production autocomplete handles breaking news and viral events.

## Summary

Autocomplete is a **prefix-lookup problem**, and a **Trie** models it perfectly: each character narrows the search, and pre-computing the **top-5 at every node** turns serving into an O(prefix length) read instead of a costly subtree scan. Split the system in two — an **offline pipeline** (Kafka → windowed aggregation → Trie build → atomic swap into S3-backed servers) and a **real-time serving layer** (Redis cache in front of an in-memory Trie) — so each is tuned for its opposite goal. A small Redis cache exploits the **Zipfian** popularity of prefixes to answer 80%+ of keystrokes without a Trie lookup. To meet the **sub-100ms** budget while staying fresh, combine a weekly batch (accuracy) with an **hourly real-time tier** that injects trending queries. Scale horizontally by **sharding on the first character**, watching for hot-shard skew, and publish updates with a **zero-downtime atomic pointer swap**.
