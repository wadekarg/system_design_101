<Callout type="analogy">
Picture a busy restaurant with one host at the door and ten tables of waiters.
The **host** doesn't cook anything — their whole job is to seat each new party at
whichever table can take them, so no single waiter gets slammed while others
stand around idle.

A **load balancer** is that host for your servers. It stands in front of the
pool, greets every incoming request, and hands it to a server that can handle it.
If a waiter walks out mid-shift (a server crashes), the host simply stops seating
new parties there — and the diners never notice.
</Callout>

## What a load balancer actually does

A **load balancer** sits between your clients and a pool of backend servers. It
accepts every incoming request and forwards it to one of the available servers
using some **algorithm**. The goal is simple: stop any single server from
becoming a bottleneck.

This is what makes **horizontal scaling** possible — handling more load by adding
machines instead of buying one giant one. Put a load balancer in front of ten
identical web servers and you can serve roughly ten times the traffic of one.
Adding an eleventh server is just registering it with the balancer. No downtime.

It also buys you **availability**. If a server crashes, the load balancer notices
(via **health checks**) and stops routing to it. The other nine absorb the slack.
From the client's side, nothing broke.

<Callout type="tip">
The alternative to horizontal scaling is **vertical scaling** — buying a bigger
box. That works until it doesn't: physical limits are real, and the top-end
machine costs far more per unit of power than several mid-range ones. Load
balancing is how you escape that ceiling.
</Callout>

## Load balancing algorithms

The algorithm decides *which* server gets the next request. Different algorithms
trade simplicity for smarter distribution.

- **Round Robin** — hand requests out in a rotating cycle: server 1, 2, 3, 1, 2…
  Dead simple, needs no state, and works great when all servers are equal and all
  requests take about the same time. Its weakness: it treats a 2 ms request and a
  2 second request identically, so a box that catches a run of slow requests can
  get buried while others idle.
- **Least Connections** — send each request to the server with the fewest open
  connections. Much better when request durations vary wildly (uploads, streaming,
  long-lived connections). The cost is a little state: the balancer has to track
  connection counts.
- **IP Hash** — hash the client's IP to pick a server, so the same client always
  lands on the same box. It's an implicit form of **sticky sessions** with no
  per-session state. But it distributes unevenly when many clients share one IP
  (corporate NAT), and changing the server count reshuffles everyone.
- **Weighted variants** — give beefier servers a higher **weight** so they receive
  proportionally more traffic. This lets you mix different-sized machines in one
  pool without over- or under-loading any of them.

<Callout type="tip">
In practice, **Round Robin** and **Least Connections** cover the vast majority of
real deployments. Reach for IP Hash only when you genuinely need affinity and
can't externalize session state (see below) — it's usually the wrong first choice.
</Callout>

## Layer 4 vs Layer 7

Where the load balancer sits in the network stack decides how much it can *see* —
and therefore how smart its routing can be.

| | **Layer 4 (Transport)** | **Layer 7 (Application)** |
|---|---|---|
| Operates on | TCP / UDP | HTTP / HTTPS |
| Can see | Source/dest IP + port | URL path, method, headers, cookies, body |
| Routing decisions | Network-level only | Content-based (`/api/*` vs `/static/*`, headers, canary) |
| Speed | Extremely fast, millions of conns/sec | Slightly more CPU to parse requests |
| Examples | HAProxy (TCP mode), AWS NLB | Nginx, AWS ALB, Caddy |
| Use when | You need raw throughput, no content routing | You need smart, HTTP-aware routing |

A **Layer 4** load balancer forwards packets based only on IPs and ports. It never
reads the payload, so it's blazing fast and cheap. A **Layer 7** load balancer
fully parses the HTTP request, which unlocks powerful tricks: route `/api/*` to
app servers and `/static/*` to a file pool, send `X-Beta-User: true` traffic to a
canary, or read cookies for sticky sessions. The only cost is a bit of CPU to
parse — negligible except at extreme throughput.

## Health checks

**Health checks** are how the balancer knows which backends are fit for traffic.
Without them, it would keep routing to a crashed server and every one of those
requests would fail.

- **Passive checks** are reactive: if a real request hits a connection-refused
  error or TCP timeout, the balancer marks that backend unhealthy. The downside —
  it only learns *after* a real user already got burned.
- **Active checks** are proactive: the balancer periodically probes a dedicated
  endpoint (like `/health`) on each backend. Non-200, too slow, or no response →
  removed from rotation. When probes succeed again, it's restored. This catches
  failures *before* user traffic hits them and tolerates transient blips.

<Callout type="warning">
The classic trap: a **shallow health check** that returns 200 OK without verifying
anything. If `/health` doesn't confirm the database connection, downstream deps, or
the connection pool, a server whose DB is *down* still looks healthy — so the
balancer keeps feeding it doomed requests. But go too deep and the check itself
becomes a load source. **Check the critical dependencies quickly, and nothing
more.**
</Callout>

## Session persistence

HTTP is stateless, yet many apps stash **session state** on an individual server —
in memory or a local file. That breaks under load balancing: if your first request
lands on server A but your second goes to server B, server B has no clue about your
session, and you're suddenly logged out or your cart is empty.

**Sticky sessions** (aka session affinity) fix this by pinning a client to the same
backend, using a session cookie or the client's IP. It works, but it's a
compromise: if that server dies, those sessions die with it, and load skews toward
whichever box collected the long-lived sessions.

The cleaner fix is to **externalize session state** to a shared store (Redis is the
go-to). Now any server can handle any request, sticky sessions become unnecessary,
and load balancing is genuinely stateless.

## Where this shows up in real systems

- **High-traffic web apps (any large site)** → an L7 balancer like Nginx or ALB out
  front, routing by path and running health checks, so app servers stay
  interchangeable and disposable.
- **Ultra-high-throughput or non-HTTP traffic (gaming, VoIP, databases)** → an L4
  balancer like AWS NLB or HAProxy in TCP mode, because raw packet-forwarding speed
  matters more than content-aware routing.
- **APIs with mixed endpoints** → L7 path-based routing splits `/api/*`,
  `/static/*`, and `/admin/*` to purpose-built pools.
- **Canary / blue-green deploys** → L7 header- or weight-based routing sends a small
  slice of traffic to the new version before the full rollout.
- **Stateful legacy apps** → sticky sessions as a bridge until session state can be
  externalized to Redis.

## Handling the pressure points

- **The load balancer is itself a single point of failure.** Run at least two,
  fronted by **DNS round-robin** (multiple LB IPs) or **anycast** (many servers
  sharing one IP, BGP routes to the nearest healthy one). Cloud-managed LBs do this
  for you.
- **Uneven load from IP Hash or sticky sessions?** Move to Least Connections and
  externalize sessions to Redis so any server can take any request.
- **Servers flapping in and out of rotation?** Tune health-check thresholds
  (require N consecutive failures) so a brief blip doesn't yank a healthy server.
- **A slow backend dragging p99?** Combine active health checks with per-request
  timeouts so the balancer routes around a degraded — not just dead — server.

## Alternatives & related ideas

<Callout type="alternative">
A load balancer isn't the only way to spread traffic. **DNS round-robin** hands out
rotating IPs at resolution time — cheap and global, but with no health awareness and
slow failover (clients cache DNS). **Anycast** advertises one IP from many locations
and lets the network route to the nearest, which is how CDNs and global services get
users to a close edge. And **client-side load balancing** (common in service meshes
like Envoy/Istio) pushes the decision into the caller, skipping a central hop
entirely. Most large systems layer these: anycast/DNS to pick a region, then a real
load balancer inside it.
</Callout>

## Summary

A load balancer is the host at the door of your server pool: it takes every request
and hands it to a server that can handle it, which is what makes **horizontal
scaling** and high availability possible. The **algorithm** (Round Robin, Least
Connections, IP Hash, weighted) decides *how* it spreads load, and the **layer**
(L4 for raw speed, L7 for content-aware routing) decides *what* it can route on.
**Health checks** keep dead and degraded servers out of rotation — but only if they
verify real dependencies, not just return 200. Finally, remember the balancer is
itself a single point of failure, so always run it redundantly behind DNS
round-robin or anycast.
