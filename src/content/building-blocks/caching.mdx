## What is Caching

A cache is a layer of fast storage that sits between a client and the authoritative source of data. When a piece of data is expensive to produce — whether because it requires a database query, a computation, or a network call to a downstream service — a cache stores the result so that subsequent requests for the same data can be served from fast storage (usually RAM) instead of repeating the expensive operation.

The fundamental trade-off is freshness versus speed. Cached data is, by definition, a copy that may diverge from the source of truth. The longer data lives in the cache, the greater the risk that it becomes stale. Caching is most appropriate for data that is read frequently, changed infrequently, and where serving slightly stale data is acceptable. User profile pictures, product catalog entries, rendered HTML fragments, and computation-heavy aggregates are all natural cache candidates. Account balances and inventory counts, where accuracy is critical, require more careful handling.

In practice, caching is often the most impactful optimization you can make to a system's performance. A single cache hit that avoids a 50-millisecond database query can reduce page load time by half. When that database serves thousands of requests per second, adding a cache in front of it can eliminate 90% of the query load, allowing the database to handle far more total traffic without additional hardware.

## Cache Hit vs Miss

A cache hit occurs when the requested data is present in the cache and returned directly. A cache miss occurs when the data is not in the cache — the system must fall back to the authoritative source, retrieve the data, store it in the cache, and return it to the caller. Subsequent requests for the same data will find it in the cache (a hit).

The **hit ratio** (also called hit rate) is the fraction of requests that are served from the cache, expressed as a percentage. A hit ratio of 95% means 95% of requests are served from cache and only 5% require a database or compute round-trip. The hit ratio is the primary health metric for a cache. Low hit ratios indicate that either the working set (the set of data actually being accessed) is too large for the cache, or that cache keys are too specific, or that data is being evicted too aggressively.

A **cache stampede** (also called thundering herd) is a dangerous scenario that occurs when a popular cache entry expires and many concurrent requests all miss at the same time, flooding the database with identical queries. Mitigation strategies include probabilistic early expiration (recomputing the cache slightly before it expires, under low load), locking (having one request refill the cache while others wait), and staggered TTLs (adding random jitter to expiration times to avoid synchronized expiry across multiple keys).

## Cache Placement Strategies

Caches can exist at multiple layers of your system, each with different trade-offs in terms of latency, capacity, and scope.

**Client-side caching** stores data on the user's device — in the browser's memory cache or local storage, or in a mobile app's local database. It provides the lowest possible latency (no network round-trip) and reduces server load. The limitation is that it is per-user — one user's cached data is not shared with another — and it cannot be easily invalidated server-side when the underlying data changes.

**CDN caching** stores content (usually static assets, but increasingly API responses) at geographically distributed points of presence. A CDN cache hit costs a fraction of a millisecond compared to hitting your origin server potentially thousands of miles away. CDN caching is covered in depth in the CDN topic, but from a caching perspective it is simply a distributed cache that sits at the network edge.

**Server-side caching** with systems like Redis or Memcached is the most common form of application-level caching. Your application servers check the cache before querying the database. Cache keys are usually derived from the query or computation parameters (for example, the key `user:12345:profile` holds the profile data for user 12345). This form of caching is shared across all application servers, meaning a cache population by one server instance is immediately visible to all others — unlike in-process (in-memory) caching, which is local to each server and requires careful coordination.

**Database query caches** are maintained by the database engine itself. MySQL had a built-in query cache (deprecated in MySQL 8.0) that stored query results keyed by query text. Most modern databases instead rely on buffer pools that cache frequently accessed disk pages in RAM, which is a lower-level and more general form of caching.

## Eviction Policies

A cache has finite capacity. When it fills up, the eviction policy determines which cached entry is removed to make room for new data.

**Least Recently Used (LRU)** evicts the entry that was last accessed the longest time ago. The intuition is that data accessed recently is more likely to be accessed again soon than data that has not been touched for a long time. LRU is the most common eviction policy and performs well for most general-purpose workloads. It requires maintaining a record of access order, which adds a small amount of overhead.

**Least Frequently Used (LFU)** evicts the entry with the lowest access count over a period. This is better than LRU for workloads where some data is accessed consistently over time (and should be retained) while other data has brief bursts of popularity. LFU is more complex to implement correctly and can suffer from cache pollution: data that was popular in the past but is no longer accessed takes a long time to age out.

**First In, First Out (FIFO)** evicts the oldest entry regardless of how often or recently it was accessed. FIFO ignores access patterns and is rarely the right choice for application caches, but it is simple and predictable.

**Time-to-Live (TTL)** is not an eviction policy in the strict sense but works alongside eviction policies. Each cache entry is given a maximum lifetime, after which it is considered expired and treated as a miss even if it is still in the cache. TTL is the primary mechanism for ensuring cache freshness — without TTL, stale data can accumulate indefinitely.

## Write Strategies

The write strategy determines what happens to the cache when data is written (created or updated).

**Write-through** writes to the cache and the database simultaneously on every write operation. The write is not acknowledged to the caller until both the cache and the database have confirmed the write. This guarantees that the cache is always consistent with the database — there is no window of inconsistency. The cost is that every write incurs the full latency of the database write; the cache provides no benefit for write performance.

**Write-back** (also called write-behind) writes to the cache immediately and asynchronously propagates the change to the database later, in a background process. This makes writes very fast — the caller gets acknowledgement as soon as the cache write succeeds — but introduces a window of data loss risk. If the cache node fails before the asynchronous write reaches the database, those writes are lost. Write-back is appropriate when write performance is critical and you can tolerate some data loss, such as tracking view counts or analytics events.

**Write-around** bypasses the cache entirely on writes: data goes directly to the database, and the cache is only populated when data is subsequently read. This avoids polluting the cache with data that may only be written once and never read (such as log records or one-time upload metadata). The cost is that the first read after a write always misses the cache. Write-around works well when your write pattern produces data that is rarely read back through the cache.

## Cache Invalidation

Cache invalidation — deciding when and how to remove or update stale entries from the cache — is famously described as one of the two hard problems in computer science (along with naming things and off-by-one errors). The difficulty is that a cache by definition holds copies of data, and whenever the original data changes, all copies must either be updated or discarded.

**TTL-based invalidation** is the simplest approach: set a time-to-live on every cache entry. After TTL seconds, the entry expires automatically. The system always serves data that is at most TTL seconds old. The challenge is choosing the right TTL — too short and you get low hit ratios; too long and users see stale data. TTL is appropriate when some staleness is acceptable and the update frequency of the underlying data is predictable.

**Active invalidation** (also called cache busting) involves explicitly removing or updating cache entries when the underlying data changes. When a user updates their profile, the application explicitly deletes or overwrites the `user:12345:profile` cache key. Active invalidation provides stronger freshness guarantees but requires the write path to have knowledge of all the cache keys that must be invalidated — which becomes complex when a single database row is referenced by many cache keys (for example, a product price change might affect many cached search results).

**Event-driven invalidation** uses a messaging system: when data changes, an event is published to a message queue or event bus, and cache invalidation consumers subscribe to relevant events and purge the appropriate cache keys. This decouples the write path from the cache invalidation logic and works well in microservice architectures where different services may cache the same underlying data.

## Redis vs Memcached

Redis and Memcached are the two dominant open-source in-memory caching systems. Choosing between them depends on what features your use case requires.

**Redis** is a single-threaded in-memory data structure server. Beyond simple key-value storage, it supports strings, hashes, sorted sets, lists, sets, streams, geospatial indexes, and more. This rich data model allows Redis to serve as more than a cache: it is used for session storage, leaderboards, pub/sub messaging, rate limiting, and distributed locks. Redis supports optional persistence — it can snapshot data to disk (RDB) or log every write operation (AOF) — so a Redis instance can survive a restart without losing its contents. Redis also supports clustering for horizontal scaling and replication for high availability. If you need data structures beyond simple strings, persistence, or any of Redis's extended features, Redis is the choice.

**Memcached** is a multi-threaded in-memory key-value store. It is simpler than Redis by design: it stores only flat string values (no data structures), has no persistence, and has minimal operational complexity. Its multi-threaded architecture means it can take better advantage of multiple CPU cores for plain cache workloads, and its simpler model makes it slightly faster for straightforward get/set operations at extreme throughput. If your use case is purely high-volume key-value caching of serialized objects and you do not need any of Redis's extended features, Memcached remains a strong choice.

In practice, Redis has become the default choice for most new systems due to its versatility. Memcached remains relevant primarily in organizations that already operate it at scale and have not found a reason to migrate.
