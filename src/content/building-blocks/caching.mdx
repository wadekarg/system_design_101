<Callout type="analogy">
Think of a **cache** like keeping your most-used spices on the counter instead of walking to the pantry every time you cook. The counter (fast storage) holds copies of what you reach for constantly, so you skip the slow trip.

The catch is the same one every kitchen has: the counter copy can go **stale**. If you refill the pantry jar but forget the counter one, you're cooking with the old stuff. That single problem — keeping the copy in sync with the real thing — is what makes caching genuinely hard.
</Callout>

## What a cache actually is

A **cache** is a layer of fast storage that sits between a client and the real source of data. When some data is **expensive to produce** — a database query, a heavy computation, a call to another service — you stash the result so the *next* request for it comes back from fast storage (usually RAM) instead of redoing the work.

The core trade-off is **freshness versus speed**. A cached value is a copy, and copies drift from the original over time. The longer it lives in the cache, the more likely it's **stale**.

So caching shines for data that is:

- **Read often** — you get many hits per stored value.
- **Changed rarely** — the copy stays valid longer.
- **Tolerant of slight staleness** — a few seconds old is fine.

Profile pictures, product catalog entries, rendered HTML fragments, and expensive aggregates are natural fits. Account balances and inventory counts, where being wrong costs money, need more care.

<Callout type="tip">
In practice this is often your biggest single win. One cache hit that skips a 50 ms database query can halve a page's load time — and putting a cache in front of a hot database can shed **90%+ of its query load**, letting the same hardware serve far more traffic.
</Callout>

## Hits, misses, and the number you watch

A **cache hit** is when the data is already in the cache and served directly. A **cache miss** is when it isn't — the system falls back to the source, fetches the value, stores it, and returns it. The next request for that same value hits.

The metric that tells you if the cache is earning its keep is the **hit ratio** — the fraction of requests served from cache. A 95% hit ratio means only 5% of requests reach the database. A **low hit ratio** usually means one of three things: the working set is too big for the cache, the keys are too specific (so nothing gets reused), or data is being evicted too aggressively.

## Where you can put a cache

Caches live at several layers, each trading latency for reach.

- **Client-side** — in the browser or a mobile app. Lowest possible latency (no network hop) but **per-user** and hard to invalidate server-side.
- **CDN** — copies at edge locations near users. A CDN hit costs a fraction of a millisecond versus a trip to a distant origin. (Covered fully in the CDN topic.)
- **Server-side** (Redis / Memcached) — the most common app-level cache. Your servers check it before the database, and because it's **shared**, a value cached by one server is instantly visible to all of them.
- **Database-level** — buffer pools that keep hot disk pages in RAM. Lower-level and automatic; MySQL's old query cache was removed in 8.0.

## Eviction: what to drop when it's full

A cache has finite room. When it fills, the **eviction policy** decides who gets kicked out.

| Policy | Evicts | Best for | Watch out for |
|---|---|---|---|
| **LRU** (Least Recently Used) | Whatever hasn't been touched in the longest | Most general workloads — the safe default | Slight overhead tracking access order |
| **LFU** (Least Frequently Used) | Whatever has the lowest access count | Steady favorites amid bursty traffic | Cache pollution — old hits linger too long |
| **FIFO** (First In, First Out) | The oldest entry, ignoring usage | Simple, predictable needs | Ignores access patterns; rarely ideal |
| **TTL** (Time To Live) | *Expires* entries after a set lifetime | Bounding staleness, not making room | It's a freshness tool, not a capacity tool |

**LRU** is the default for good reason: recently used data tends to be used again soon. **TTL** isn't really an eviction policy — it caps how *old* a value can get, and it's your main lever for freshness. Without a TTL, stale data can sit around indefinitely.

## Write strategies: what happens when data changes

When a value is written or updated, the **write strategy** decides how the cache and database stay in step.

| Strategy | How writes flow | Upside | Downside |
|---|---|---|---|
| **Write-through** | Write cache **and** database together, ack only when both succeed | Cache is always consistent with the DB | Every write pays full DB latency |
| **Write-back** | Write cache now, flush to DB asynchronously later | Very fast writes | Data loss if the cache dies before flushing |
| **Write-around** | Write straight to the DB, skip the cache | Cache never fills with write-only junk | First read after a write always misses |

**Write-through** trades speed for safety — no inconsistency window, but no write speedup either. **Write-back** is the opposite: blazing writes, but a crash before the flush loses data (fine for view counts, risky for orders). **Write-around** keeps the cache clean when data is written once and rarely read back, like log records.

## Cache invalidation: the genuinely hard part

**Cache invalidation** — deciding when to remove or refresh stale entries — is famously one of the two hard problems in computer science (along with naming things, and off-by-one errors). The trouble is structural: a cache holds *copies*, and every time the original changes, every copy must be updated or thrown away.

- **TTL-based** — give every entry a lifetime; it auto-expires. Simplest approach. The whole game is picking the TTL: **too short** and your hit ratio tanks; **too long** and users see stale data.
- **Active (cache busting)** — the write path explicitly deletes or overwrites the key when data changes (update a profile, drop `user:12345:profile`). Strong freshness, but the writer must know *every* key affected — which gets ugly when one row feeds many cached results.
- **Event-driven** — the writer publishes a "this changed" event; invalidation consumers subscribe and purge the right keys. Decouples the write path from the cache, which is why it wins in microservice setups where several services cache the same data.

## Where this shows up in real systems

- **Product catalogs / pricing** → read-heavy, changes a few times a day → cache with a modest TTL; the occasional stale price is acceptable.
- **User sessions / auth tokens** → read on nearly every request → server-side cache (often Redis) shared across all app servers.
- **View counts / likes / analytics** → write-heavy, loss-tolerant → write-back so the flood of increments doesn't cripple the database.
- **Static assets / images / JS bundles** → rarely change, globally requested → CDN edge caching with long TTLs and content-hashed URLs.
- **Leaderboards / rate limiters** → need atomic counters and sorted structures → Redis, using it as more than a plain cache.

<Callout type="warning">
The classic ways caching bites you:

- **Cache stampede (thundering herd)** — a hot key expires and thousands of concurrent misses hammer the database at once. It can take the origin down.
- **Staleness** — users see old data because a TTL is too long or an invalidation was missed.
- **Invalidation gaps** — a value changes but its cache key never gets busted, so the stale copy lives on until (if ever) it expires.

The trap underneath all three: treating the cache as the source of truth. It isn't — it's a **best-effort copy**, and your design has to assume it can be wrong.
</Callout>

## Handling the pressure points

- **Stampede?** → add **random jitter** to TTLs so keys don't expire in lockstep, use a **lock (single-flight)** so one request refills while the rest wait, and consider **probabilistic early expiration** — refresh a hot key slightly before it dies, under low load.
- **Staleness?** → shorten the TTL for data that matters, or switch to **active/event-driven invalidation** so updates propagate immediately instead of waiting out a clock.
- **Invalidation gaps?** → keep your key scheme predictable and centralized, and prefer **event-driven purges** so the write path doesn't have to remember every downstream cache by hand.

## Alternatives & related ideas

<Callout type="alternative">
Caching isn't the only way to make reads cheap. **Read replicas** spread query load across copies of the database when the bottleneck is throughput, not per-query cost. **Materialized views** precompute expensive aggregates inside the database itself. A **CDN** is really just a cache pushed to the network edge for geographically spread users. And sometimes the honest answer is *don't cache* — if data must be exactly correct on every read (a bank balance, remaining inventory), reach for the source of truth and optimize *it* instead of layering a copy you'll have to keep honest.
</Callout>

## Summary

A **cache** keeps a fast copy of expensive data so you stop redoing slow work, and it's often the biggest single performance win you can make. Reach for it when data is **read often, changed rarely, and okay to be slightly stale**, and watch the **hit ratio** to know it's working. Pick an eviction policy (**LRU** by default) and a write strategy that matches your tolerance for latency versus data loss. The hard part is always **invalidation** — bound staleness with TTLs, bust keys actively or via events when correctness matters, and defend the hot keys against **stampedes** with jitter and locking. Above all, never trust the cache as the source of truth; it's a copy that can be wrong.
