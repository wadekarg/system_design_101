<Callout type="analogy">
Imagine a busy library with one master copy of every book, kept behind the
front desk. Only the **head librarian** is allowed to edit that master copy —
crossing out a line, adding a page. But hundreds of people want to *read* those
books at once.

So the library prints copies and puts them on shelves all over the building.
Readers grab whatever copy is nearest, and the head librarian's edits are
carried out to every shelf. That's **replication**: one authoritative copy for
writes, many copies for reads — with the catch that a freshly-edited page takes
a moment to reach the far shelves.
</Callout>

## What replication actually does

**Database replication** means copying your data from one node onto one or more
other nodes. The original is the **leader** (or primary); the copies are
**followers** (or replicas). Every write applied to the leader is streamed to
the followers so they hold the same data.

It buys you two things at once:

- **High availability** — if one node dies (and it will, eventually), the others
  keep serving data. A single node is a **single point of failure**.
- **Read scaling** — one machine has a hard ceiling on reads per second. Spread
  reads across many replicas and that ceiling lifts.

The whole game is keeping the copies in sync. Every write on the leader must
**eventually** reach every follower. When writes arrive faster than they
replicate — or a follower drops offline — the copies drift apart, and how you
handle that drift is what separates the replication strategies below.

## Leader-Follower: the default shape

The most common setup is **leader-follower** (also called primary-replica). One
node is the leader, and **all writes go through it**. The leader applies each
write, records it in a **replication log**, and ships those log entries to its
followers. Each follower replays the log in the same order and lands on the same
state. Reads can come from the leader *or* any follower.

This fits **read-heavy** apps perfectly. A social feed might be 1% writes (posts,
likes) and 99% reads (loading feeds, profiles). All 1% hits the leader; the 99%
fans out across a dozen followers. Add another follower, get more read
capacity — no extra write cost beyond replicating to it.

It also gives you a recovery path: a follower that's caught up can be
**promoted** to leader when the old one dies.

<Callout type="tip">
In practice, replication lag on a healthy leader-follower cluster is single-digit
**milliseconds**. Postgres, MySQL, and MongoDB all ship this out of the box —
you point an app's "read" connections at replicas and its "write" connection at
the primary, and you've scaled reads without touching your schema.
</Callout>

## Synchronous vs Asynchronous: the core dial

The single most important decision is **whether the leader waits for followers
to acknowledge a write before telling the client "done."**

In **synchronous replication**, the leader sends the write to a follower and
**waits** for its acknowledgement before confirming to the client. The upside is
the strongest guarantee: if the leader dies one instant later, a fully-updated
follower is *guaranteed* to exist, so **no data is lost**. The cost is latency —
every write now pays for an extra network round-trip, and if the synchronous
follower goes offline, the leader **blocks all writes** until it's back.

In **asynchronous replication**, the leader writes locally, confirms to the
client **immediately**, then ships the write to followers in the background.
Writes are fast and a slow follower never blocks you. The risk: if the leader
crashes before those writes replicate, they're **gone**.

| | Synchronous | Asynchronous | Semi-synchronous |
|---|---|---|---|
| Write latency | Higher (waits for follower) | Lowest (local only) | Slightly higher |
| Data loss on leader crash | None | Possible | None (one sync follower) |
| Follower down blocks writes? | Yes | No | No (others are async) |
| Best for | Money, orders, critical writes | Caches, analytics, feeds | Most production databases |

<Callout type="tip">
Most real deployments pick the middle: **semi-synchronous** — exactly *one*
follower is synchronous (so you never lose an acknowledged write) while the rest
are asynchronous (so a single slow replica can't freeze the whole system). It's
the default sweet spot in production MySQL and Postgres setups.
</Callout>

## Multi-leader and leaderless: when one leader isn't enough

A single leader is a bottleneck for users far from it. Two variations relax that.

**Multi-leader** (active-active) puts a leader in each data center. Users write
to the *nearest* leader, and leaders replicate to each other — great for
geographically spread writes. The catch is **write conflicts**: if two users
edit the same record in different regions at once, both leaders accept, and there
is no obvious winner. You need conflict resolution — **last-write-wins** (simple
but loses data and trusts clocks), **merge**, or kicking it back to the app.

**Leaderless** (the Dynamo model, used by **Cassandra** and **Riak**) drops the
single leader entirely. A client writes to *many* replicas at once; the write
succeeds once a **quorum** of **W** out of **N** nodes acknowledges. Reads hit
**R** replicas and take the newest value.

The magic invariant is **W + R > N**. With N=5, W=3, R=3, any read set of 3 and
any write set of 3 *must* overlap on at least one node — so a read always sees
the latest write. Tune W and R to slide between consistency and availability.

| | Single-leader | Multi-leader | Leaderless |
|---|---|---|---|
| Who accepts writes | One node | One per region | Any replica (quorum) |
| Write conflicts | Impossible | Must be resolved | Resolved via versioning |
| Geo write latency | High for far users | Low everywhere | Low everywhere |
| Consistency | Strong-ish | Eventual | Tunable (W/R) |
| Complexity | Lowest | Highest | High |

## Where this shows up

- **Read-heavy web apps (social, e-commerce catalogs)** → single-leader with many
  async followers, because reads dwarf writes and stale-by-milliseconds is fine.
- **Banking / payments / order systems** → synchronous or semi-sync, because
  losing an acknowledged write is unacceptable even if it costs latency.
- **Global collaborative apps / multi-region SaaS** → multi-leader, because users
  worldwide need low write latency and the app can define conflict rules.
- **Always-on, high-write stores (Cassandra behind messaging, IoT, activity
  feeds)** → leaderless, because tolerating node failure without blocking writes
  matters more than reading the very latest value.

## Pressure points: how replication breaks

<Callout type="warning">
Three traps bite almost everyone:

- **Replication lag → stale reads.** A user updates their email, sees "saved,"
  then a read from a lagging follower shows the *old* value — a
  **read-your-own-writes** violation. It looks like your write failed when it
  didn't.
- **Async data loss.** With asynchronous replication, a leader crash *after*
  confirming but *before* replicating silently loses those writes. Fine for a
  cache, catastrophic for a payment.
- **Split-brain.** During a network partition, two nodes both believe they're the
  leader, both accept writes, and the data **diverges** into two conflicting
  histories that are painful to merge.
</Callout>

## Handling the pressure points

- **Beat stale reads** by routing a user's post-write reads to the leader, or by
  tracking each write's **replication position** and refusing replicas that
  haven't caught up to it, or by pinning a user to one replica (sticky sessions).
- **Bound data-loss risk** with **semi-synchronous** replication — one sync
  follower guarantees no acknowledged write vanishes, without the cost of making
  *every* follower synchronous.
- **Prevent split-brain** with **quorum**: a node can only become leader if a
  **majority** of the cluster agrees. On a partition, only the larger half forms
  a quorum; the smaller half goes read-only. Add **fencing tokens** — a
  monotonically increasing number stamped on every write — so storage rejects a
  stale ex-leader's late writes.
- **Fail over smartly** by promoting the *most caught-up* follower (smallest lag)
  to minimize the data-loss window. Tools like **Patroni** (Postgres) automate
  detection, quorum election, and promotion.

## Alternatives & related ideas

<Callout type="alternative">
Replication copies *all* the data to every node — it scales **reads** and
**availability**, not write throughput or storage. When one machine can't hold
the data or absorb the *writes*, you need **sharding** (partitioning): split the
data into disjoint pieces across nodes. In real systems you usually combine
both — **shard** for write/storage scale, then **replicate each shard** for
availability and read scale. And when even eventual consistency across regions is
too weak, reach for **consensus systems** (Raft/Paxos, e.g. etcd or Spanner) that
give strong consistency at a higher latency cost.
</Callout>

## Summary

Replication keeps copies of your data on multiple nodes so reads scale and a dead
machine doesn't take you down. The **leader-follower** model — one writable
leader, many readable followers — is the default for read-heavy apps. The core
dial is **synchronous** (no data loss, higher latency) versus **asynchronous**
(fast, but risks losing writes on a crash), with **semi-synchronous** as the
common compromise. Watch for **replication lag** causing stale reads and
**split-brain** during partitions — both are handled with careful read routing,
quorums, and fencing. When you need to scale *writes* or storage rather than
reads, replication isn't the answer — that's what **sharding** is for.
