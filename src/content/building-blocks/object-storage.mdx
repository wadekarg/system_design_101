<Callout type="analogy">
Think of object storage as a **giant valet coat-check for files**. You hand over
a coat (your file) and get back a **ticket** (a unique key). You don't get to
pick a hanger, arrange a closet, or reach in and sew a button on the coat while
it hangs there — you just drop the whole coat off and later show your ticket to
get the whole coat back.

That's the deal: **no folders, no partial edits — just "give me the whole file
for this ticket."** In exchange, the check-room is effectively infinite and
almost never loses your coat.
</Callout>

## What object storage actually is

Object storage manages data as **objects**: each object bundles the **file's
bytes**, a **unique key** (its identifier), and some **metadata**. That's it.

Unlike a file system with its nested directory tree, object storage uses a
**flat namespace**. Every object lives directly inside a container — a **bucket**
in Amazon S3 — addressed by a key string. No nested directories, no folders, no
path traversal.

The whole point is to store **huge volumes of large, unstructured files** with
**extreme durability** and **near-unlimited scale**, without the cost and
fragility of network file systems. Think billions of user photos, petabytes of
video, endless build artifacts and log archives.

There's a catch. You give up things file systems offer:

- **No partial writes** — you can't read a file's first kilobyte, tweak it, and
  write it back. Every write replaces the **whole object**.
- **No efficient appends** — you can't cheaply tack bytes onto an existing object.

That's fine for the target workloads: images, videos, backups, and logs are
**written once and read many times**.

## Object vs File vs Block storage

These three paradigms solve different problems. Pick the wrong one and you fight
the tool forever.

- **Block storage** slices data into fixed-size **blocks** and hands them to an
  OS or database, which builds its own structure on top. It's what your SSD and
  cloud volumes (AWS EBS) really are — fast, random-access, attached to **one**
  machine. Databases love it because they need low-latency access to specific
  pages on disk.
- **File storage (NAS)** presents the familiar **folder tree** over a network,
  so **many** machines can mount and share the same paths (AWS EFS, Azure Files).
  Great for shared config or legacy apps expecting a file path — but pricey and
  awkward for billions of independent files.
- **Object storage** (S3, Google Cloud Storage, Azure Blob) is built for **large
  unstructured files at scale**, accessed over **HTTP** with no mounting,
  massive concurrency, and automatic capacity growth — at a much lower price per
  gigabyte.

| Dimension | Block storage | File storage (NAS) | Object storage |
|---|---|---|---|
| Model | Raw fixed-size blocks | Hierarchical folder tree | Flat key → object |
| Access | Attached to one instance | Mounted by many instances | HTTP GET/PUT, no mount |
| Edits | Random read/write in place | Read/write/append in place | Overwrite whole object only |
| Latency | Microseconds | Low, network-bound | Tens of milliseconds |
| Scale | Volume-sized | Moderate | Effectively unlimited |
| Cost / GB | Highest | High | Lowest |
| Best for | Databases, OS disks | Shared file paths | Photos, video, backups, logs |

<Callout type="tip">
The latency gap is real: an object GET is **tens of milliseconds**, versus
**microseconds** for block storage. That's why databases never live on object
storage — they'd crawl. Object storage trades per-request speed for scale,
durability, and price.
</Callout>

## How it works under the hood

When you store an object, you write its **bytes**, a **key**, and optional
**metadata**. S3 then spreads copies **redundantly** across many physical
locations — multiple availability zones, sometimes regions — using **erasure
coding**.

S3 advertises **11 nines of durability** (99.999999999%). Concretely: store 10
million objects and you'd expect to lose **one every 10,000 years**. It hits
that not by keeping three full copies, but with erasure coding — a mathematical
scheme that splits data into redundant fragments, and **any sufficient subset of
fragments rebuilds the original** even if some are lost.

<Callout type="tip">
Durability is not availability. 11 nines means S3 won't **lose** your bytes; it
doesn't promise you can always **reach** them this instant. Availability is a
separate, lower number (S3 Standard targets ~99.99%), and outages do happen.
</Callout>

The key namespace is **flat**. A key like `photos/user123/avatar.jpg` is just a
string — the slashes are part of the key, not directories. Consoles fake folders
by grouping shared prefixes, but underneath every object sits directly in the
bucket. So `logs/2024/01/15/app.log` and `logs/2024/01/16/app.log` are two
independent objects that merely share a prefix.

Because access is plain HTTP, reads are ordinary **GET** requests, and
parallelism is free: a million clients can download at once with no
coordination, and S3 scales serving capacity automatically.

## S3 concepts worth knowing

S3 (Simple Storage Service) is the original and its vocabulary became the de
facto standard other services copy.

- **Buckets** — top-level containers with a **globally unique** name, a region,
  and access policies. Names are global because they appear in the URL
  (`my-bucket.s3.amazonaws.com`).
- **Versioning** — keeps every version of an object instead of overwriting.
  Upload a new `avatar.jpg` and the old one survives under its own version ID —
  your safety net against accidental overwrite or deletion.
- **Lifecycle policies** — automate management by age: move to a cheaper tier
  after 30 days, delete after 365. Ideal for data with a known shelf life like
  logs or temp artifacts.
- **Pre-signed URLs** — time-limited, cryptographically **signed** URLs that
  grant access to a **private** object. Your server generates one with your
  credentials; the client uses it to upload or download directly from S3 **with
  no credentials of their own**, until it expires.
- **IAM access control** — who can do what to which resource. Give app servers
  **read-only**, give CI/CD **write** to specific prefixes, and grant **delete**
  to almost nothing.

Objects also flow through **storage tiers** that trade retrieval speed and cost:

| Tier | Access pattern | Retrieval | Relative cost | Example use |
|---|---|---|---|---|
| Hot (Standard) | Frequent | Instant | Highest storage, cheap reads | Live site assets |
| Cool (Infrequent Access) | Occasional | Instant, per-GB read fee | Cheaper storage, pricier reads | Older user uploads |
| Archive (Glacier) | Rare | Minutes to hours | Cheapest storage, slow/costly reads | Compliance backups |

<Callout type="tip">
Lifecycle policies + tiers are where the money is saved. A log file might start
Hot, drop to Infrequent Access at 30 days, land in Glacier at 90, and get
deleted at 365 — all automatically, cutting storage cost by an order of magnitude
without anyone touching it.
</Callout>

## Where this shows up in real systems

- **Image / video hosting** (Instagram, YouTube) → billions of write-once,
  read-many blobs; unlimited scale and low cost per GB are exactly the fit.
- **Static website & app assets** (JS, CSS, fonts, images) → cheap origin store,
  fronted by a CDN so users never hit S3 directly.
- **Backups & disaster recovery** → 11 nines durability plus Glacier tiers make
  it the default cold-storage vault.
- **Data lakes & ML training sets** → petabytes of raw files that batch jobs read
  in parallel; throughput and price matter more than per-file latency.
- **Log & event archives** → high-volume, append-only-ish streams that lifecycle
  policies age into cheap tiers over time.

## Pressure points and how they bite

<Callout type="warning">
Object storage breaks in ways that surprise people who treat it like a file
system:

- **No in-place edits.** Changing one byte means re-uploading the whole object.
  Never model mutable, field-level data (like a live counter) as an object — use
  a database.
- **Listing is slow and costs money.** `LIST` on a bucket with millions of keys
  paginates and bills per request. Don't build features that scan the bucket at
  runtime; keep an **index in a database** instead.
- **Hot-key throttling.** Sequential or monotonic key prefixes
  (`2024-01-15T10:00:01`, `...:02`, …) pile requests onto one partition and get
  throttled. Add a **high-cardinality prefix** (a hash) so load spreads.
- **Eventual consistency on some operations.** Overwrites and (historically) list
  results can lag. S3 now offers strong read-after-write for new objects, but
  cross-region replication and other systems often don't — never assume a write
  is instantly visible everywhere.
</Callout>

### Handling the pressure points

- **Mutable data?** → keep it in a database; store only the immutable blob in
  object storage, with the DB row holding the object's key.
- **Need to enumerate objects?** → maintain your own index (a DB table of keys +
  metadata); reserve `LIST` for admin tooling, not the request path.
- **Write-heavy with time-based keys?** → prefix keys with a hash or reversed
  timestamp to avoid a hot partition.
- **Reading right after writing across regions?** → design for lag: poll,
  retry, or route reads to the region you wrote to until replication catches up.

## Alternatives & related ideas

<Callout type="alternative">
Reach for something else when object storage's constraints hurt:

- **Database (SQL / NoSQL)** for anything you need to **query, join, or update
  field-by-field** — store the blob in S3 and the queryable metadata in the DB.
- **Block storage (EBS)** when a database or app needs **low-latency random
  access** to a mounted disk.
- **File storage (EFS/NAS)** when **multiple machines must share a POSIX file
  tree** with real read/write/append semantics.
- **A CDN in front of S3** — not an alternative but a near-mandatory companion
  for static delivery (below).
</Callout>

For static asset delivery, **always pair object storage with a CDN**. Serving
straight from S3 means every request crosses the internet to one region and
racks up transfer costs. Put CloudFront or Cloudflare in front and repeat
requests are served from a nearby **edge cache** — only the first miss touches
S3 — slashing both latency and egress bills.

## Summary

Object storage is the internet's warehouse: a **flat key → object** model that
holds **large, unstructured, write-once files** at effectively unlimited scale,
**11 nines** of durability, and the lowest cost per gigabyte — accessed over
plain HTTP. It deliberately gives up **in-place edits, appends, and cheap
listing**, so it's wrong for mutable, queryable data (that's a database's job)
and for low-latency random access (that's block storage). Lean on **versioning,
lifecycle tiers, pre-signed URLs, and tight IAM** to run it safely, and watch for
**hot-key throttling** and **eventual consistency** at scale. And whenever you're
serving assets to users, **put a CDN in front** — object storage is the origin,
not the delivery network.
