<Callout type="analogy">
Think of a SQL database as a **giant spreadsheet with a strict librarian**. Every
sheet (a **table**) has a fixed set of columns, and the librarian refuses any row
that breaks the rules — no missing required fields, no order pointing at a customer
who doesn't exist.

That strictness feels like friction at first. But it's exactly why you can trust the
numbers: when money moves or an order ships, the librarian guarantees the books
always balance.
</Callout>

## Relational databases: tables with rules

A **relational database** stores data in **tables** — grids of **rows** (records) and
**columns** (attributes) — with a **predefined schema** that says which columns exist,
what type each holds, and what constraints apply (not null, unique, foreign key).

Tables connect through **foreign keys**. A row in `orders` has a `user_id` that
references the `id` column in `users` — that's how the database knows *which* user
placed *which* order.

The defining trait is **schema-first**: you define the structure *before* you insert
data. That has a cost — schema changes on big tables can be slow or need downtime —
but it buys you a guarantee. A `NOT NULL` column will never hold a null; a foreign
key will never point at a row that doesn't exist. Your application code can trust the
shape of every row it reads.

**SQL** (Structured Query Language) is the universal language for talking to these
databases. It's **declarative** — you describe *what* you want, and the database's
query planner figures out *how* to fetch it efficiently:

```sql
SELECT * FROM orders
WHERE user_id = 42 AND status = 'shipped'
ORDER BY created_at DESC LIMIT 10
```

<Callout type="tip">
The big three you'll meet in practice: **PostgreSQL** (the most feature-rich
open-source option), **MySQL** (ubiquitous in web apps), and **SQLite** (embedded
right inside an app — it's likely on your phone right now, powering apps you use daily).
</Callout>

## ACID: the four promises

**ACID** is the set of guarantees SQL databases make for **transactions** — groups of
operations treated as one unit. These promises are why SQL is the default whenever
correctness is non-negotiable.

| Property | Plain-English promise | The bank-transfer example |
|---|---|---|
| **Atomicity** | All-or-nothing | Debit + credit both happen, or neither does — no half-done transfer |
| **Consistency** | Only valid states | A transfer that would break a constraint is rejected whole |
| **Isolation** | No peeking at partial work | A concurrent reader sees the state *before* or *after*, never mid-update |
| **Durability** | Once committed, it stays | A crash a millisecond after commit can't lose the data |

- **Atomicity** — if you debit account A and the server crashes before crediting
  B, the debit rolls back. No inconsistent balances, ever.
- **Consistency** — every transaction moves the database from one valid state to
  another. Insert an order referencing a nonexistent user? Rejected.
- **Isolation** — concurrent transactions don't see each other's half-finished work.
  Tunable via **isolation levels** (Read Committed → Repeatable Read → Serializable);
  stronger isolation means more **lock contention**.
- **Durability** — achieved through **write-ahead logging (WAL)**: every change is
  written to a durable log *before* touching the main data files. After a crash, the
  database replays the WAL to restore committed state.

<Callout type="tip">
"Consistency" in ACID is not the same "consistency" as in the CAP theorem. ACID
consistency means *not violating your schema's rules*. CAP consistency means *every
node returns the latest write*. Same word, different worlds — a classic interview trap.
</Callout>

## Schema, normalization, and indexes

A good schema is the foundation of performance. **Normalization** organizes data so
each fact lives in exactly **one place**. Change a customer's name in one `customers`
row, and every order referencing that customer reflects it automatically through the
foreign key. Store the name on every order instead, and a rename means updating
thousands of rows — with a real risk of missing some.

But normalization can go too far. Highly normalized schemas need many **JOINs** to
rebuild a full view, and joins cost CPU. For read-heavy workloads, **denormalization**
— deliberately duplicating data to skip joins — is a common trade: a reporting table
might store pre-computed aggregates instead of re-running a huge `GROUP BY` every time.

An **index** is a separate data structure (usually a **B-tree**) the database keeps
alongside a table to speed up lookups. Without an index on `orders.user_id`, finding
matching rows means a **full table scan** — reading every row. With one, the database
walks the B-tree in **O(log n)** time.

<Callout type="tip">
Indexes aren't a minor tweak — they're often the difference between a **30-second**
query and a **2-millisecond** one on the same table. The first thing to check on a
slow query is almost always: is there an index on the column you're filtering by?
</Callout>

The catch is **write cost**. Every insert, update, and delete must update *all*
indexes on the table. A table with ten indexes does eleven writes per logical write —
one to the table, ten to the indexes. So index the columns your real queries filter,
join, and sort on, and delete indexes nothing uses.

## Joins: stitching tables back together

A **JOIN** combines rows from multiple tables using a related column — the practical
payoff of the relationships your foreign keys express.

- **`INNER JOIN`** — returns only rows with a match in *both* tables.
  `SELECT orders.id, users.name FROM orders INNER JOIN users ON orders.user_id = users.id`
  gives one row per order, tagged with its user's name.
- **`LEFT JOIN`** — returns *all* rows from the left table plus any matches on the
  right; unmatched left rows come back with NULLs. Perfect for "all users *and* any
  orders they've placed," including users with zero orders.

## Where this shows up

- **Payments, accounting, order management** → the canonical SQL use case. ACID makes
  atomic fund transfers safe; a mid-transfer crash still leaves the books balanced.
- **Reporting and analytics** → SQL's expressive joins, aggregations, and window
  functions let analysts answer new questions without shipping code.
- **Anything with rich relationships** → users → orders → line-items → products.
  Foreign keys and joins model this naturally; a key-value store would fight you.
- **Systems that need ad-hoc queries** → when you don't know tomorrow's question,
  SQL's flexibility beats a database tuned for one access pattern.

<Callout type="warning">
SQL breaks in predictable ways under load:

- **N+1 queries** — an ORM loads 100 orders, then fires one query *per order* for its
  user: 101 round trips instead of 1. Fix with **eager loading** (a JOIN or a single
  `WHERE id IN (...)` batch).
- **Missing indexes** — a query filtering on an unindexed column silently does a full
  table scan. Fine at 10k rows, catastrophic at 10M. Use `EXPLAIN` to catch it.
- **Lock contention** — high-isolation transactions holding locks on hot rows make
  others queue up, tanking throughput. Keep transactions short and touch fewer rows.
- **Write-scaling ceiling** — a single primary can only absorb so many writes. Past
  that, you need replication or sharding, and complexity jumps.
</Callout>

## Handling the pressure points

- **N+1 queries** → turn on eager/batch loading; log query counts per request in
  development so a stray N+1 is obvious before it ships.
- **Missing or wrong indexes** → run `EXPLAIN`/`EXPLAIN ANALYZE`, add indexes matching
  real WHERE/JOIN/ORDER BY columns, and drop unused ones so writes stay cheap.
- **Lock contention** → shorten transactions, lower the isolation level where safe, and
  reorder operations to grab locks in a consistent order to avoid deadlocks.
- **Read pressure** → add **read replicas** and route reads to them; cache hot queries.
- **Write pressure** → scale the primary vertically first (it goes a *long* way), then
  shard only when you truly must.

## Alternatives & related ideas

<Callout type="alternative">
When SQL's shape doesn't fit, reach for:

- **NoSQL (key-value, document, wide-column)** — when you need built-in horizontal
  write scaling or a flexible/evolving schema more than joins and multi-row transactions.
- **Replication** — copy the database to replicas to scale *reads* and add redundancy,
  without giving up the SQL model.
- **Sharding** — split one big table across machines to scale *writes*, at the cost of
  cross-shard joins and transactions.
- **Caching (e.g. Redis)** — put a fast layer in front of the database so hot reads
  never touch it at all.

The honest default: a single well-tuned PostgreSQL instance handles tens of thousands
of QPS and terabytes of data. Reach for the alternatives when you've *measured* that
you've outgrown it — not before.
</Callout>

## Summary

A SQL database is a strict, table-based store where a **schema** enforces the shape of
your data and **ACID** transactions guarantee correctness even through crashes — which
is why it's the default for money and orders. **Indexes** turn slow scans into
O(log n) lookups but tax every write, so index for your real queries. **Joins**
reconstruct relationships, but naive ORM use invites the **N+1 problem**. SQL scales
*up* effortlessly and *out* painfully; when you genuinely outgrow one machine, replicas
handle reads, sharding handles writes, and NoSQL becomes worth a look. Reach for those
only once you've measured the need — a single tuned instance takes most systems
surprisingly far.
