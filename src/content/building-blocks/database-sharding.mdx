<Callout type="analogy">
Imagine one librarian trying to run a library with **every book in the world**.
No matter how fast she is, there's only one desk — everyone lining up to check
out a book waits in the *same* queue, and the building physically can't hold that
many shelves.

**Sharding** is opening many branch libraries, each holding a *slice* of the
collection (A–F here, G–M there). Now checkouts happen in parallel at many desks.
The catch: to find *any* book you need a rule for which branch it lives in — and
a book that references three branches at once becomes a genuine headache.
</Callout>

## What sharding actually does

**Sharding** (also called **horizontal partitioning**) splits a database into
independent pieces called **shards**. Each shard holds a *subset* of the rows and
runs on its own database instance, potentially on its own hardware. Put all shards
together and you have the complete dataset.

Contrast this with **replication**, which copies the *whole* dataset onto multiple
machines. Replication scales **reads** — you spread queries across copies — but it
does nothing for **writes**, because every write still hits a single leader.

Sharding attacks exactly that ceiling. It spreads writes across multiple leaders
(one per shard), so total write throughput is roughly **N × one shard's throughput**
for N shards. That's how systems store the truly massive: Twitter keeps billions of
tweets by splitting them across hundreds of shards, each holding a manageable slice.

<Callout type="tip">
Reach for sharding **last**, not first. A well-tuned PostgreSQL box on modern
hardware handles billions of rows and thousands of writes/second. Push vertical
scaling and read replicas hard before you take on the operational tax of shards.
</Callout>

## First, the simpler cousin: vertical partitioning

Before splitting by rows, consider splitting by **columns**. **Vertical
partitioning** breaks a wide table into narrower ones. A `users` table with 50
columns might become:

- **`users_core`** — id, email, password hash — touched on *every* request.
- **`users_profile`** — bio, avatar, preferences — touched rarely.

Same rows, different columns. Keeping the hot columns compact means more rows fit
in memory and the cache works harder. **Horizontal partitioning (sharding)** is the
opposite cut: same columns, *different rows*. You reach for it when the problem is
the sheer number of rows and the write rate — not row width.

## Choosing how to split: the shard key

The **shard key** is the column whose value decides which shard a row lands on.
It's the single most consequential choice in a sharding design, because it dictates
both how evenly load spreads and how expensive your queries become.

| Strategy | How it maps keys | Range queries | Even distribution | Resharding | Watch out for |
|---|---|---|---|---|---|
| **Range** | Contiguous key ranges per shard | Cheap (one shard) | Poor | Easy-ish | Write hotspot on newest range |
| **Hash** | `hash(key) % N` | Expensive (all shards) | Excellent | Painful (rehash everything) | Range scans, migrations |
| **Geographic** | By region/country | Cheap within region | Uneven (busy regions) | Moderate | Regions differ in size |
| **Directory** | Lookup table per entity | Depends | Fully controllable | Easy (move a row) | Extra hop; directory is critical |

**Range-based** sharding gives cheap range scans ("users 500k–600k live on one
shard") but hotspots when new keys cluster at one end — auto-incrementing IDs or
timestamps dump every fresh write onto the current shard.

**Hash-based** sharding spreads writes perfectly evenly, even for sequential keys,
because a hash scatters consecutive values across shards. The price: range queries
now fan out to *every* shard, and resharding means rehashing and moving mountains
of data.

**Directory-based** sharding keeps a lookup table saying "user 12345 is on shard 4."
Maximally flexible — you can move one row anywhere without touching an algorithm —
but every query pays a directory round-trip, and that directory becomes a
must-be-up dependency.

<Callout type="tip">
Pick the strategy from your **access pattern**, not your gut. Mostly point lookups
by ID? Hashing spreads load beautifully. Lots of range/time-window scans? Range
sharding keeps them on one shard — you'll just have to manage the hotspot.
</Callout>

## Where this shows up in real systems

- **Twitter / tweet storage** → hash or Snowflake-style keys spread billions of
  writes evenly; timelines are pre-computed so no single shard is read hot.
- **Cassandra / DynamoDB** → consistent-hash the partition key by default, trading
  cheap range scans for painless scaling and even load.
- **Time-series / metrics (InfluxDB, Prometheus remote stores)** → range-shard by
  time *and* accept the "now" hotspot, because time-window queries dominate.
- **Multi-region SaaS** → geographic sharding pins EU customers to EU shards for
  latency *and* data-residency (GDPR) — even if regions aren't equally sized.
- **Large e-commerce** → shard orders by `customer_id` (co-location) so a customer's
  cart, orders, and history all live on one shard — no cross-shard joins on checkout.

## When shards break: the pressure points

<Callout type="warning">
**Hot shards & the celebrity problem.** If one shard takes 80% of the writes, you
paid for complexity and got 25% more capacity, not 8×. The classic case: a celebrity
with 100M followers whose rows all sit on one shard — every post hammers it while
the rest idle.

**Cross-shard joins are gone.** `orders JOIN users` is trivial in one database and
*impossible* across shards — no query planner spans machines. You fetch from shard A,
fetch from shard B, and join in application code: slower and more error-prone.

**Resharding is brutal.** With `hash(key) % N`, going 8→9 shards remaps nearly every
key. Mid-migration, a key might live in the old shard *or* the new one, and reads
must handle both.

**Global uniqueness breaks.** Each shard's auto-increment can hand out the same
integer, so `id = 42` is no longer unique across the cluster.
</Callout>

## Handling the pressure points

- **Hot shards / celebrities** → add a **random suffix** to the hot key to fan its
  rows across shards (gather at read time), **replicate** hot rows for read
  distribution, or serve **pre-computed/cached views** so the hot row never sits on
  the critical read path.
- **Cross-shard joins** → **co-locate** related data under the same shard key
  (a customer's orders on the customer's shard) so most joins stay single-shard.
- **Distributed transactions** → avoid 2PC where you can; design so a transaction
  touches one shard, or accept **eventual consistency** across shards.
- **Resharding** → use **consistent hashing** so a new shard only steals ~1/N of
  keys from its ring neighbor. Migrate via **dual-reads** (check both locations) or
  **blue-green** (fill a new cluster, then cut over).
- **Global IDs** → generate them centrally (**Snowflake**, **UUIDs**) or **encode
  the shard ID** into the key so it's unique by construction.

## Alternatives & related ideas

<Callout type="alternative">
Before sharding, exhaust the cheaper options. **Vertical scaling** (a bigger box)
carries you astonishingly far. **Read replicas** solve read-throughput problems
without touching your write path. **Caching** (Redis/Memcached) absorbs hot reads
so the database never sees them.

When you *must* distribute, **consistent hashing** is the routing layer that makes
resharding survivable, and a **NoSQL store** (Cassandra, DynamoDB, MongoDB) often
bakes sharding, rebalancing, and replication in so you don't hand-roll it. Reach for
manual sharding of a relational database only when these don't fit.
</Callout>

## Summary

Sharding **horizontally partitions** your data across independent shards so writes
and storage scale past a single machine — unlike replication, which only scales
reads. The **shard key** and strategy (range, hash, geographic, directory) decide
everything: range keeps scans cheap but risks hotspots, hashing spreads load evenly
but punishes range queries and resharding. The price of scale is real complexity —
**hot shards**, vanished **cross-shard joins**, painful **resharding**, and lost
**global uniqueness** — which you tame with co-location, caching, consistent hashing,
and central ID generation. Because that tax is steep, push vertical scaling, read
replicas, and caching to their limits first, and shard only when they demonstrably
can't keep up.
