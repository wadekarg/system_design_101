<Callout type="analogy">
Think of ordering food. **HTTP** is a takeout counter: *you* walk up, ask,
and get handed your order. If the kitchen invents a new dish, it has no way to
tell you — you'd have to keep walking back to ask "anything new?"

Real-time apps flip this. The kitchen (server) wants to shout "your order's
ready!" the instant it happens. The techniques below are different ways to keep
a line of communication open so the server can reach *you* — from "keep asking"
(polling) all the way to a two-way intercom (WebSockets).
</Callout>

## Why plain HTTP struggles with real-time

HTTP is a **request-response** protocol built around a **pull model**: the
client asks, the server answers, done. That's a perfect fit for fetching a page,
submitting a form, or querying an API — the client *knows* when it wants data.

**Real-time apps invert this.** A chat needs to push a message the moment it
arrives. A dashboard pushes metrics every second. A game pushes positions tens
of times per second. The server has data that must reach the client — but the
client has no idea *when* it'll arrive, so it can't know when to ask.

That mismatch is why a family of techniques exists, each trading off complexity,
infrastructure compatibility, and capability differently.

## Short polling: just keep asking

The simplest approach. The client sends a normal HTTP request on a **fixed
interval** ("anything new?"). If there's data, the server returns it; if not, an
empty response. Wait, ask again.

It needs **no special server support** — it's plain HTTP — and it's trivial to
implement. For low-frequency needs (refresh a dashboard every 30s, check a job
every 10s), it's entirely reasonable.

The pain shows up at scale. **100,000 users polling every 5 seconds = 20,000
requests/second**, most returning nothing. Drop the interval to 1 second for
snappiness and you 5× the waste. Short polling doesn't scale to high-frequency,
high-concurrency real-time.

## Long polling: ask, but wait for an answer

Long polling reduces empty responses. Instead of answering immediately, the
server **holds the request open until it actually has data**, then responds and
closes. The client instantly reopens a new request — a continuous cycle.

To the client it feels like a **stream**: it's always waiting, and responses
arrive the moment there's news. To the server, it means holding **many idle open
connections** and answering them only when relevant events fire.

<Callout type="tip">
Long polling runs over standard HTTP, so it sails through proxies, CDNs, and
corporate firewalls that choke on WebSockets — its main selling point. The catch:
every message still pays a full HTTP round trip (kilobytes of headers), and the
server must juggle many idle connections. Event-driven servers (Node.js, Nginx)
do this cheaply; **thread-per-connection servers burn one OS thread per idle
client** and fall over.
</Callout>

## Server-Sent Events: a one-way firehose

**SSE** is an HTML5 web standard for pushing a stream of events over a single
long-lived HTTP connection. The browser opens it with the `EventSource` API, and
the server keeps it open indefinitely, sending events as formatted text lines.

SSE is **strictly one-directional** — server to client only. To send data *up*,
the client uses a separate HTTP request. For many cases that's plenty: live
scores, news feeds, stock tickers, progress bars, and notifications all flow
one way.

<Callout type="tip">
SSE has **automatic reconnection built in**. If the connection drops, the
browser reconnects on its own, and if the server tagged events with IDs, the
client replays the `Last-Event-ID` header so the server resumes right where it
stopped. You get reliability for free — no manual reconnect logic like
WebSockets demand. Over HTTP/2, many SSE streams multiplex onto one TCP
connection, keeping per-stream overhead low.
</Callout>

## WebSockets: a two-way intercom

WebSockets give you **full-duplex** communication over a single persistent TCP
connection. Either side can send at any time, with tiny overhead once connected.

It starts as a normal HTTP request carrying an `Upgrade: websocket` header. If
the server agrees, it replies **101 Switching Protocols** and the connection
upgrades from HTTP to the WebSocket protocol. From there, both sides exchange
**WebSocket frames** — data units with just a **2–10 byte header**, versus HTTP's
kilobytes per request.

That low per-message cost plus two-way flow makes WebSockets the right pick for
**high-frequency bidirectional** work: chat (messages both ways), multiplayer
games (actions up, state down), collaborative editing (every keystroke), and
live trading (orders up, prices down).

<Callout type="tip">
WebSockets are **persistent and stateful** — the connection lives until closed,
so there's no repeated handshake. That's a performance win but a scaling headache
(next section). And some corporate proxies and CDNs that terminate HTTP can't
handle the upgrade — which is exactly why **SSE or long polling make good
fallbacks** when compatibility is uncertain.
</Callout>

## Comparing the four

| Technique | Direction | Connection | Infra compatibility | Best for |
|---|---|---|---|---|
| **Short polling** | Client pulls | New request each time | Universal | Low-frequency status checks |
| **Long polling** | Client pulls (held) | Reopened per message | Universal | WebSocket fallback, blocked networks |
| **SSE** | Server → client only | One long-lived HTTP | Good (HTTP/1.1 & HTTP/2) | One-way feeds, notifications |
| **WebSockets** | Both ways (full-duplex) | One persistent TCP | Fair (proxies may block) | Chat, games, collab, trading |

## Where this shows up

- **Job-status dashboards, config refresh** → **short polling**. Delay is fine,
  audience is small, and plain HTTP means nothing to operate.
- **Live scores, stock tickers, news feeds, progress bars** → **SSE**. Data flows
  one way and the free reconnect-and-resume keeps it robust.
- **Slack / Discord chat, multiplayer games, Google Docs, trading desks** →
  **WebSockets**. Both sides talk constantly and latency matters.
- **Legacy or locked-down corporate networks** → **long polling**. When the
  WebSocket upgrade is blocked, this is the compatible workhorse.

## Pressure points

<Callout type="warning">
The hard part isn't opening a connection — it's **keeping a million of them alive
and reachable**.

- **Connection scaling** — each WebSocket/SSE pins a client to *one* server
  instance and eats file descriptors and memory. Idle isn't free.
- **Stale connections** — networks drop connections silently. Without a
  **heartbeat**, a server can hold thousands of dead sockets it thinks are live.
- **Load-balancer stickiness** — a message that originates on server 1 can't
  reach a client attached to server 3 unless you route it there.
- **Proxy/LB timeouts** — many proxies kill "idle" connections after ~30–60s,
  silently breaking long-lived streams.
</Callout>

## Handling the pressure points

- **Scale connections** with event-driven servers (Node.js, Nginx, Go) that
  handle idle connections cheaply, and shard clients across many instances.
- **Reconnect + heartbeat** — send periodic ping/pong frames to keep connections
  marked active and to detect dead peers fast; on the client, reconnect with
  exponential backoff. SSE gives you reconnect and `Last-Event-ID` resumption for
  free; WebSockets you wire up yourself.
- **Load-balancer stickiness** — **sticky sessions** (route a client to the same
  server by IP or cookie) keep a client's messages on one instance, but offer no
  graceful failover: if that server dies, its connections drop.
- **Cross-server routing** — put a **pub/sub backend (e.g. Redis Pub/Sub)** behind
  the WebSocket tier, keyed by client ID. Any server publishes a message; the
  server holding that client's socket receives it and forwards it. This decouples
  message delivery from connection state so any server can reach any client.
- **Beat proxy timeouts** — set the heartbeat interval *below* the proxy's idle
  timeout so the connection never looks idle.

## Alternatives & related ideas

<Callout type="alternative">
Don't hand-roll connection management if you can avoid it. **WebSocket libraries**
(Socket.IO, Phoenix Channels, SignalR) bundle reconnection, heartbeats, and
transport fallback (WebSocket → long polling) automatically. **Managed services**
(AWS API Gateway WebSockets, Ably, Pusher, PubNub) run the fan-out and scaling
for you.

For the delivery layer behind any of these, real-time systems lean on
**message queues / pub-sub** ([message queues](message-queues)) to route events
between services and the connection tier. And if you only need occasional
server-to-client nudges, a plain **push notification** service may beat holding
connections open at all.
</Callout>

## Summary

HTTP pulls, but real-time apps need the server to **push** — so you keep a channel
open. **Short polling** just re-asks on a timer (simple, wasteful at scale).
**Long polling** holds each request until there's news (universal compatibility,
per-message HTTP overhead). **SSE** streams one way with free reconnect (ideal for
feeds and notifications). **WebSockets** give low-overhead two-way traffic (chat,
games, collab) at the cost of stateful connections. Pick by **direction of data
flow and infrastructure constraints**, and once you go stateful, budget for the
real work: heartbeats, reconnection, sticky sessions or a **pub/sub backend**, and
proxy timeouts.
