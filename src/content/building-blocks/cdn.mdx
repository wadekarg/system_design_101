## What is a CDN

A Content Delivery Network (CDN) is a geographically distributed network of servers — called Points of Presence (POPs) or edge nodes — that cache copies of your content closer to your users. Instead of every request traveling all the way to your origin server (which might be in a single data center in Virginia or Frankfurt), users are served from a POP that may be in the same city or country as they are.

The motivation is physics: light travels through fiber optic cable at roughly 200,000 kilometers per second. A request from a user in Sydney to a server in London covers approximately 16,000 kilometers of cable (accounting for routing), which means the round-trip adds at least 160 milliseconds of latency before any server processing happens. A CDN POP in Sydney or Singapore serves that same user with 5–10 milliseconds of round-trip latency. For most web assets — images, JavaScript bundles, stylesheets, fonts, video — this latency difference is the dominant factor in perceived page load speed.

CDNs operate at massive scale. Major CDNs like Cloudflare and Akamai have hundreds of POPs distributed across dozens of countries. Collectively they handle a substantial fraction of all global internet traffic. This scale also means CDNs can absorb traffic volumes that would overwhelm most origin servers, making them a natural DDoS mitigation layer in addition to their latency benefits.

## How CDNs Work

When a CDN receives a request from a user, it checks whether it has a valid cached copy of the requested resource. If it does (a cache hit), it serves the response directly from its local cache with no connection to your origin. If it does not (a cache miss), it forwards the request to your origin server, receives the response, caches the response locally, and returns it to the user. All subsequent requests for the same resource from users near the same POP will be cache hits.

The CDN uses the Cache-Control and Expires HTTP response headers sent by your origin to decide how long to cache the response. A JavaScript bundle with a content-addressed filename (like `app.a3f92c.js`) can be cached indefinitely — if the content changes, the filename changes. An HTML page that changes daily might be cached for one hour. An API response for a user's account details probably should not be cached at all.

CDN cache keys are typically derived from the full URL, including query parameters. `https://example.com/api/products?category=shoes` and `https://example.com/api/products?category=hats` are distinct cache keys. Some CDNs allow you to configure custom cache key rules — for example, ignoring certain query parameters that have no effect on the response, which increases hit rates.

## Push vs Pull CDN

CDNs can be configured to populate their caches in two fundamentally different ways, with different operational implications.

A **pull CDN** (the more common model) operates lazily. When a user requests a resource that is not yet cached at the POP nearest to them, the CDN pulls the content from your origin server on demand, caches it, and returns it. The first request for a given resource at a given POP incurs the origin round-trip; all subsequent requests are cache hits. The primary advantage of the pull model is simplicity: you do not need to do anything special when you deploy new content. The CDN automatically picks up new content as users request it, and old cached content expires according to TTL settings. Pull CDNs are the right choice for most websites and APIs.

A **push CDN** requires you to explicitly upload content to the CDN's storage. Your deployment pipeline pushes assets to the CDN's servers, and the CDN serves them from there. You explicitly control what is cached, where it is distributed, and when it is updated. Push CDNs are appropriate for content you know will be accessed heavily and predictably — a video streaming platform that pre-positions a new movie release across all POPs before a scheduled premiere, for example. The operational cost is higher: you must build the push step into your deployment pipeline and explicitly manage cache invalidation when content changes.

## Cache-Control Headers

The CDN's caching behavior is primarily governed by the HTTP Cache-Control response header. This header is sent by your origin server and instructs both CDNs and browsers how to cache the response.

`max-age=N` tells clients (browsers and CDNs alike) to cache the response for N seconds. `s-maxage=N` does the same but applies only to shared caches (CDNs) — it overrides `max-age` for CDN caching while allowing a different TTL for the browser cache. This lets you say "CDN, cache this for one day; browser, cache this for ten minutes" with a single header.

`no-cache` is commonly misunderstood: it does not mean "do not cache." It means "cache this, but always revalidate with the origin before serving it." The CDN stores the response but sends a conditional request (with an `If-None-Match` or `If-Modified-Since` header) to the origin on each subsequent request. If the content has not changed, the origin returns a 304 Not Modified (with no body), and the CDN serves its cached copy. `no-store` truly prevents caching.

`public` marks a response as cacheable by any cache (including CDNs). `private` marks a response as cacheable only by the browser, not by CDNs — important for responses that contain user-specific data, such as account details or personalized recommendations.

Deploying static assets with content-addressed filenames and `Cache-Control: public, max-age=31536000, immutable` (one year, immutable) is the gold standard for frontend performance: the browser and CDN cache them essentially forever, and the only way to serve updated content is to change the filename, which is what modern build tools (Webpack, Vite) do automatically when content changes.

## CDN Benefits Beyond Speed

Latency reduction is the headline benefit of CDNs, but modern CDNs offer a range of additional capabilities that are valuable independent of caching.

**DDoS protection** is perhaps the most important secondary benefit. Because CDN POPs collectively handle enormous traffic volumes, they can absorb volumetric DDoS attacks that would instantly overwhelm a typical origin server. Cloudflare, for example, has mitigated attacks exceeding 1 terabit per second. The CDN identifies and drops attack traffic at the network edge, protecting your origin from even seeing the traffic.

**TLS termination** at the edge means that HTTPS handshakes happen at the nearest POP, not at your origin. The TLS handshake adds 1–2 round-trips of latency; by terminating it at a POP close to the user rather than at an origin on the other side of the world, CDNs significantly reduce the cost of establishing secure connections. Traffic between the CDN POP and your origin can use a separate, persistent TLS session that is not on the critical path for each user request.

**Web Application Firewall (WAF)** capabilities built into CDNs like Cloudflare and AWS CloudFront allow you to inspect and filter incoming requests for malicious patterns — SQL injection attempts, common exploit signatures, bots — at the network edge before those requests ever reach your application code.

**Geographic blocking and traffic management** allow you to restrict content to specific countries or regions, route traffic to different origins based on geography, or implement A/B tests at the CDN layer.

## Popular CDNs

**Cloudflare** is the most widely used CDN by site count. Beyond caching, it offers DDoS protection, WAF, DNS, SSL certificates, Cloudflare Workers (serverless compute at the edge), and a global network of hundreds of POPs. Its free tier makes it accessible to small projects, while its enterprise tier handles Fortune 500 workloads.

**Amazon CloudFront** integrates natively with the AWS ecosystem — S3, ALB, Lambda@Edge, AWS Shield — making it the natural choice for applications already running on AWS. CloudFront's edge locations are deeply integrated with AWS's backbone network.

**Akamai** is the oldest and one of the largest CDNs, with a particularly strong presence in enterprise and media streaming. It is the CDN of choice for organizations with the most demanding performance and compliance requirements.

Modern CDNs are increasingly capable of caching not just static assets but also API responses and even dynamically generated HTML (with appropriate cache keys and TTLs). Static assets like images, JavaScript bundles, fonts, and videos remain the ideal CDN use case — their content is stable, they are large (so avoiding the origin round-trip has high value), and they are requested frequently enough to achieve high hit rates.
