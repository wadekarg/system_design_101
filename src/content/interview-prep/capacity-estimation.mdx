<Callout type="analogy">
Capacity estimation is like planning groceries for a party. You don't count out exactly 137 chips per guest — you think "about 30 people, roughly 2 handfuls each, so a few big bags." Rough, but good enough to know whether you need one cart or three.

The goal isn't precision. It's landing on the **right order of magnitude** so you don't show up with a single bag of chips for a hundred hungry guests — or, in system terms, a single database for 300 million users.
</Callout>

## Why estimate at all

Every major design decision is **scale-dependent**. Single database vs. sharded cluster, sync vs. async replication, relational store vs. object store — all of them hinge on the numbers. A system serving 10,000 users a day can be one server with a Postgres instance. A system serving 300 million users a day needs a fundamentally different architecture.

You're not aiming for precision. Production teams have monitoring and load tests for that. In an interview, you just need to know whether you're designing for **tens, thousands, or millions** of requests per second, and whether storage is in **gigabytes, terabytes, or petabytes**. Getting the magnitude right narrows the design space and stops you from defending an architecture that would collapse under real load.

Interviewers watch for this step specifically. Skip straight to boxes and you look like someone who designs by intuition. Do a quick, confident estimate — even a rough one — and you signal that you've built systems at scale and understand that **load shapes architecture**.

## The building blocks: sizes and powers of ten

Work in powers of ten and anchor to a few memorized data sizes. That's the whole trick.

| Unit | Bytes | Rough shorthand |
|------|-------|-----------------|
| 1 KB | ~10^3 | thousand |
| 1 MB | ~10^6 | million |
| 1 GB | ~10^9 | billion |
| 1 TB | ~10^12 | trillion |
| 1 PB | ~10^15 | quadrillion |

Common field sizes to memorize:

| Data type | Size |
|-----------|------|
| 1 ASCII character | 1 byte |
| 32-bit integer | 4 bytes |
| 64-bit long / timestamp | 8 bytes |
| UUID | 16 bytes |
| Typical URL | ~100 bytes |
| A 280-char tweet + metadata | ~300 bytes |

<Callout type="tip">
**In practice — the powers-of-ten cheat sheet.** Round everything to the nearest power of ten and let the zeros do the work. A tweet is "a few hundred bytes," a photo is "about a megabyte," a video is "tens of megabytes." Add up fields to size a row, then multiply. If you're ever off by less than 10x, you're fine — the design decision won't change.
</Callout>

## Traffic estimation: from users to QPS

Traffic estimation walks forward from your user base to requests per second in a few steps.

- **Step 1 — Daily Active Users (DAU).** Pull this from requirements. "Design Twitter at current scale" → state ~300M DAU and move on. A brand-new product → anchor to a plausible target and say so out loud.
- **Step 2 — Actions per user per day.** How often does the average user do the core write? A social user posts maybe 0.1–1 time/day; a chat user sends dozens of messages/day.
- **Step 3 — Average QPS.** Divide total daily actions by seconds in a day.
- **Step 4 — Peak QPS.** Multiply average by 2.
- **Step 5 — Read/write ratio.** Multiply write QPS by the ratio to get read QPS.

<Callout type="tip">
**In practice — the one formula that matters.**

```
QPS = DAU × actions per user per day ÷ 86,400
```

Round **86,400 seconds/day to ~100,000 (10^5)**. So "1 million actions/day" is ~10 QPS, "1 billion/day" is ~10,000 QPS. This single approximation turns messy division into shifting zeros.
</Callout>

**Peak, not average.** Traffic is never uniform — social spikes on big events, e-commerce on sales, news on breaking stories. Size for the peak:

```
Peak QPS = 2 × Average QPS
```

A system that survives average load but dies on spikes fails at the worst possible moment.

**Read/write ratio.** Most systems are **read-heavy**. A timeline is read far more than it's written. If write QPS is 34 and the ratio is 10:1, read QPS is 340. These drive different decisions: write QPS sizes your **primary database and write path**; read QPS sizes your **caching and read replicas**.

| System | Typical read:write | Why |
|--------|-------------------|-----|
| Social feed / timeline | ~100:1 | Everyone scrolls, few post |
| E-commerce catalog | ~50:1 | Browsing vastly exceeds buying |
| Messaging | ~1:1 | Every send is roughly one read |
| Analytics ingestion | write-heavy | Writes flood in, reads are batched |

## Storage estimation

Once you know the write rate, storage is just multiplication:

```
Storage per day  = write QPS × record size × 86,400
Storage per year = Storage per day × 365
```

Then apply two multipliers people forget:

- **Retention.** Keep data 5 years? Multiply by 5. Append-only data (logs, events, messages) grows without bound until you archive or delete — so state your retention assumption explicitly. It's a design decision, not a given.
- **Replication.** Store 3 copies for durability and your real footprint is 3x the logical size. Object stores like S3 handle this internally, but if you're provisioning raw disk for a database cluster, the replication factor matters.

## Bandwidth estimation

Bandwidth is data flowing over the network per second. It's separate from QPS because payloads vary wildly in size.

```
Inbound  bandwidth = write QPS × average write payload
Outbound bandwidth = read  QPS × average read response
```

Many small reads (profiles, short posts) → modest outbound. Large media (video, hi-res images) → outbound **dominates** and becomes the primary concern. CDNs exist largely to push that bandwidth closer to users and spare the origin — a decision that's only obvious once you've estimated bandwidth first.

## Where estimation changes the design

- **Small text records (tweets, comments)** → storage is trivial; the challenge is read fan-out and caching.
- **Large media (video, images, backups)** → storage and bandwidth explode into petabytes; pushes you to object storage + CDN + compression.
- **Append-only streams (logs, events)** → unbounded growth; forces retention policies, tiering, and archival.
- **Bursty consumer traffic (social, e-commerce)** → the 2x peak multiplier drives autoscaling and queue buffering.

## The biggest mistake

<Callout type="warning">
**The #1 error: designing for average load and forgetting peak.** Your math says 34 QPS, you provision for 34, and the system tips over the moment a spike hits 3x average during a viral event. Always carry the **peak (≥2x)** number forward into every capacity decision.

A close second: **skipping replication and retention**. A "320 GB/year" text estimate quietly becomes a multi-petabyte problem once you add media, 3x replicas, and 5-year retention. State those multipliers out loud so they don't ambush you.
</Callout>

## Worked example: Twitter scale

Let's put it all together on a Twitter-scale estimate.

**Given:** ~300M DAU; ~1% post per day; average tweet ~300 bytes of text; ~10% of tweets carry a ~1 MB media attachment; read:write ratio 10:1.

**Write QPS:**

```
Tweets/day        = 300,000,000 × 1%     = 3,000,000
Average write QPS = 3,000,000 ÷ 86,400   ≈ 34/second
Peak write QPS    = 34 × 2               ≈ 70/second
```

70 peak writes/second is undemanding — a single well-provisioned database handles it easily. The read path is where it gets interesting.

**Read QPS:**

```
Read QPS      = 34 × 10   = 340/second
Peak read QPS = 340 × 2   = 680/second
```

680 read QPS is still manageable, but a single timeline request may fan out to many individual tweet reads for someone following thousands of accounts. That's why Twitter's real challenge is **fan-out**, not raw QPS.

**Text storage:**

```
Daily  = 34 × 300 bytes × 86,400  ≈ 880 MB/day
Yearly = 880 MB × 365             ≈ 320 GB/year
```

320 GB/year of text is trivial — years of tweets fit on one SSD. Text is not the bottleneck.

**Media storage:**

```
Tweets with media/day = 3,000,000 × 10%   = 300,000
Media/day             = 300,000 × 1 MB    ≈ 293 GB/day
Media/year            = 293 GB × 365       ≈ 107 TB/year
```

107 TB/year is a completely different animal. That single number explains why Twitter stores media in object stores like S3 (not the primary DB), serves it through CDNs, and compresses aggressively. The estimate revealed the real architectural driver — **media, not text** — in under five minutes, before drawing a single box.

## Summary

Capacity estimation is party-planning math for systems: aim for the **right order of magnitude**, not precision. Start from DAU, compute **QPS = DAU × actions ÷ 86,400** (round the seconds to ~100k), and always carry the **2x peak** number forward. Multiply write QPS by record size for storage, then apply **retention and replication** multipliers that quietly turn gigabytes into petabytes. Split traffic by **read:write ratio** to know whether to invest in caching or the write path — and let the numbers, computed in a few confident minutes, reveal the real bottleneck before you draw a single box.
